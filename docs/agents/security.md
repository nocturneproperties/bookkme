# Security rules

Read before adding a sensitive action, an email code, a single-use token, data taken from another service, or changing the Android signing certificates. Moved out of `AGENTS.md`; every rule here is as binding as one there.

- **Never accept another service's identity/pricing data as free text from the client.** A snapshot field sourced from another service's data (an employee's name, a client's contact info, a service's price/duration, …) must be resolved server-side via a synchronous internal client call at write time (`BusinessClient`-style, see `service/business/client` + the `Api.Internal.*` routes it calls) — the wire DTO the client submits carries only the foreign id(s), never the name/price/etc. it claims. When a caller always needs the same set of related fields together (e.g. an appointment booking needs its employee, client and services in one shot), resolve them with one combined operation/HTTP round trip instead of one call per entity — fewer network failure points, and a slim consumer-shaped aggregate type (see `BusinessDTO`, `AppointmentBookingContext`) is normal here rather than reusing raw domain entities 1:1. There are exactly two booking flows, each with its own route and its own business lookup, every field required: a user booking for themselves (an employee booking themselves included) sends `AppointmentRequestDraft` to `POST /api/appointments/request`, and appointments calls `GetAppointmentBookingContext(businessId, employeeId, userId, serviceIds)`, which finds, takes over or creates the caller's client row; an employee booking an existing client sends `InstantAppointmentDraft` (the same plus `clientId`) to `POST /api/appointments/instant`, and appointments calls `GetStaffBookingContext(businessId, employeeId, clientId, serviceIds)`, which only reads the business's client row (`BUSINESS_CLIENT_NOT_EXISTS` otherwise). Never merge the two into one request with nullable ids. Who may book into an employee's schedule on the instant path is today's appointments permission, `assertOrSelf(UPDATE, actorId = caller, assigneeId = employee.userId)`: the update grant books anyone in the business, a view grant only oneself; it runs in its own transaction before the booking transaction so the booking still locks first. Both booking paths check the quote token through `BookingQuoteVerifier` and throw the shared `BookingQuoteError` (`PriceChanged`, `DurationChanged`, `ServicesSignatureMiss`, `TokenAlreadyUsed`). The instant route once took a whole `Appointment` from the body and checked only `userId == initiatorUserId`, a field from the same body, so anyone could book any business at any price.

- **A sensitive action is confirmed with a passkey action confirmation token, never by trusting the session alone.** The app gets one from `POST /api/auth/passkey/confirm_action` (`ConfirmAction`, `docs/operations/authorization/action-confirmation.md`): a fresh assertion of the caller's own passkey, then a 2-minute JWT signed with auth's keys whose audience is `TokenAudience.actionConfirmation` (`<domain>/action-confirmation`, never the access audience, so the two can't stand in for each other; `TokenValidationTest`) and whose claims (`ActionConfirmationClaims` in `library/actionconfirmation/api`) bind it to `user_id`, `action`, `business_id` and `target_id`, with a unique `jti`. The protected operation wraps its work in `ActionConfirmationGate.spend(token, grant, rejection) { … }` (`library/actionconfirmation`, bound per scope by `actionConfirmationModule(Scope)`): it checks the token with `ValidationType.ACTION_CONFIRMATION` and all four claims against the `ActionConfirmationGrant`, spends the `jti` once with the single-use pattern below, before the work and so before its transaction, and releases it on any failure or cancellation. Build the grant with its factory (`ActionConfirmationGrant.clientDeletion`, `personalDataExport` with `businessId = Uuid.NIL` and the caller as target, `businessDataExport`), never by hand. A new action is a new `ConfirmableAction` entry, its `ActionConfirmationClaims.ACTION_*` string, its branch in `ConfirmActionImpl` and an `ActionConfirmationGrant` factory. Test an operation behind it with the real gate from `ActionConfirmationTestTokens` (`testFixtures(projects.library.actionconfirmation.impl)`: `tokenFor(grant)`, `isSpent(tokenId)`), never a mocked gate. Any passkey check of a signed-in caller must use `FinishAssertion.finishOwnedBy(userId, request)`: the sign-in challenge names no user, so a bare `FinishAssertion` accepts any account's passkey (account deletion did until 0.17.0). Only sign-in itself, which takes its identity from the passkey, calls it directly.

- **An email code goes through `library/email`, never a hand-rolled cache key** (`docs/email-verification.md`; `emailModule(Scope)`, reading `APPLICATION_HOSTINGER_MAIL_TOKEN`, `APPLICATION_HOSTINGER_MAILBOX_ID` (only for a real token), `APPLICATION_EMAIL_SENDER_NAME` and `APPLICATION_EMAIL_CODE_SECRET`, at least 32 bytes). The API token `development_token` (`LoggingEmailSender.DEVELOPMENT_API_TOKEN`) binds `LoggingEmailSender` instead of `HostingerEmailSender`: nothing is sent, and every email's text body, code included, is logged at INFO under a WARN at startup. Only `deployment/dev` sets it; in prod a logged code would let anyone reading Loki sign up with or switch to any address, so the monolith role refuses to deploy with it (or `CHANGE_ME`) in `vault_hostinger_mail_token`, and refuses an unset `vault_hostinger_mailbox_id`. Mail goes out from that mailbox's own address (the Mail API has no `from` field) under the sender name `BookkMe`, and the code secret comes from `vault_email_code_secret` (`monolith_env`). Codes and the per-address cache keys are HMAC-SHA256 under that secret (`EmailCodeHasher`), never a bare hash: a 6-digit code's plain SHA-256 is reversed from a Valkey dump in milliseconds, and a hashed address is confirmed by hashing a guess. Rotating the secret only invalidates codes still pending (10 minutes). `EmailCodeIssuer.issue(email, purpose, ownerId, render)` claims a 60-second per-address cooldown, counts the send against 5 an hour, stores only the code's HMAC, mails the code through `EmailSender` (the Hostinger Mail API; a 422 `ERR_VALIDATION_FAILED` whose `params` name `to` or `to.<n>` becomes `EmailSendError.Undeliverable`, 429 and 5xx are retried twice; a bounce after the API accepted the message is never reported back) and only then makes it the owner's current code, so a failed send keeps the previous code working and releases the cooldown, while the hourly count stays spent. `EmailCodeRedeemer.redeem(verificationId, code, ownerId) { verified -> … }` works like `ActionConfirmationGate.spend`: it accepts only the owner's newest code, counts the attempt (a sixth one ends the verification), claims a `:redeemed` key and releases it if the work fails or is cancelled. Do the write that depends on the address inside that block, never send an email inside `transactionManager.transaction { }`, and test against the real store on `InMemoryCacheClient(timeSource = …)` with a mocked `EmailSender`; an operation in another module tests against `EmailTestMailbox` (`testFixtures(projects.library.email.impl)`: the real issuer and redeemer, a recording sender, `codeSentTo(email)`, `refusesDelivery`), never a mocked issuer or redeemer. Its errors are `EmailErrorCodes` 910001–910005. **Every stored email is verified or a Telegram account's placeholder, so nothing downstream checks whether it is.** The placeholder (`library.email.PlaceholderEmail`, `<telegram user id>@telegramundeliverable.org`, a domain nobody controls) is never mailed: `emailModule` wraps every sender in `PlaceholderRefusingEmailSender`, which answers `EmailSendError.Undeliverable` without calling the API, `EmailCodeIssuer` refuses it before claiming a cooldown, and `EmailNotificationSender` skips it silently. A new email path goes through that sender, never around it. Sign-up emails a code with the passkey challenge (`StartRegistration`, owner = the challenge's `requestId`, which lives as long as the code) and `FinishRegistration` redeems it before verifying the passkey, so a mistyped code doesn't spend the challenge, and creates the user with the redeemed address, never `userInfo.email`. After sign-up a user's address is written only by `ChangeUserEmail` (internal `POST /api/internal/user/{id}/email`), called by auth's `ConfirmEmailChange` once the code `StartEmailChange` sent to the new address is redeemed (owner = the caller). `EditUser` never writes the email and answers a different one with `EMAIL_CHANGE_REQUIRES_VERIFICATION`. A redeem block checks `verified.purpose` (`EmailPurpose`), and a new path that stores an address must go through a redeemed code too. The code emails are rendered by `AuthEmails` from `i18n/auth_emails*.properties` in the `Accept-Language` language.
- **Notification emails go only to the address the user service published.** Notifications stores it from `UserEvent.Updated` (sent by `CreateUser` at sign-up, `ChangeUserEmail` and `EditUser`) in `notification_email_targets`, so it is always verified or a placeholder, which it skips; a new writer of a user's email must publish that event in its transaction, or the user stops getting email. `EmailNotificationSender` reads the address and `DeviceDataSource.getLastUsedLanguage` (the device signed in to last, English without one) in a transaction and sends through `EmailSender` (`emailModule(NotificationsScope)`, which needs `APPLICATION_HOSTINGER_MAIL_TOKEN`, `APPLICATION_HOSTINGER_MAILBOX_ID` and `APPLICATION_EMAIL_SENDER_NAME`) outside it. `NotificationParameters.emailContent` HTML-escapes the rendered body, because its arguments (business, client and employee names, cancellation reasons) are user-entered; never interpolate them into `htmlBody` unescaped. `SendNotification` emails `NotificationType.ACCOUNT` even with the email channel off, and the email footer says so (`email.footer.account`); a new type picks its footer in `NotificationEmail.kt`.
- **Telegram Mini App sign-in trusts only Telegram's Ed25519 signature** (`POST /api/auth/telegram/sign_in`, `SignInWithTelegram`, `Ed25519TelegramInitDataVerifier`, `docs/operations/authorization/telegram-sign-in.md`). The raw `initData` is checked as Telegram's third-party validation describes: the signed text is `<bot id>:WebAppData`, a line feed, then every field except `hash` and `signature`, URL-decoded, sorted by key and joined as `key=value` lines, verified with Telegram's production public key (hard-coded; the test-environment key is never accepted, since test-server user ids are a separate namespace and would sign in as a production user with the same id). The server needs only the bot id (`APPLICATION_TELEGRAM_BOT_ID`; unset means the route answers 503 `TELEGRAM_SIGN_IN_UNAVAILABLE`, a non-numeric value fails resolution), never the bot token. Data older than an hour (`auth_date`) is `TELEGRAM_DATA_EXPIRED`, data dated more than a minute ahead is invalid, and nothing else in `initData` (username, photo, `start_param`) is trusted or stored. The account is found by `telegram_identity.telegram_id_index`, the `BlindIndex` of the decimal Telegram user id (`blindIndex()` binding of `library/encryption`, `APPLICATION_BLIND_INDEX_KEY`), so authorization still holds no plaintext personal data. A new account is created through `UserClient.createUser` with the Telegram first and last name and the placeholder email, then linked in auth's transaction, with `AuthEvent.UserDeleted` as compensation like passkey sign-up. Such an account has no passkey until the user adds one, so it can't pass `ActionConfirmationGate` (account deletion, data exports, client deletion) before that.

- **Single-use tokens are claimed with one atomic `CacheClient.setIfAbsent` (Redis `SET NX EX`), never a `get` check followed by a later `set`.** The two-step version lets concurrent requests with the same token both pass. Reserve before doing the work, keep the reservation on success, and release it (`delete`, best effort) on any failure, wrapping the work in `runCleaningUpOnFailure(cleanUp = { release… }) { … }`, so a rejected call doesn't burn the token (`CreateAppointmentRequestImpl` + `AppointmentRequestDataSource.reserveOfferToken`/`releaseOfferToken`). `InMemoryCacheClient` implements `setIfAbsent`, so datasource tests cover it.

**A change to the Android app's signing certificates must update the passkey relying party too.** `deployment/prod/nginx/static/android_well_known.json` (served as Digital Asset Links from a read-only bind mount, picked up by the next `make infra tags=nginx` without a config name to bump) lists the certificates' SHA-256 fingerprints, and WebAuthn checks the same certificates again as `android:apk-key-hash:<hash>` origins in `createRelyingParty` (`service/authorization/domain/impl/.../passkey/RelyingPartyFactory.kt`). Each hash is its fingerprint's raw bytes in unpadded base64url (`echo <fingerprint> | tr -d ':' | xxd -r -p | base64 | tr '+/' '-_' | tr -d '='`). Updating only the well-known file makes the app's passkey registration and sign-in fail the origin check (missed in `c9b2aa5c`). Keep both lists in sync in the same change, and bump the version, since the origins are code.
