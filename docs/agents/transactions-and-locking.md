# Transactions and locking

Read before writing an operation that locks rows, books a slot, or holds locks while waiting on something outside the database, and before writing a MariaDB locking test. Moved out of `AGENTS.md`; every rule here is as binding as one there.

- **`transactionManager.transaction { }` may run its block up to 3 times.** `core/data/map/Mapper.kt` maps MariaDB's write conflicts to `Error.TransactionConflict`: error 1020 "Record has changed since last read" (`innodb_snapshot_isolation=ON`, the default since 11.6) and deadlocks (1213 / SQLState `40001`), found anywhere in the cause chain. `ExposedTransactionManager` re-runs the whole block in a fresh transaction, with a fresh snapshot, up to `MAX_ATTEMPTS_ON_CONFLICT` (3) times with a short jittered backoff, and only then returns the conflict, which `respondWith` turns into a 409. Only the outermost call retries. A nested `transaction { }` (e.g. `CreateAppointmentRequestImpl` → `createAppointment`) makes a single attempt and passes the conflict up: re-running an inner block inside an outer transaction that already failed would be wrong. The manager tracks this with its own coroutine-context marker, not Exposed internals. It also sets `maxAttempts = 1` on every Exposed transaction: Exposed's built-in retry would otherwise re-run a block 3 times on *any* raw `SQLException`, including a constraint violation flushed at commit, and stack on top of this retry. Consequence for every operation: a block must be safe to re-run. Database writes are, since they roll back. Anything else in the block repeats on retry: a cross-service call is made again (harmless for the reads they are today). Don't add new non-database side effects inside a transaction block. `eventProducer.send` is not one: it is a database write (see the outbox rule in `docs/agents/events.md`), so only the attempt that commits leaves an event. Tests: `ExposedTransactionManagerTest` (H2) for retry/give-up/nesting, and `BusinessRowLockMariaDbTest` for a real 1020 (two updates of one service row) and a real deadlock (two transactions locking two business rows in opposite order), both recovering through the retry.

- **Every datasource call runs inside `transactionManager.transaction { }`, event handlers and consumers included.** `dbQuery { }` doesn't open a transaction: outside one, Exposed throws `IllegalStateException: No transaction in context.` A route's operation always had one, but an operation called only by an `EventHandler` was never exercised that way: `UpdateDeviceLanguage` and `SendNotification` failed on every delivery, and the consumers' own `exhaustedEventDataSource.save` failed too, so an exhausted event went back to the DLT forever (`Failed to persist exhausted event … No transaction in context.`). `KafkaEventConsumer`/`EmbeddedEventConsumer` therefore take the scope's `TransactionManager` and save through it. In tests, `InMemoryExhaustedEventDataSource(transactionManager)` rejects a save outside a transaction the same way. Give it the consumer's `mockedTransactionManager()` (`testFixtures(projects.core.domain.datasource)`), and assert an operation's transaction by recording `transactionManager.isInTransaction()` inside the datasource stub (`UpdateDeviceLanguageTest`). Keep non-database side effects (push, email) out of the transaction, since a conflict retry would repeat them: `SendNotification` reads the settings in a transaction and sends after it.

- **Take a row lock as the transaction's first statement, before any plain read — including the permission lookup.** MariaDB runs at REPEATABLE READ (nothing in `core` overrides it), and InnoDB fixes a transaction's snapshot at its *first* plain read. Lock first and the snapshot is taken after the lock is granted, so every later plain read sees what the previous holder committed. Read first (e.g. `getPermission`) and then lock, and two things go wrong. A later plain read still sees the old snapshot and misses rows committed while you waited, so two concurrent invitation creations could both take the last slot. Making that read a locking read doesn't rescue it either: MariaDB ≥ 11.6 ships `innodb_snapshot_isolation=ON`, so a locking read that meets a row changed after the snapshot fails with error 1020 "Record has changed since last read" (a 500). Whether that happens depends on the query plan: `hasServices` escaped only because its `LIMIT 1` was answered from the `business_id` index. So: lock first, then plain reads (`CreateEmployeeInvitationImpl`, `UpdateBusinessImpl` when `currencyCode` is sent, `CreateServiceImpl`/`UpdateServiceImpl`, `DeleteServiceGroupImpl`; in appointments, approving a request locks the request, then the settings, then reads the permission, since an overlap check from a snapshot taken before the settings lock misses the booking it waited for), and pin the order with a `coVerifyOrder { lockBusiness(...); getPermission(...); … }` impl test. When an operation must call another service and must not hold a lock during that call, split it: check and resolve in a first short transaction and outside any transaction, then lock first in the writing transaction, compare the locked row with the one checked and answer `Error.TransactionConflict` (409) if it changed, and repeat the checks after the locks (`UpdateAppointmentImpl`). Return the mismatch out of the block and throw the conflict after it: a `TransactionConflict` thrown inside `transaction { }` makes `ExposedTransactionManager` re-run that same block three times for nothing. Keep any check that depends on the lock result (e.g. "the stored currency is unsupported") until after the permission check, so a caller without access learns nothing. `Query.forShare()` (`core/data/RowLocking.kt`) emits `LOCK IN SHARE MODE` on MariaDB and falls back to the stronger `FOR UPDATE` on H2, which has no shared row lock; use it for the lock itself, not for reads after a snapshot exists. H2 can't reproduce snapshot or lock-mode behavior, so test locking against a real MariaDB with `BusinessRowLockMariaDbTest` as the template: testcontainers `mariadb:11.8.3-ubi9`, schema from the real Flyway migrations via `createDatabase`, holder/waiter interleavings ordered with `CompletableDeferred` plus polling `information_schema.INNODB_TRX` for `trx_state = 'LOCK WAIT'` — **more slowly than every 100ms** (`SLOWER_THAN_INNODB_TRX_CACHE_REFRESH`): InnoDB serves `INNODB_TRX` from a cache it refreshes only after 100ms *without reads*, so a 10ms poll that first reads just before the waiter blocks keeps getting the stale snapshot forever (this was the 'flaky under load' timeout of `BusinessRowLockMariaDbTest` and `OutboxRelayMariaDbTest`), and `SET SESSION innodb_lock_wait_timeout = 1` to make "would block" fail fast. Two more traps in such tests. Every test in the class shares one container, so rows earlier tests left behind change which gaps a scan locks (and can change the plan): a "does it block?" test passed or failed depending on test order until `ClientRetentionMariaDbTest` (business) emptied the tables in a `@BeforeEach` (a blocking `transaction(db = database) { … }`, not `runBlocking`). Give the waiting side its own single-connection pool (a second `createDatabase(…, maxPoolSize = 1)`; Flyway does nothing the second time), so its `SET SESSION innodb_lock_wait_timeout = 1` never reaches a connection another transaction borrows: resetting it in a `finally` runs before commit, where Exposed still flushes pending inserts that would then wait the default 50 seconds. And wrap the waiter's whole `suspendTransaction` in `runSuspendCatching`, not just the call inside it: when a DAO insert times out inside the block, Exposed still flushes the pending child inserts at commit, outside an inner catch, so the test fails on a foreign key error instead of reporting the lock wait. Assert the lock wait itself (a `SQLException` with `errorCode == 1205` in the cause chain), not just `isFailure`, and pair a "doesn't block at READ COMMITTED" test with a "blocks at REPEATABLE READ" one, so the first can't pass because the scenario never locked anything. Never write `Instant.fromEpochMilliseconds(0)` (every `stub()`'s default) into a MariaDB `TIMESTAMP` column: its range starts at `1970-01-01 00:00:01` UTC, and Connector/J sends the value in the JVM's zone, so it fits on a UTC+1 laptop and fails on CI's UTC runner with `Incorrect datetime value`, reported as `SQLSyntaxErrorException` (Connector/J maps SQLState class `22` to it; `ClientRetentionMariaDbTest`). Use an old in-range date (`Instant.parse("2000-01-01T00:00:00Z")`). Reproduce CI's zone with an init script, since the worker JVM ignores `TZ`/`JAVA_TOOL_OPTIONS`: `allprojects { tasks.withType(Test).configureEach { systemProperty "user.timezone", "UTC" } }`, passed as `./gradlew -I utc.init.gradle …`.

- **A transaction that holds row locks while it waits on something outside the database must not take gap locks.** `OutboxRelay.relayBatch` locks its batch (`SELECT … ORDER BY id LIMIT n FOR UPDATE`) and keeps the locks while Kafka acknowledges; at the default REPEATABLE READ, a scan that reaches the end of the table also locks the gap after the last row, so every business write's outbox `INSERT` waited behind a slow broker until `innodb_lock_wait_timeout` (proved by `OutboxRelayMariaDbTest`). It runs at `transactionManager.transaction(TransactionIsolation.READ_COMMITTED) { }` instead (record locks only). `mockTransaction()` stubs both `transaction` overloads. Publish a batch with `RawProducer.publishAll`: Kafka sends every record, then awaits all acks (one round trip, per-partition order kept by the single idempotent producer), tested with `MockProducer(autoComplete = false)` through `KafkaEventProducer`'s internal `Producer` constructor.

- **Appointment/request double-booking is guarded by a lock, not a unique index.** Every write that books a slot (`CreateAppointment`, `UpdateAppointment`, `CreateAppointmentRequest`) first takes `AppointmentSettingsDataSource.getForUpdate(businessId)`, which serializes them per business, then runs `hasOverlapsWith` (active statuses only). Don't put a unique index on `(user_id, business_id, date_start)` or similar slot columns: it also counts cancelled/declined rows, so rebooking a freed slot fails with a 500 (that index existed until `V7` for exactly this reason). A new booking path must take the same settings lock before its overlap check.
