# Events

Read before sending events, adding an event handler or touching consumers. Moved out of `AGENTS.md`; every rule here is as binding as one there.

- **Every event goes through the transactional outbox, so `eventProducer.send` must run inside `transactionManager.transaction { }`.** In every service scope `StandardEventProducer` is `OutboxEventProducer`: it stores the encoded event in the service's own `outbox_event` table within the caller's transaction, and `OutboxRelay` publishes committed rows afterwards (`docs/transactional-outbox.md`). A rollback or conflict retry discards the row together with the write, so an event exists exactly when its write committed. A `send` outside a transaction throws `IllegalStateException` (checked with `transactionManager.isInTransaction()`) and the event is lost, so a compensating send after a failed transaction needs a transaction of its own (`FinishRegistrationImpl`'s `onFailure`). A service that starts sending events needs an `outbox_event` migration (the same SQL as `business/V15`), the table in its ER diagram, and `outboxModule(Scope)` in both module builders. Each service's `<Svc>ModuleTest` pins that wiring through `serviceScopeWithMockedInfrastructure(Scope, module)` (`testFixtures(projects.library.outbox)`), which mocks the transaction manager, transport producer, consumer and root `CacheClient`, so the real modules resolve without env vars or a broker. `mockTransaction()` reports `isInTransaction()` as true while a mocked block runs, so an operation test can assert that a send happened inside one. Consumer-side DLT sends go to `KafkaEventProducer` directly, never through the outbox.

- **Event consumers deduplicate per consumer group with an atomic claim, never a read-only "was it processed?" check.** `KafkaEventConsumer` and `EmbeddedEventConsumer` both run every receiver through `IdempotentDelivery` (`core/data/eventstreaming/impl`), backed by `CacheEventIdempotencyStorage` (`core/data/repository`, bound in `commonModule()`): `claim` is one `setIfAbsent` on `event:<consumerGroup>:<topic>:<idempotencyKey>` (1-min claim, `EventIdempotencyStorage.claimTtl`; a key that vanishes between the `SET NX` and the read is claimed again, not reported in progress), a successful handler then `markProcessed` (kept 1 hour, `PROCESSED_TTL`: every redelivery path — DLT retries, the `IN_PROGRESS` wait, an outbox batch republished after a crash or deploy, a Kafka rebalance — arrives within minutes; a Kafka consumer that stays down longer than that with processed-but-uncommitted offsets would handle those events again, and so does a hand replay of `exhausted_event`, which is meant to; it was 24 hours, which made the markers the bulk of Valkey's memory), and a failed or cancelled one `release`s the claim (under `NonCancellable`) before the DLT retry, so the retry can claim it again. Every `deliver` call claims and releases under its own random `deliveryId`, stored in the claim record, and `release` is a compare-and-delete on it (`CacheClient.deleteIfEquals`: a Lua `GET`-compare-`DEL` on Redis, `computeIfPresent` in `InMemoryCacheClient`): a handler that outlived its claim must not free the claim of the delivery that took over, or wipe the processed marker it left, which let a third delivery handle the event again (`IdempotentDeliveryTest` reproduces it in virtual time via `inMemoryEventIdempotencyStorage(testTimeSource)`; `InMemoryCacheClient(timeSource = …)` drives Caffeine's expiry from a `TestTimeSource`/`testTimeSource`, so TTL tests never wait; like Valkey's `SET … EX`, every `set` replaces the key's expiration (`WritingExpiry`) and a `deleteIfEquals` that doesn't match leaves it untouched (`InMemoryCacheClientTest`) — with `Expiry.creating` the processed marker silently kept the claim's 1-minute TTL, so marker-lifetime tests passed for the wrong reason). A cancellation the handler throws itself (a `withTimeout` inside it) is an ordinary failure and retried; only the consumer's own cancellation (`ensureActive()`) stops the delivery. `IN_PROGRESS` (another delivery holds the claim, or a crashed one left it) is waited out: `IdempotentDelivery` re-claims every second for up to `claimTtl`, so a crashed delivery's event is handled once its claim expires instead of being parked. A parked event is deleted 30 days after it was parked (`ExhaustedEventReplayerImpl.DEFAULT_RETENTION`, `deleteParkedBefore` on every tick), since its payload can hold personal data. Until then it is replayed by `ExhaustedEventReplayer` (`docs/exhausted-events.md`): every start marks all parked rows `replay_requested`, and a 1-minute loop locks requested rows (READ COMMITTED, like `OutboxRelay`), hands each to `Consumer.replay` — which publishes it to that consumer group's own DLT topic with attempt 0 and a new random key, so no other group sees it and a re-failure parks a new row instead of hitting the old row's unique key — then deletes the replayed rows and clears the request on rows the consumer refuses (no receiver, undecodable, embedded consumer not started), so a poison row can't loop. It also exports `events_exhausted{consumer_group, topic}` (the `MeterRegistry` from `startServer`, bound in Koin by `meterRegistryModule`), which drives the `EventsExhausted` alert. `startEventHandling` starts every scope's `EventHandler`s before any replayer: an embedded publish to a topic nobody has subscribed to yet is silently dropped. Only a claim still held after the TTL, or a failed claim, goes through the DLT; a failed `markProcessed` is only logged, since the handler already succeeded. A handler must therefore finish within `claimTtl`. `deliver` returns `DeliveryOutcome` (`HANDLED` / `SKIPPED_DUPLICATE`) so logs tell a skipped duplicate from a processed event. DLT topics are per consumer group (`DltRetry.dltTopic(topic, consumerGroup)` = `<topic>_<consumerGroup>_dlt`): with one shared `<topic>_dlt`, every group subscribed to it and re-ran every other group's failures, multiplying retries (7 attempts instead of 3 with two failing groups). Two things this replaced, both silent event loss: the old `isEventProcessed` was the HTTP `getResponseOrLock`, which *writes* an in-progress lock on a miss and was never released, so every DLT retry saw it and skipped the event; and the key was `topic:idempotencyKey` with no consumer group while every service shares one Redis (`redis_local`, no key prefix), so of the four `AuthEvent.UserDeleted` consumers only the first to check handled it. The consumer group is part of the key, not the instance: replicas of one service share it, which is what makes a rebalance redelivery a duplicate. Test consumers with `inMemoryEventIdempotencyStorage()` (`testFixtures(projects.core.data.eventstreaming.impl)`, the real storage on `InMemoryCacheClient`), never a hand-written fake: the old `RecordingIdempotencyStorage` fake had no lock side effect, which is why every DLT test passed while production lost the events.

- **An event with personal data implements `PersonalEvent` and names its one `dataSubject`** in a getter-only property (`override val dataSubject: DataSubject get() = …`, so it is never serialized): its outbox and parked copies are sealed whole under that person's key, and an event whose subject was erased is dropped instead of delivered (`docs/agents/personal-data.md`). Nothing is registered; the relay opens sealed bytes without knowing the type. Sealing stays out of core: a consumer parks through `ExhaustedEventDataSource.save(event, dltEvent)`, which returns `Parked.Stored` or `Parked.SubjectErased`, and `Consumer.replay` takes an `ExhaustedEvent` whose `ParkedPayload` is `Readable`, `SubjectErased` (dropped, the row is deleted) or `Unreadable` (kept). Every service scope calls `personalDataCipher()` (or `noPersonalDataCipher()`) and then `exhaustedEventDataSource()` from `library/outbox`, which binds `SealingExhaustedEventDataSource`.
