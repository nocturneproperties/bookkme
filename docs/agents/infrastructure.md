# Monolith and shared infrastructure

Read before touching the monolith wiring, database connection, token signing, internal HTTP clients, logging, metrics or the Redis cache client. Moved out of `AGENTS.md`; every rule here is as binding as one there.

**The monolith (`src/main/kotlin/com/bookk/server/MonolithServer.kt`) uses `EmbeddedEventConsumer`/`EmbeddedEventProducer`, never Kafka.** Each service has two module builders: `xModule()` (e.g. `authModule()`, `appointmentsModule()`) includes `eventStreamingTransportModule(Scope, SERVICE_NAME)` (Kafka) and is what the standalone microservice starts with, while `xEmbeddedModule()` includes `embeddedEventStreamingTransportModule(Scope, SERVICE_NAME)` (both from `core/data/eventstreaming/impl/.../di/DI.kt`). A service that sends events also includes `outboxModule(Scope)` in both, which binds its `StandardEventProducer` and `OutboxRelay` (see the outbox rule in `docs/agents/events.md`); notifications sends none and has neither. `MonolithServer.diModules()` lists every service's `xEmbeddedModule()`, plus one `topicQueueHolderModule()` providing a single root-level `TopicQueueHolder<String>` singleton shared by all five scopes. `TopicQueueHolder` is pub/sub, not a point-to-point queue: `subscribe(topic)` hands each caller its own `Channel`, and `publish(event)` fans the event out to every subscriber of that topic — this matters because several services' `EventHandler`s register receivers for the same topic (e.g. `AuthEvent.UserDeleted` is consumed by user, business, appointments and notifications), so a single shared `Channel` per topic would let only one of them win the event. When adding a new service to the monolith, register it the same way: give it an `xEmbeddedModule()` with `embeddedEventStreamingTransportModule(NewScope, NEW_SERVICE_NAME)` (plus `outboxModule(NewScope)` if it sends events) and add that to `diModules()`, no other wiring needed. The service name is not optional: it becomes the consumer group the idempotency storage keys on, and two services sharing one would skip each other's events.

**The monolith needs a single cross-schema DB user, unlike per-service deployments.** `createDatabase(schemaName, ...)` (`core/data/database/Migration.kt`) reads its host/port/user/password from `AppLevelConstants`, which is process-global (`System.getenv("APPLICATION_DB_*")`) — only `schemaName` varies per call. A standalone microservice gets one schema-scoped MariaDB user (`deployment/dev/db/init.sql` creates `user`/`authorization`/`business`/`appointments`/`notifications`, each granted only on its own database). The monolith runs all five services' `createDatabase` calls inside one process reading the same env vars, so it needs one MariaDB user granted on all five schemas — `init.sql` also creates a `monolith` user with `GRANT ALL PRIVILEGES` on each of the five databases. Root-cause a `FlywaySqlUnableToConnectToDbException` / `Access denied for user 'monolith'` in the monolith container before assuming a code bug: `init.sql` only runs on a MariaDB volume's *first* initialization, so a pre-existing dev `database_data` volume won't pick up a newly added user until the grants are applied by hand (`docker exec <db-container> mysql -h 127.0.0.1 -P 3307 -u root -p'<MARIADB_ROOT_PASSWORD>' -e "..."`) or the volume is recreated. Flyway in `createDatabase` connects with the schema in the JDBC URL (`jdbc:<url>:<port>/<schema>?createDatabaseIfNotExist=true`), not a bare host: with no default schema, Flyway's MySQL support "restores" the connection after migrating by running `CREATE SCHEMA`/`USE`/`DROP SCHEMA` on a random UUID name, which every schema-scoped user is denied, logging `Access denied … to database '<uuid>'` + `Unable to restore connection to having no default schema` on each startup (`MigrationMariaDbTest`). `createDatabase` connects with `sslMode=verify-full` on both its Flyway and HikariCP URLs: MariaDB ≥ 11.4 generates a self-signed certificate, which Connector/J ≥ 3.4 verifies against the login password (zero-configuration TLS, only for `mysql_native_password`/`ed25519` users with a password; `MigrationMariaDbTest` covers a `REQUIRE SSL` user and the refusal of a certificate it can't verify), so there is no CA to manage. Flyway's migrate runs inside `retryWhileDatabaseUnreachable` (`ConnectRetry.kt`): while the database can't be reached at all (an `UnknownHostException`, `SocketException` or `SocketTimeoutException` anywhere in the cause chain), it waits 1, 2, 4, 8 s, then 10 s, about 3 minutes over 20 retries, logging `Database unreachable …` each time. Every other failure is thrown at once. Don't use Flyway's own `connectRetries` instead: it retries every `SQLException`, so a rejected login or an unverifiable certificate also waited 3 minutes before failing (`MigrationMariaDbTest`'s certificate test caught it). `MigrationMariaDbTest` opens the database's port only after `createDatabase` has started, through an in-process TCP proxy (`LateProxy`). Each test schema needs its own `src/test/resources/db/migration/<schema>/V1__…sql`, or Flyway finds no migrations and the schema stays empty. After migrating, `createDatabase` connects Exposed through one HikariCP pool per schema (`poolName` = schema, `maximumPoolSize` from `APPLICATION_DB_POOL_SIZE`, default 10, `isAutoCommit = false`, REPEATABLE READ), so the monolith holds 5 × pool size connections (keep that under MariaDB's `max_connections`, 151 by default; the pool keeps them all open while idle, so ~33% is the idle baseline). `poolConfig` pings idle connections every 5 minutes (`keepaliveTime`, HikariCP's own default is off): anything between the app and the database that drops idle TCP flows (a swarm virtual IP after 15 minutes) must see traffic before it does (`PoolConfigTest`) and a transaction no longer opens its own connection. Hikari resets isolation and autocommit when a connection is returned (a READ COMMITTED `OutboxRelay` batch doesn't leak, `MigrationMariaDbTest` pins it), but not session variables: a `SET SESSION …` stays on that pooled connection for whatever borrows it next, so production code must never set one, and a test that does (`innodb_lock_wait_timeout = 1`) affects later transactions on the same `Database`. The root project itself carries the `bookk.microservice` convention plugin (`build.gradle.kts` applies it directly, not `.apply(false)`), so `./gradlew publishImageToLocalRegistry` with no module path builds and tags the monolith image as `bookkme-server:latest` (and `:<version>`) straight from the repo root, no subproject prefix needed.

The monolith registers `/jwks.json` once, combining `AuthScope` and `BusinessScope` through `jwks(AuthScope, BusinessScope)`; `authRoute()` and `businessRoute()` register no JWKS, each standalone `main` adds `jwks(<Scope>)` itself. Both services use the same issuer hostname in the monolith but keep separate signing keys. Registering their standalone JWKS routes together serves only auth's keys and makes `SERVICE_QUOTE` verification fail. `MonolithJwksTest` covers the combined active/retiring keys and standalone isolation. Because the monolith's issuer and key set are shared, only the audience tells token types apart: every `ValidationType` verifies against its own (`ValidationType.audience` in `TokenValidatorFactoryImpl`; `access` = the bare domain, `serviceQuote` = `<domain>/service-quote`, `actionConfirmation`), and an issuer writes the matching `TokenAudience`. Until 0.17.0 quotes used the access audience, so a quote's signature passed the access check and only `authTokenValidator`'s claim parsing (which threw a 500) stopped it. A new token type gets its own audience, `TokenValidatorFactoryImplTest` fails otherwise. `authTokenValidator` returns `null` (401) for a token without valid account claims.

- **An internal HTTP client is `internalHttpClient(System.getenv("APPLICATION_<SVC>_SERVICE_HOSTNAME"), clientTag)`** (`core/client`): Resources, the caller's service name as `User-Agent`, 3 retries on server errors, ProtoBuf, a fresh `Idempotency-Key` per request and `installInternalCallLogging()`. Bind it under its own named qualifier in the client module (`businessClientModule`, `authClientModule`, …): `userClientModule` binds its `HttpClient` unqualified, so a second unqualified one in the same scope would replace it. A new `APPLICATION_<SVC>_SERVICE_HOSTNAME` must be added to `monolith_env` (`monolith.service`), `deployment/dev/service/monolith.env` and the calling service's dev env file. A domain impl module that declares its own `@Serializable` class needs `alias(libs.plugins.kotlin.serialization)`: `bookk.domain.impl` doesn't apply it, and the missing serializer only shows at run time (`Serializer for class … is not found`). A `<Svc>ModuleTest` resolving something behind `ActionConfirmationGate` adds `single<TokenValidatorFactory> { mockk() }` next to the service module, since `startServer` provides it in production and `serviceScopeWithMockedInfrastructure` doesn't (`UserModuleTest`).

- **Log level and request metrics are set in `core`, not per service.** The root logger level comes from `APPLICATION_LOG_LEVEL` (default `info`; the dev env files in `deployment/dev/service` set `debug`). `logback.xml` must keep a single `<root>`: with two, logback applies the last one, which is how prod logged at DEBUG (`LogbackConfigurationTest`). To silence one known, harmless library message, add a `<turboFilter class="com.bookk.core.log.SuppressedMessageFilter">` with its `<logger>` and exact `<message>` format string (the `{}` template, not the rendered text), as for Yubico's `Allowed origin is not a valid URL` warning about the `android:apk-key-hash:` origins. Never raise the whole logger's level, which would also hide its real warnings. Every request is logged once at INFO by `installRequestLogging()` (`[status], METHOD path`), and `installRequestMetrics()` exports request durations as Prometheus histogram buckets (5ms … 10s, `ktor_http_server_requests_seconds_bucket`, aggregated with `histogram_quantile`) instead of Micrometer's default client-side percentiles, which cannot be combined across routes or instances (`RequestObservabilityTest`). Internal service-to-service HTTP clients install `installInternalCallLogging()` (`core/client`): request and response lines and bodies, written at DEBUG to the `com.bookk.core.client.InternalCall` logger, so they show in dev and never in prod (`InternalCallLoggingTest`). Ktor's `Logger.DEFAULT` logs at INFO whatever the level is, which is how prod logged every internal call's body; the `AppLevelConstants.BUILD_TYPE` switch that chose `BODY` was a compile-time `DEBUG` and is gone.

- **`RedisCacheClient` must return every borrowed connection to the pool:** `withPooledConnection { }` is `borrowObject().use { }`. Lettuce's pool hands out wrapped connections whose `close()` returns them; a bare `with(connectionPool.borrowObject())` opens a fresh Redis connection on every call and never closes it, which is how it leaked one connection per cache call until `RedisCacheClientTest` caught it. `withTransaction` queues writes on the **async** API between `MULTI` and `EXEC`, without waiting for replies: a coroutine command inside `MULTI` waits for a reply that only arrives at `EXEC`, so Lettuce's `coroutines().multi { }` hangs forever. If the action fails it sends `DISCARD` (through `runCleaningUpOnFailure`) before the connection goes back to the pool. Inside a transaction only `set`/`delete` work; `get`/`setIfAbsent`/`deleteIfEquals`/`increment` throw `UnsupportedOperationException`, since their result doesn't exist until `EXEC`. A counter with a lifetime (attempts, rate limits) is `increment(key, expiration)`: one Lua `INCR` + `PEXPIRE … NX`, so the first increment's expiration stays and later ones never extend the window (a fixed window, not a sliding one); `InMemoryCacheClient` keeps it the same way through `compute` and an expiry that keeps the current duration on an increment. `RedisCacheClientTest` runs against a real Valkey (`valkey/valkey:8.1.11-alpine`, the Redis fork every environment uses) via testcontainers (`GenericContainer`, Docker required, like the Kafka tests) and asserts `INFO clients` to catch pool leaks.
