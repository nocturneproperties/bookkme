# Business domain rules

Read before touching prices and currencies, client rows (uniqueness, takeover, merges) or device identity. Moved out of `AGENTS.md`; every rule here is as binding as one there.

- **Every amount inside one business is in the business currency.** Joda `Money.plus` throws `CurrencyMismatchException` on mixed currencies, and every total here is a plain `reduce { acc, price -> acc + price }` (`IssueQuoteImpl`, `Appointment.totalAmount`, `AppointmentRequest.totalAmount`), so a mixed-currency business turns quoting and booking into 500s. Hence: `CreateService`/`UpdateService` re-denominate the client's price into the business currency (`Money.inCurrencyOrNull`, `service/business/domain/impl/.../operation/service/BusinessCurrencyPricing.kt`; an amount with more decimals than the currency allows is `PricePrecisionInvalid`, not rounded), and `UpdateBusiness` rejects a currency change once `ServiceDataSource.hasServices` is true (`CurrencyLocked`; re-sending the stored code is always a no-op). Both sides go through `BusinessDataSource.lockBusiness(id, RowLock)`, which locks the business row and returns its currency: `UpdateService` takes `RowLock.SHARED` (updates don't block each other), `CreateService` and a currency change take `RowLock.EXCLUSIVE` (creation also counts against the service limit, see creation limits below), each as the transaction's first statement (see the lock-first rule in `docs/agents/transactions-and-locking.md`). A stored code `CurrencyValidator` rejects (legacy rows such as `usd`) doesn't lock, so the owner can still fix it, and service writes reject it with `BusinessCurrencyInvalid` instead of a 500. A new write that stores a price on a business entity must take the same lock and never trust the currency the client sends.

- **A client's email is unique per business, across detached and integrated clients alike; its phone is not** (`client_business_id_email_unique`, compared case-insensitively under `utf8mb4_uca1400_ai_ci`, so in-memory dedup lowercases; the phone has no index at all since business `V18` dropped `client_business_id_phone_unique` and `client_phone`). A business only ever creates detached clients (`CreateClient` takes `Client.Detached`, the route ignores `ClientRemote.userId`), and no business write looks a contact up in the user service: that would tell any business which phones have an account and hand it the user's profile. A detached client is only a placeholder for a person until they use the app: a user's first booking (`GetAppointmentBookingContextImpl`) takes over the one detached row holding their email (`ClientDataSource.getClientsByEmails` + `takeOverClient`, keeping its `id` — appointments store it as `client_id` — and `description`) and announces it with `BusinessEvent.ClientLinked` (empty `mergedClientIds`), so appointments records the account on that row's history (`LinkClientUser`). A profile email change that collides with a detached row of a business where the user is already integrated deletes that row and links it into the user's client the same way before the sync (`findClientMergesForUser`, `SyncUserProfileImpl`). **Never match a client by phone.** Only the email is verified (sign-up and `ConfirmEmailChange` prove it with a code), so a takeover or merge by phone hands a stranger's client row, its notes and appointment history to whoever typed that phone into their profile; a phone-only match gets a new row instead. User emails are unique too, so two integrated rows can't collide except transiently while two users swap an email. A write that stores a client email relies on the index alone and maps `.onConstraintFailure { }` to `BUSINESS_CLIENT_EXISTS` (`CreateClientImpl`, `UpdateClientImpl`); a lookup before the write is only for reporting per-row results, as in `ImportClientsImpl`, where one violation would otherwise fail the whole batch without naming the row. Batch imports are capped (`ImportClients.MAX_CLIENTS` = 500) because nothing caps a request body: Ktor decodes the whole ProtoBuf list before any check runs, and one transaction holds the whole batch. `EmailValidator` accepts lowercase addresses only and `PhoneValidator` rejects a space before `+`; both rules apply to single creates and imports alike.

**Creation limits are stored per business or per person, with the default in code.** Every create that grows a business or a person's footprint checks a limit: active employees (`CreateEmployeeInvitation`, `JoinBusiness`, and reinstating in `SetEmployeeSuspension`; suspended staff don't count, so suspending frees a place and reinstating must re-check), clients (`CreateClient`, `ImportClients`), services, service groups, pending appointment requests per user per business (`CreateAppointmentRequest`), businesses a person owns (`CreateBusiness`; one person may own several, and joining a business as an employee isn't limited), and passkeys per account. A business-related limit lives in a nullable column on the business's own row (`business.max_*`, `appointment_settings.max_pending_requests_per_client`) and a person-related one in a row the business service owns (`user_limits.max_businesses`, created by `UserLimitsDataSource.lockForUser` on the first business creation), never in another service, so the check needs no cross-service call; `NULL` means the code default (`BusinessLimits.DEFAULT_*`, `AppointmentSettings.DEFAULT_MAX_PENDING_REQUESTS_PER_CLIENT`, `UserLimits.DEFAULT_MAX_BUSINESSES`), resolved when the row is read, so changing a default later reaches every row nobody overrode. Only operators set the columns, with SQL; no route writes them, and no write path may store the resolved default back (`SettingsEntity` exposes it as `val`, `user_limits` rows are only inserted empty). Only the passkey limit and the saved-businesses limit are plain constants (`AttachNewPasskeyToAccount.MAX_PASSKEYS`, `SaveBusiness.MAX_SAVED_BUSINESSES`). The saved-businesses limit is the one deliberate soft cap: appointments has no per-person row to lock, and the developer chose to let two simultaneous saves end one over 100 rather than add a lock-only table, so `SaveBusiness` counts without serializing (and inserts with `INSERT IGNORE`, so a repeated save stays a no-op). Every other limit stays race-safe as described here. A business limit is read from `LockedBusiness.limits`, so the count runs under `lockBusiness(id, RowLock.EXCLUSIVE)` taken as the first statement: a shared lock would let two creations both see the last free slot. A person's count runs after locking their own `user_limits` row (`lockForUser`, `INSERT IGNORE` then `SELECT … FOR UPDATE` on the primary key). Don't lock a person through a range of their child rows instead (`getBusinessIdsOfUserForUpdate`): for someone with no rows yet that takes only a gap lock, and two such transactions deadlock when both insert into the gap. Check the limit after the permission check, so a caller without access can't learn the business is full, and before any write the failure would have to undo (`JoinBusiness` checks before redeeming the invitation). A limit error is a 422 `BusinessError` of its own per operation, reusing one code across operations (`BUSINESS_EMPLOYEES_LIMIT_REACHED` in both invitation and join). Bulk creates fill up to the limit and report the rest per row (`ImportClients` rejects them with `BUSINESS_CLIENTS_LIMIT_REACHED`) instead of failing the batch. A client's own booking (`getOrCreateIntegratedClient`) is never refused for the client limit, since that would turn away a paying customer. Every limit a caller can hit must have a way back under it through the API (suspending staff, `WithdrawAppointmentRequest`, deleting clients, services and groups), except owned businesses, which no route deletes yet, so an operator raises `max_businesses`; check a limit after the operation's own validation, so a request that is wrong anyway reports that error (`CreateAppointmentRequest` counts pending requests after the date, schedule and overlap checks).

**Device identity spans an account and installation.** Authorization and notifications both identify a device association by `(authId, deviceUuid)`, never by installation UUID alone. Notification creation must preserve the existing token and language on replay and reject a conflicting user. `DeviceDeleted` and `DeviceLanguageUpdated` carry `authId`; legacy payloads default it to `Uuid.NIL` and are rejected for manual reconciliation. Push-token routes take `authId` from `AppPrincipal`. Inactive-device deletion returns both fields through `DELETE RETURNING`, and failed sign-up only compensates the remote user: its device and creation outbox entry roll back together, so it must not emit a device-deletion event.
- **A business link name never contains `_`** (`BusinessLinkPolicy`, `^[a-z0-9]+(-[a-z0-9]+)*$`, 3 to 32 characters, pinned by `BusinessLinkPolicyTest`). The Telegram Mini App reads a `start_param` starting with `op_` as an operation BookkMe created (`docs/telegram-launch-parameters.md`), so a name with an underscore could make a business link look like an account deletion or export confirmation. Keep `_` out of the allowed characters whenever the link name rules change.
