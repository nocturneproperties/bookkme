# Build, formatting and CI

Read before changing Gradle files, formatting setup, opt-ins, workflows, images or Testcontainers. Moved out of `AGENTS.md`; every rule here is as binding as one there.

New gradle modules must be registered in `settings.gradle.kts` (one `include` per submodule, grouped per service). Convention plugins (`libs.plugins.bookk.microservice`, `bookk.domain.impl`, `bookk.domain.api`, `bookk.data`, …) already add Ktor/Koin/MockK/kotlin-test deps and JUnit platform — do not re-add them; `bookk.client` adds no MockK, so a client module with mocking tests declares `testImplementation(libs.mockk)` itself. **Declare each dependency once per build file**: IntelliJ warns `Dependency … is declared multiple times` for the same dependency in two configurations. `testImplementation` already inherits `implementation`, and `applyTestFixturesConvention()` (`build-src/.../convention/TestFixturesConvention.kt`, called by every convention plugin) makes `testFixturesImplementation` inherit it too, so neither repeats a main dependency. A main dependency whose types the fixtures hand to other modules' tests, or that appears in the main module's public API (a supertype, a public constructor parameter, a return type), is `api`, never `implementation` plus `testFixturesApi` (`core/data/eventstreaming/impl`: `KafkaTestBroker.drain` returns Kafka `ConsumerRecord`s). Fixtures of fixtures go through `testFixturesApi(testFixtures(…))` when the module's own tests need them as well (`core/service`). A module that needs only Kotlin applies `libs.plugins.bookk.kotlin`, never bare `libs.plugins.kotlin.jvm`, so it gets the same toolchain and opt-ins.

**Formatting is the official Kotlin code style, enforced by ktlint through Spotless.** `kotlin.code.style=official` (`gradle.properties`) sets IntelliJ's formatter, and `.editorconfig` runs ktlint (version `ktlint` in `gradle/libs.versions.toml`) with `ktlint_code_style = intellij_idea`, the ktlint style that agrees with that formatter, so IntelliJ's Reformat Code and ktlint don't fight (`ktlint_official` would). Spotless is configured once in the root `build.gradle.kts` over every `*.kt` and `*.gradle.kts` in the repository, build-src included. Run `./gradlew spotlessApply` after changing code; CI runs `spotlessCheck` before building and fails on any unformatted file. ktlint adds trailing commas to every multi-line argument and parameter list. Rules turned off in `.editorconfig`, each for a reason: `kdoc`, because the openApi plugin reads route KDoc inside `authenticate { }` blocks, which ktlint forbids; `class-signature`, because it wraps a single supertype constructor call onto its own line after the colon (`class X :` / `    BusinessError(`), which the official conventions don't ask for: keep `class X : BusinessError(` on one line; `package-name` only for the existing `build_src` and `delete_account` packages (a new package has no underscore). A file holding one class is named after it (`filename` rule). Never silence a rule with `@Suppress("ktlint:…")` in source; a rule that doesn't fit the project is disabled with its reason here.

**Lines are at most 120 characters** (`max_line_length = 120` in `.editorconfig`, which IntelliJ's formatter reads too). ktlint wraps argument lists, call chains, infix calls and lambdas itself. It doesn't wrap a long function or class signature, a `when` branch, a `) = Call(…)` body or a string literal, and spotlessApply fails on those. Fix them by hand: one parameter per line with a trailing comma (`): Result<X> = transactionManager.transaction {` stays on the closing line), a named value or helper for a long condition (`isReadyBefore(now)` in `DataExportsImpl`), a block body with `return`, or a string split with `+`. KDoc and comment lines are exempt, so a route's OpenAPI KDoc keeps one field per line. When Spotless hits a lint it can't fix in a file, it reports that one lint and leaves the **whole file unformatted**, so after each fix run spotlessApply again until it passes. A test name must leave `` fun `name`() = runUnitTest { `` within 120 characters (about 92 characters of name at class level, 85 with `runIntegrationTest`).

**ktlint-specific settings go in `ktlintOverrides` in the root `build.gradle.kts`, not `.editorconfig`.** Spotless reads standard keys like `max_line_length` from `.editorconfig` but ignored `ktlint_standard_<rule> = disabled` and `ktlint_ignore_back_ticked_identifier` there, even with a fresh daemon and no configuration cache. Passed through `editorConfigOverride`, they work. The overrides: `function-expression-body` is off because it rewrote every single-`return` block body into `= value` (block bodies are the convention, see `AGENTS.md`). `function-signature` is off because it collapses a wrapped parameter list back onto one line whenever it fits, then moves the body to the next line after `=` and re-indents all of it. With it off, a long signature is a lint you wrap by hand, as above. `ktlint_ignore_back_ticked_identifier` skips a line only when the backticked test name itself crosses column 120.

**Opt-ins live only in `build-src/.../convention/KotlinConvention.kt`; never write `@OptIn` in source.** Stdlib markers (`ExperimentalUuidApi`, `ExperimentalTime`) are enabled everywhere. A library's marker is listed with its `group:module` and enabled per compilation only when that module is on the compilation's resolved compile classpath (`-jvm` suffix stripped). Enabling a marker unconditionally makes every module without that library warn `Opt-in requirement marker … is unresolved`, and a module on bare `kotlin.jvm` got no opt-ins at all, so it warned `This declaration needs opt-in`. A new experimental API is a new entry in that map, not an annotation. The classpath check reads module ids from the dependency graph (`incoming.resolutionResult.rootComponent`), never from `incoming.artifacts.resolvedArtifacts`: artifact results carry the task dependencies of other modules' jars, so their provider can't be queried before those tasks run. A Gradle compile never noticed, but IntelliJ's sync runs no tasks, and the Kotlin plugin's lenient argument import swallowed the failure and imported an empty `optIn`, so the IDE flagged every opt-in, stdlib markers included, while Gradle compiled cleanly.

**CI and image publishing.** The monolith image (`ghcr.io/nocturneproperties/bookkme-server:<version>`) is published by pushing a `monolith/<version>` tag (`.github/workflows/monolith-publish.yml`); the workflow fails unless the tag equals `version` in the root `build.gradle.kts`, because Jib tags the image with the project version, not the git tag, and then calls `.github/workflows/deploy.yml`, which only runs `ansible-playbook playbooks/deploy.yml` (also runnable by hand with a version, for rollbacks). A successful `Publish monolith` run (published and deployed) triggers `.github/workflows/project-mark-released.yml` (adapted from the client repo's): it moves this repository's issues from `Done` to `Released` on the `bookkme-board` project (org project 1, shared with `bookkme-client`, so it filters on `content.repository`) and comments the tag on each, with the `PROJECT_TOKEN` secret for the project and `github.token` for the comments; a hand rollback through `deploy.yml` doesn't trigger it, a missed run can be dispatched with the tag. `workflow_run` fires only from the workflow file on the default branch (`main`), so it does nothing until merged there. `Build and test` (`push-build-and-test.yml`) runs only on pushes to `develop` and pull requests into `develop`, like the client repo: the `develop` → `main` release PR and its merge commit run nothing (they used to build and test the same code twice more), and the tag's publish workflow builds the image. Microservice images are still published, never deployed: an `auth/`, `user/`, `business/`, `appointment/` or `notification/<version>` tag runs `.github/workflows/microservice-publish.yml` (one workflow, the prefix picks the Gradle module, same version check). Every workflow runs on GitHub-hosted runners pinned to `ubuntu-24.04` (not `ubuntu-latest`, which moves to a new Ubuntu on GitHub's schedule; the repository is public, so they are free; there is no self-hosted runner stack any more), so the deploy job reaches the manager over SSH from the internet. Workflows never run `docker` against the swarm themselves, and never run the infra playbook (run it by hand). The deploy job installs Ansible with `uv`, pinned to the versions of a local Homebrew install, and it must pull with the registry token from the vault, not `GITHUB_TOKEN`: `--with-registry-auth` stores the credentials in the service for later pulls, and `GITHUB_TOKEN` expires with the job. Image tasks need `--no-configuration-cache`: Jib's task holds a `Project` reference the configuration cache cannot serialize.

**Every third-party image is pinned to an exact version, in dev, prod and Testcontainers alike** (`valkey/valkey:8.1.11-alpine`, not `8.1-alpine` or `latest`). A floating tag moves on its own: prod ran `nocodb/nocodb:latest`, and the next admin stack deploy would have upgraded NocoDB the day upstream published a release. An image with no version tags is pinned by digest instead (`strm/dnsmasq:latest@sha256:…`, last pushed in 2020; wg-easy is pinned the same way). To pin something already running in prod without upgrading it, read the resolved digest from `docker --context swarm-manager service inspect <stack>_<service> --format '{{.Spec.TaskTemplate.ContainerSpec.Image}}'` and look that digest up in the repository's tags on Docker Hub. Changing only the tag (same digest) still counts as a spec change for Swarm, which restarts the service on the next deploy. Our own Jib images in `deployment/dev` (`bookkme-*:latest`) are exempt, since the rollout scripts build them right before starting them.

Keep Testcontainers at **1.21.4 or newer** (`testcontainers` in `gradle/libs.versions.toml`). Docker Engine 29, which GitHub's `ubuntu-24.04` runners ship, rejects API versions below 1.44. Older Testcontainers (1.20.4) negotiate 1.32, so every container test in CI fails in `@BeforeAll` as `initializationError` / `IllegalStateException` ("Could not find a valid Docker environment"). The same tests still pass against a local Docker Desktop 27. Gradle stops at the first failing module, so CI usually reports only one such test (`MigrationMariaDbTest`).
