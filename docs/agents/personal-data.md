# Personal data

Read before touching data exports, legal documents, client and user ids on appointments, account or client erasure, dormancy or retention. Moved out of `AGENTS.md`; every rule here is as binding as one there.

- **A data export is a `library/export` row, built by a job, never in the request** (`docs/data-export.md`). A service offering one binds `dataExportModule(Scope)` and a `DataExportAssembler`, gets the `data_export` table in its migration (the same SQL as in user `V5`), registers `<svc>-buildDataExports` (10 s) and `<svc>-deleteExpiredDataExports` (1 h), deletes the owner's row in the owner's own erasure transaction (`DataExports.discard`), calls `subjectKeys(<SVC>_SHORT_RETENTION_SCHEMA, environment)` inside its `scope(Scope) { }`, with the environment lookup threaded from `<svc>Module(environment)` so the module tests can pass the keys (`UserModuleTest.KEY_ENVIRONMENT`, like `AuthModuleTest.EMAIL_ENVIRONMENT`) (every document is encrypted under a random key of its own, `data_export.key_id`, which a restart, expiry and `discard` shred in the same transaction; a row without `key_id` is never served), and starts it behind an action confirmation token (`ActionConfirmationGate.spend`, then `DataExports.start` as the transaction's first statement). The assembler calls other services outside any transaction and must finish within the 10-minute build lease; its `announceReady` runs inside the transaction that stores the document. Each service hands over its part of a personal export on `GET /api/internal/export/<service>/{userId}`, and appointments its part of a business export on `GET /api/internal/export/appointments/business/{businessId}`; a part's DTO lives where its consumer can depend on it (the service's client module, or business's domain api like every business client type). An appointment or request where the user is not the client is exported without the client's details, note or reasons (Art. 15(4)), and a new field holding another person's data in a personal export follows the same rule. Any erasure of a person a business holds discards that business's export in the erasure's own transaction (`DeleteClient`, `DeleteInactiveClients` for each business that lost a client, `ReapplyClientErasures`, and `DeleteUserBusinessData` for every business where the user had a client or employee record), so an erased person never stays readable in a stored document; a new erasure path in business does the same, through one `discardAll` for every business it touched, never a `discard` per business (`SubjectKeys.shredAll` likewise for many keys). An export whose owner isn't the caller (the business export) checks the caller's right in its own transaction before `ActionConfirmationGate.spend`, so a refused caller's token isn't spent and never sees the 429 that tells an export ran today, and again right after `DataExports.start` locked the row (`StartBusinessDataExportImpl`).

- **Which privacy policy and terms of service version each user accepted lives in the user service** (`docs/legal-documents.md`). Versions are rows in `legal_document_version` that the operator inserts by hand, the one in effect is the latest whose `effective_at` has passed, and `legal_document_acceptance` is append-only (`INSERT IGNORE`, a version's FK refuses its deletion once accepted). Only a version in effect can be accepted (`LegalDocumentError.VersionUnknown`, shared by sign-up's `CreateUser` and `AcceptLegalDocuments` through `publishedAcceptances`). Sign-up must accept the version in effect of every published document (`acceptedDocuments` is required on the wire, `CreateUser.Error.LegalDocumentsNotAccepted` otherwise, checked before the profile insert); after sign-up the server never blocks a user who hasn't accepted a newer version, the app does. A new document is a `LegalDocument` entry plus a nullable field on `AcceptedLegalDocuments` (no enum-keyed map on the wire).

- **The privacy policy and terms of service texts live in `docs/legal/`**: `bookkme/` for the BookkMe service we operate (gitignored, so it exists only in local checkouts and must never be linked from tracked files), `template/` for self-hosting businesses (public), each in English, Polish and Ukrainian. They state what each service stores, every retention period, and the processors. A change to any of those (a new personal-data field, a changed lifetime or job interval, a new email, push or other external provider, or a new SDK, device permission or on-device store in bookkme-client) updates both sets in all three languages in the same change, and the annexes of `bookkme/data-processing-agreement.*.md` (workspace data, retention, security measures, subprocessors), following the table in `docs/legal/README.md`, and the record of processing activities `bookkme/records-of-processing.en.md` (a new table or column holding personal data, a processor, a retention period or a security measure; its section 6), and the release notes tell the operator to publish a new BookkMe version. Never name BookkMe's hosting provider there; the self-hosting template may identify its own provider. Keep operator country, governing law, regulators and transfer safeguards explicit and deployment-specific; a translation does not select a legal regime. A privacy-policy acknowledgement is not blanket processing consent, and a free-text note is not by itself explicit consent to sensitive-data processing. Check `docs/legal/legal-review.md` for unresolved publication dependencies and preserve factual erasure limits, including retained appointment reasons.

- **Provider terms and crash reporting have a checked baseline in `docs/legal/provider-and-crashlytics-audit.md`.** Standard Cloudflare, Postmark and Firebase terms incorporate their data-processing arrangements; do not assume separate signatures are required. BookkMe Postmark message retention is 45 days, with suppression records kept longer; Google starts Crashlytics removal after 90 days rather than guaranteeing completion then. Android/iOS ship Crashlytics off by default (manifest/plist), opt-in in Settings, so the policies give consent as its basis; a persisted SDK choice overrides that default. Appointment history has no age-based expiry while the business exists, per the developer's decision; preserve separate client/account erasure. Support is by email only, kept 24 months after the last message in BookkMe's mailbox. `PostmarkEmailSender` sends every email with `TrackOpens=false` and `TrackLinks=None`, which the no-tracking statement in the policies relies on. Only BookkMe's employees and director may access production data, from the countries where they are located and never from Ukraine; the BookkMe policy and DPA say so and no longer offer a list of access countries, which their access does not need (not a Chapter V transfer). Giving a contractor access makes them a processor: DPA, Annex 3, both policies and the record of processing first. Mail to the legal and support addresses goes through Cloudflare Email Routing to a consumer Gmail mailbox (Google as controller, no DPA, an accepted risk), with replies through Postmark SMTP.

- **An appointment's `client_id` (`ClientSnapshot.id`) is the business's client row id, never a user id; the users on it are separate columns.** Integrated and detached clients alike get a random `client.id`, so matching it against a user id (`client_id = userId`) silently matches nothing: account deletion never cleared a user's details from appointments that way. Every appointment and request carries two users: `initiator_user_id` (`initiatorUserId`) is who booked, and `client_user_id` (`client.userId`, nullable) is the client's own account, resolved server-side (the booking context's client row, never the request body or the caller: on an instant appointment the caller is the employee) and cleared on erasure. Never use one for the other: `AppointmentEvent.*.clientUserId` carries `client.userId`, and notifications skip a client without an account. A request is the exception: only the client books one, for themselves, so `AppointmentRequest.client` is a `RequestClientSnapshot` whose `userId` is the caller and never null, `appointment_request.client_user_id` is `NOT NULL`, and `RequestCreated`, `RequestApproved` and `RequestRejected` carry a non-null `clientUserId`. Erasure deletes a request instead of clearing the column; `linkClientUser` only replaces it. Account deletion is handled inside appointments on `AuthEvent.UserDeleted` by `client_user_id` (`DeleteUserAppointmentData`): it cancels the user's upcoming scheduled appointments in both roles first, in one locking read (`client_user_id = ? OR employee_user_id = ?`, both indexed; a second locking read after the first one's plain read of the services could fail with 1020): as client with reason "User deleted their account", telling each one's employee through `AppointmentEvent.CancelledForDeletedClient` (no client name, it is sent after the erasure), as employee with "Employee deleted their account", telling a client with an account through `AppointmentEvent.Cancelled` (a stopgap until #137 reassigns them). It then clears the client snapshot and `client_user_id`, anonymizes the employee name and sets `employee_user_id` to `Uuid.NIL`, sets `initiator_user_id` to `Uuid.NIL` on appointments they booked (`unlinkInitiator`), and deletes the requests where the user is client or employee. Last, it drops every business the user owns (`detachBusinessesOwnedBy`, by `business_has_appointments.owner_user_id`, everything under it by cascade), after the notifications, which read the business snapshot: account deletion carries only the user id, and every service erases what it holds from it, with no follow-up events. `owner_user_id` is set from `BusinessDTO.ownerUserId` when appointments are enabled (never the caller, who may be an employee with a full grant; `EnableAppointmentsForBusiness` reads `deleted_user` for the owner first and refuses a deleted one) and kept by `BusinessEvent.Updated`. It is nullable until 0.19.0: rows created before 0.18.0 get it from the `appointments-fillBusinessOwners` job, which asks business over the client (never a cross-schema query, which fails between microservices that each have their own database server) and drops a business whose owner is already deleted; until then `BusinessEvent.Deleted` covers them. Business deletes the user's client and employee rows outright (`DeleteUserBusinessData`; the employee's services, hours, days off and grants go by `ON DELETE CASCADE`), never anonymizes them. It records the user in `deleted_user` first. Erasing by `client_user_id` is only correct while that column is complete, and a client row can gain an account after appointments were booked for it (a takeover or merge in business). So business announces it with one event, `BusinessEvent.ClientLinked(businessId, clientId, userId, mergedClientIds)`: the kept row, its account, and the duplicates deleted into it (booking takeover, or profile sync). Appointments moves the duplicates' rows onto the kept client and fills `client_user_id` on all of them in one transaction (`LinkClientUser`). Moving and linking stay in one event on purpose: as two events on separate topics they could arrive in either order and leave moved rows without the account. This event and `UserDeleted` have no relative order, so `LinkClientUser` reads `deleted_user` first under a shared lock and runs the erasure for the rows it just linked when the account is gone. The lock makes a link and a deletion wait for each other in either order (`DeletedUserLockMariaDbTest`). `markDeleted` is an `INSERT IGNORE`, never an upsert: an upsert takes an exclusive lock on an existing row, so two links for an already-deleted user, each holding the shared lock, deadlocked, and it overwrote the first deletion time. Both booking paths (`CreateAppointmentRequestImpl` for the caller, `CreateInstantAppointmentImpl` for the client row's account when it has one) read `deleted_user` the same way as their first statement and reject a deleted account with `Error.OperationNotAllowed`, so a booking can't store a person's details after their erasure ran; a new booking path must do the same. `client_user_id` is indexed on both tables: the erasure's `SELECT … FOR UPDATE` by it would otherwise scan, and at REPEATABLE READ lock, the whole table and block every business's bookings. Any new business write that gives a client row an account must publish `ClientLinked`, or the user's earlier appointments escape erasure. Deleting a client is the per-business counterpart: `DeleteClient` locks the client row first (`getClientForUpdate`), lets only the owner delete an integrated client (an employee with the `CLIENTS` delete grant gets `Error.OperationNotAllowed`, a 404), and publishes `BusinessEvent.ClientDeleted(businessId, clientId)`. Appointments then runs `DeleteClientAppointmentData`: `deleted_client` (`INSERT IGNORE`, keyed by client id) first, then cancel the upcoming appointments by `business_id` + `client_id` (the only locking read), anonymize every one (snapshot, note and `client_user_id` cleared, read as "Deleted Client"), delete the requests, and notify the employee (`CancelledForDeletedClient`, `cause = REMOVED_BY_BUSINESS`) and a client with an account (`AppointmentEvent.Cancelled`). `LinkClientUser` and both booking paths read `deleted_client` under a shared lock right after `deleted_user`, for the same ordering reason (`DeletedClientLockMariaDbTest`). A new booking path must check both tombstones.

- **An account unused for 3 years is deleted after three warnings.** `authentication.last_active_at` is written by `GenerateAuthToken` (every refresh and sign-in, at most once a day, `recordActivity` resets `dormancy_stage` to `ACTIVE`). The daily `auth-handleDormantAccounts` job (`HandleDormantAccounts`) warns 60, 30 and 7 days ahead with `AuthEvent.AccountDormancyWarning` (only the 7-day one is `final`; `dormancy_stage` is an Exposed `enumeration`, stored by ordinal, so inserting a stage renumbers every stage after it and existing rows take the new meaning) (notifications type `ACCOUNT`, never suppressed) and then erases through `AccountEraser`, the same code as `DeleteAccount`; it skips an owner while any other member of their business was active within 3 years (`BusinessClient.getOwnedBusinessMemberIds`), and locks the account first and leaves it alone if it changed since it was listed. `AccountDataSource.deleteAuthorization` takes the account id (`authentication.id`), never the user id: account deletion passed the user id until 0.17.0 and deleted nothing.

- **Data that served its purpose has a fixed lifetime.** Requests are deleted 60 days after their slot ended (`appointments-deleteExpiredRequests`), `deleted_user`/`deleted_client` tombstones 60 days after the deletion (`appointments-deleteExpiredTombstones`; twice the 30-day backup window, and longer than parked events live, so a late replay still finds them), parked events after 30 days. Account deletion deletes requests where the user is the client or the employee, and keeps the ones they only booked for someone else with `initiator_user_id` set to `Uuid.NIL`.

- **Every account and client erasure is recorded, so a backup restore can run it again.** `AccountEraser` writes `authorization.erased_account` (account deletion and dormant-account deletion), and `DeleteClient` and `DeleteInactiveClients` write `business.erased_client` (`ErasedClientDataSource.record`), each in the erasure's own transaction, so a record exists exactly when its erasure committed (`INSERT IGNORE`, the first time is kept). A restore to an earlier point undoes the erasures after it: the restore tool re-inserts every record from the latest backup with `reapply_requested` (`deployment/ansible/README.md`, Restoring prod), and the `auth-reapplyErasures` and `business-reapplyErasures` jobs (every minute, first run at start) erase them again, one transaction per record that claims it first (`claimReapply`, a conditional `UPDATE` that locks the row, so only one instance acts during a `start-first` deploy) and then erases, sending the usual `AuthEvent.UserDeleted` / `BusinessEvent.ClientDeleted`. A new path that erases an account must go through `AccountEraser`, and a new path that deletes a business's client must record it, or a restore brings that person back. Records live 60 days, twice the 30 days of backups (`*-deleteExpiredErasureRecords`). Clients deleted with their user's account aren't recorded on their own: the account's record re-runs that.

- **A client is kept only while they are active within the business's retention period.** The business is the controller of its clients' data and sets the period as a business setting, `business.client_data_retention_months` (12 to 120, default 36, `UpdateBusiness`). `client.last_activity_at` is set when a client row is created, edited or taken over, and moved forward (never back) to each booked visit's end by `RecordClientVisit`, fed by `AppointmentEvent.ClientVisitBooked`. A new appointments write that books or moves a slot must send that event in its transaction, or the business may delete a client with an upcoming appointment. The daily `business-deleteInactiveClients` job (`DeleteInactiveClients`, one `READ_COMMITTED` transaction per business, so it takes no gap locks that hold up new clients, `ClientRetentionMariaDbTest`) deletes the rows older than the cutoff and sends `BusinessEvent.ClientDeleted` for each, the same erasure as `DeleteClient`. Client deletion (`anonymizeClient`) and account deletion (`anonymizeClientUser`) erase the same appointment fields through one helper, `eraseClientDetails` in `AppointmentDataSourceImpl`: client name (placeholder), phone, email, `client_user_id` and the optional `note`; the cancellation reason and the price adjustment reason stay as the business's record (developer's decision). A new appointment column that holds client data goes into that helper. Every status guard (`requireEditable` / `requireCompletable` / `requireNoShowMarkable`) also refuses an appointment that ended more than `Appointment.EDIT_WINDOW` (7 days) ago with `AppointmentStatusError.EditWindowClosed` (`APPOINTMENT_EDIT_WINDOW_CLOSED`), and a new operation that changes an appointment calls one of them. Cancelled appointments are terminal and must be replaced with a new booking; unresolved appointments are locked. Scheduled, completed and no-show outcomes can be corrected within the edit window. An update that keeps the date and employee preserves the recorded status, attribution and checkout, even for an existing past date. Changing the date or employee reopens it as scheduled, clears the old checkout, requires a future date and rechecks booking availability.

- **A personal data breach follows `docs/legal/bookkme/breach-procedure.en.md` and is recorded in `docs/legal/bookkme/breach-log.en.md`** (both gitignored, like the record of processing). Its containment steps name real tables, secrets and commands (`authorization.auth_device` refresh-token columns, `signing_key` in `authorization` and `business`, the vault entries, `monolith-mariadb-users-init-v<n>`), so a change to sessions, signing keys, a secret, a backup or a table holding personal data updates the procedure's sections 5 and 6 in the same change (its section 10). Deleting every `signing_key` row and restarting is the only way to stop tokens signed by a compromised key; ordinary rotation keeps the old key verifying for 7 days.

- **Data subject requests follow `docs/legal/bookkme/subject-request-procedure.en.md` and are recorded in `docs/legal/bookkme/subject-request-log.en.md`** (both gitignored). There is no admin route: staff erase an account for someone who can't use the app by inserting an `authorization.erased_account` row with `reapply_requested = TRUE`, which `auth-reapplyErasures` runs through `AccountEraser` within a minute, never by deleting rows. Staff never edit profile or client rows by hand (it skips the `UserUpdated` sync, and from 0.18.0 the fields are encrypted). Requests about a business's records go to the business; BookkMe never acts on them alone (DPA 3.2). A restriction or legal hold is `deletion_hold` on `authorization.authentication` or `business.client`, set by staff with SQL: `getDormantAccounts` and `deleteInactiveClients` filter it out, and `HandleDormantAccounts` also skips a listed held account. Any new automatic deletion of an account or client must honour the same flag. A change to how an account is found by email, to the erasure records or reapply jobs, to what the personal export holds, or to the hold updates the procedure's sections 4.1, 5.1, 5.3, 5.4 and 6.2 in the same change.

- **The legal texts already promise crypto-shredding for 0.18.0, so its implementation is bound by them** (`docs/legal/README.md`). Per-person AES-GCM keys, wrapped by a master key outside the database (vault), live in `library/encryption` (`SubjectKeys`, `BlindIndex`, `ScopeDSL.subjectKeys(keySchema)`, called inside the service's `scope { }`), not in `core`. Each service holding personal data (user, business, appointments, notifications; authorization's tables and events hold none) has a short-retention schema, `<svc>_short_retention` (`<SVC>_SHORT_RETENTION_SCHEMA`), holding `subject_key` and nothing else. Every other table, `outbox_event`, `exhausted_event` and `data_export` included, stays in the service schema, which is binlogged and point-in-time recoverable (the outbox must be). So no table may hold plaintext personal data: every copy of it (event payload fields, export documents, parked events, snapshots) is encrypted under a key that dies when the data must die, never moved into the short-retention schema. The service's own migration creates the schema (`CREATE DATABASE IF NOT EXISTS`, then the qualified `CREATE TABLE`), so the app's database user needs `ALL PRIVILEGES` on `<svc>_short_retention`: prod grants it in `users-init.sql.j2` (`short_retention_schemas`, wrapped in a handler for error 1133 because the init file also runs before the entrypoint creates the app user), dev in `deployment/dev/db/init.sql`. Each service's data tests extend `ShortRetentionSchemaContract` (testFixtures of `library/encryption/impl`), which runs the real migrations on MariaDB and checks that the library encrypts, decrypts and shreds through the migrated table that the short-retention schema holds only `subject_key`, and that the outbox, parked-event and export tables stay in the service schema. The short-retention schema is separate because prod binlogs and the main dump cover every schema for 30 days, so the short-retention schemas are left out of both (`binlog_ignore_db`) and get their own dump every 5 minutes, kept 7 days; a restore replays the service schemas to the chosen point and takes the newest key dump. Keys are written in the service's own transaction (same server), so a rolled-back write leaves no key (`SubjectKeysMariaDbTest`). They encrypt account name, email and phone; client and employee details; the client and employee snapshots on appointments and requests; appointment and request notes; `Client.description`; notification email and Telegram targets. Lookups and uniqueness use HMAC blind indexes. Cancellation, decline and price-adjustment reasons stay plaintext. Erasure destroys the key in the erasure's own transaction: `SubjectKeys.shred` replaces the row with a tombstone (`wrapped_key` and `master_key_version` NULL, `shredded_at` set, the first shredding time kept), and writes one for a subject that never had a key, so a tombstone is never deleted. It also inserts the id into the service schema's `shredded_subject` (`INSERT IGNORE`, first time kept), which is binlogged unlike the key schema: a restore loads the newest 5-minute key dump and then tombstones every id in that ledger, so nobody erased after the key dump gets their key back (`deployment/AGENTS.md`, Backups). A service holding keys creates `shredded_subject` in its migration, like `subject_key`. `encryptor(subjectId)` returns `null` for a tombstoned subject instead of creating a fresh key, so a late write of an erased person's data is skipped rather than stored readable (a handler treats it as a no-op, not a failure that parks the event). A service's `subject_key` holds user, client and export ids side by side with no type column, which is only safe because every subject id is a random UUID the server generated: never key data under an id taken from a request or derived from another id (a client id equal to its user id would share, and with it shred, that user's key). `encryptor`, `shred` and `shredAll` refuse `Uuid.NIL` with an `IllegalArgumentException` (the test fakes too): NIL stands for an anonymized or unknown person, so a key under it would be shared by everyone written that way. A handler that would also create rows of its own for the person (default notification settings) checks `isShredded(subjectId)` first, which reads the tombstone without creating a key, and does nothing for an erased person (`UpdateTargetInformation`). `Decryptor.decrypt` returns `Decrypted.Plain`, `Decrypted.Shredded` (tombstone: the person was erased) or `Decrypted.Missing` (no row at all: a key lost in a restore, or a bug, never an erasure; callers log it as an error). Documents (exports) use the `ByteArray` overloads of `encrypt`/`decrypt`. `subject_key` is backed up separately and those backups are kept **at most 7 days**: the privacy policies, DPA 10.2 and Annex 2 promise that an erased person's encrypted fields can't be read from any backup after 7 days. A restore takes the newest key backup, and `subject_key` stays off NocoDB's allowlist. A change to the field list, the key wrapping or the 7 days updates those texts in all three languages, the record of processing section 5 and the breach procedure section 6 in the same change.
- **Every erasure shreds the keys of the people it erases, in its own transaction, in every service holding keys.** Each service finds the ids in its own tables, never from a follow-up event. **An erasing operation runs in three phases: select, delete, shred.** First it selects what it erases with locking reads (`get…ForUpdate`: `getClientIdsOfUserForUpdate`, `getBusinessIdsOwnedByForUpdate`, `getClientIdsForUpdate`, …), every one of them before the transaction's first plain read, since a locking read after it can fail with error 1020; then the plain reads (details and snapshots for notifications); then the writes, which return `Unit` and take the selected ids (`cancelAll(ids, reason)`, `detachBusinesses(ids)`, `deleteClients(ids)`); then outbox events and export discards; and `subjectKeys.shredAll(...)` last, over the ids the select phase returned. Read the ids before the delete, since a cascade leaves nothing to read afterwards, and never have a write return what it erased. Keep the queries few: one statement per table for a set of rows (`inList`, `batchInsert`), never one per id, but don't merge unrelated tables into one query just to save a round trip. Reference: `DeleteUserAppointmentDataImpl`. Account deletion shreds the user's id in user, business, appointments and notifications, plus the ids of the client rows erased with it (their own client rows, and every client of a business they owned). Business shreds a client's id on `DeleteClient`, `DeleteInactiveClients`, `ReapplyClientErasures` (even when the row is already gone: the restored key backup may predate the shred) and when a profile sync merges a client away; appointments on `ClientDeleted`, on `ClientLinked` for each `mergedClientIds` (after moving their rows to the kept client, which re-encrypts them under the kept client's key: `reassignClients`), on `BusinessEvent.Deleted` and when `appointments-fillBusinessOwners` drops a business. Notifications keys clients by account, so it shreds only on `UserDeleted`. `shredAll` ignores an empty collection, so callers pass what they erased without checking. A new erasure path shreds too, and its test asserts it with `ShredRecordingSubjectKeys` (testFixtures of `library/encryption/api`), whose `shreddedInTransaction` only counts shreds made inside the transaction.
- **An event holding personal data is encrypted wherever it is stored.** The event implements `PersonalEvent` (`core/data/eventstreaming/api`) and names the one person it is about in a getter-only `dataSubject` (never serialized): `DataSubject.User(userId)`, or `DataSubject.Client(clientId, userId)` for a business's client. Today that is `UserEvent.Updated`, `AppointmentEvent.RequestCreated` and `BusinessEvent.EmployeeInvitationRedeemed`; cancellation and decline reasons are not personal data, and an event carries no personal field its consumers don't use. An event with personal data about two people needs a design decision first (split it, or seal it in layers), never a second subject bolted on. The whole encoded payload is sealed, not single fields, so a field can't be forgotten and nothing has to know the event's type to open it: `OutboxEventProducer` seals it with the producing service's key before writing `outbox_event`, `OutboxRelay` opens it before publishing (events travel in memory, never stored readable), and a consumer that parks an event has it sealed again with its own key by its `ExhaustedEventDataSource` (`SealingExhaustedEventDataSource`), which opens it again in `lockReplayRequested`. All of them go through `PersonalDataCipher` (`storedPayload` / `readablePayload`), which lives in `library/outbox` with `OutboxEvent` and `OutboxEventDataSource`, never in core: core's consumers only see outcomes (`Parked.Stored` / `Parked.SubjectErased` from `save`, and a `ParkedPayload` that is `Readable`, `SubjectErased` or `Unreadable` on replay); `SubjectKeysPersonalDataCipher` stores a `SealedPayload(keyId, ciphertext)` envelope, so the key id is readable next to the ciphertext. Events without personal data are stored as plaintext with `personal_data_encrypted = false`, as are rows written before 0.18.0. When the subject's key is shredded the event is dropped (the erasure supersedes it); a producer refuses to send one (the transaction fails); a missing key drops it too and reports it through `MissingKeys.report(topic)` (an error log plus `personal_data_key_missing_total{source}`); a payload that fails to open (`UnreadableSealedPayload`) is dropped by the relay and refused on replay, while a database error while fetching a key propagates so nothing is lost. A service keys client data by client id (`ClientKey.CLIENT_ID`) except notifications, which keys it by the client's account (`LINKED_USER_ID`, falling back to the client id) because it only learns of account deletions. Each service binds its cipher by calling `personalDataCipher()` inside its `scope { }` (authorization: `noPersonalDataCipher()`, which refuses personal events), followed by `exhaustedEventDataSource()`, which wraps the plain `exhausted_event` rows (`ExhaustedEventRowDataSourceImpl`, internal) in that cipher. These library bindings are `ScopeDSL` extensions, never `Module`s taking the scope's qualifier: a module can't be included inside a `scope { }`, and a qualifier passed separately can name the wrong scope and compile.
- **A table column holding personal data is encrypted the way `user.profile` is** (`ProfileCipher`, `UserDataSourceImpl`, `UserEntity.store`). Each field gets a `VARBINARY` `<field>_encrypted` column holding `Encryptor.encrypt(ByteArray)` under the subject's key, sized for the plaintext column's maximum in UTF-8 plus 29 bytes; a field looked up or kept unique gets a `CHAR(44)` `<field>_index` with `BlindIndex.ofCaseInsensitive` (trimmed and lowercased) and the unique constraint. Encryption and indexing happen in the datasource, so the domain keeps plain values; the cipher class and the `MissingKeys` report come from the scope's `subjectKeys(...)`. Every write stores ciphertext only and sets that row's plaintext columns to NULL; reads decrypt, and fall back to the plaintext columns while a row's marker ciphertext is NULL (`email_encrypted`; a required field, so `name_encrypted` where the email is optional). Tables holding the same fields share one cipher: business clients and employees both use `ContactCipher`, keyed by `client.id` and by `employee.user_id`, with a batched `ContactReader` per list read. A write recomputes only the indexes of contacts it changes (all of them on a plaintext row), because a row whose key is missing decrypts to empty values and must keep its real index. Until the plaintext columns are gone, a new or changed contact is also checked against them (`requireNoPlaintextHolder`, throwing `Error.UniqueConstraintFailed`), since the new unique index can't see unencrypted rows, and lookups match the index or the plaintext column. A `<svc>-encryptPlaintext<Things>` job encrypts the old rows in batches of 100 (`FOR UPDATE`, one transaction each) until a batch comes back short; 0.19.0 drops the plaintext columns and the job. A `Decrypted.Missing` reads as empty fields and calls `MissingKeys.report("<table>")` once per row (the user chose that over a 404 or a 500, so the person can re-enter their data, which creates a fresh key); a `Decrypted.Shredded` reads the same without the report, and readers of another person's data (snapshots, clients) map it to a placeholder. A field only ever read by its owner's id gets no blind index (notification targets, `TargetCipher`), and one read as a whole value rather than shown (an address to send to) reads as absent when undecryptable, so an insert-if-missing checks that the row exists (`hasEmail`), never that its value reads as null. Appointments and requests share `SnapshotCipher`: the client snapshot and note under `client_id`, the employee name under `employee_user_id`, never under `Uuid.NIL` (an anonymized employee), one batched `SnapshotReader` per read. Their erasure sets the plaintext and the encrypted columns to NULL instead of writing a placeholder, and the reader shows that, like a shredded key, as "Deleted Client" or "Deleted User", so the backfill job never meets a placeholder it can't encrypt. A search over an encrypted field decrypts in memory (`getAllPaginated` with a query), and a write that moves rows to another subject re-encrypts them under the new subject's key before the old one is shredded. Tests use `InMemorySubjectKeys`, `UnkeyedBlindIndex` and `RecordingMissingKeys` (testFixtures of `library/encryption/api`).
