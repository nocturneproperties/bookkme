# bookk-server — Deployment Playbook

Dev and prod deployment, CI image publishing aside (that stays in the root `AGENTS.md`). Claude Code loads this file through `deployment/CLAUDE.md` whenever it reads a file under `deployment/`; every rule in the root `AGENTS.md` still applies.

## Prod topology

**Prod deployment is scripted with Ansible in `deployment/ansible/`** (see its README). Prod runs the monolith, not the five microservices, and has no Kafka: one `monolith` stack (`deployment/prod/monolith/monolith-compose.yml`) with the app, one MariaDB holding all five schemas and one Redis. The app carries the network aliases `authorization.service`, `user.service`, `business.service`, `appointments.service`, `notifications.service`, so nginx's per-service `/api/<svc>` routes reach it unchanged, and every `*_SERVICE_HOSTNAME` in its env (`monolith_env` in `inventory/group_vars/all/main.yml`) is `monolith.service`, because `TokenIssuerImpl` issues both auth tokens and quotes with the single `APPLICATION_SERVICE_HOSTNAME` and the validators expect it as the auth/business issuer. The database is bootstrapped by `db/init-schemas.sh`, mounted as a swarm config with mode `0444` so the MariaDB entrypoint *sources* it (an executable `.sh` is run instead, and `docker_process_sql` is then undefined); it creates the five schemas and grants the app user only those, root is limited to `localhost`.

## Database and cache networking

MariaDB and Valkey sit only on the encrypted `storage` overlay (the app, both exporters and NocoDB join it next to `operational`; nginx, the VPN and monitoring can't reach them), and MariaDB runs with `require_secure_transport = ON` (`db/my.cnf`; dev's `deployment/dev/db/my.cnf` sets it too, so a local SQL client on `127.0.0.1:3307` must enable SSL, while the throwaway migration database on 3308 stays plaintext). Every client other than the app (whose `createDatabase` connects with `sslMode=verify-full`, see the root `AGENTS.md`) must enable TLS itself: `database-exporter` runs with `--tls.insecure-skip-verify` (its Go driver can't do that verification), and each NocoDB source has SSL on.

MariaDB's sizing lives in its own `db/tuning.cnf` (swarm config `monolith-mariadb-tuning-v<n>`, mounted next to the encryption `my.cnf` in `/etc/mysql/conf.d/`, which the ubi9 image reads through `/etc/my.cnf.d/docker.cnf`), sized for the 2 vCPU / 8 GB / NVMe worker: a 2G buffer pool, 512M redo log, `innodb_io_capacity = 1000`, `innodb_flush_neighbors = 0`; and `wait_timeout = 600` (down from 8 hours, so a client connection that vanished without closing is dropped within 10 minutes instead of filling `max_connections`); everything else stays at the 11.8 defaults, and a change needs a new config name.

The `database` service runs with `endpoint_mode: dnsrr`: behind a swarm virtual IP, IPVS silently forgets a TCP connection after 900 s without traffic, so HikariCP's idle pool connections broke on the client side while MariaDB kept every one open, until `1040 Too many connections` took all five pools to zero (seen in prod on 0.15.8, with `Failed to validate connection … closed connection` warnings). With `dnsrr`, `monolith.database` doesn't resolve at all while the database has no running task, so a database restart (any change to its configs or secrets) used to crash an app that was starting at that moment.

## Restart policy

Swarm counts restarts in a sliding `window`, and once a task reaches `max_attempts` there it is never restarted again, even after the window has passed. A dead task container can't be revived by hand either: `docker restart` fails with `unable to get secret from secret store`, because the worker drops a task's secrets when it ends. `docker service update --force <stack>_<service>` starts a new task, but from the service's *current* spec. After a failed update, that is the rolled-back one (`failure_action: rollback`), and it can predate an infrastructure change made by the same deploy. On 0.16.0 the app failed its update, Swarm rolled it back to the 0.15.11 spec, which joins only `operational`, while the database had already moved to `storage`. That spec can never resolve `monolith.database`, so neither a forced update nor any restart policy brings it back. Check `docker service inspect <svc> --format '{{.UpdateStatus.State}}'` (`rollback_*`) and the spec's networks, then redeploy the intended version instead.

The `monolith` service therefore has its own `restart_policy` (10 s delay, 5 within 10 m) on top of `createDatabase`'s ~3-minute connect retry. During a database outage of any length that allows at most 3 restarts in 10 minutes, so Swarm never gives up. Only a crash right after startup (configuration, migration) stops after 5. If any of these change, keep `window` ÷ (retry budget + `delay` + JVM start, ≈ 3.3 min today) below `max_attempts`.

## Memory sizing and placement

The worker's memory limits are sized together with it: MariaDB 3G (a full 2G pool measured 2.17G), Valkey 768M with `--maxmemory 512mb --maxmemory-policy noeviction` (a full cache rejects writes with an error instead of OOM-killing the container or evicting idempotency and claim keys, and the headroom covers the AOF rewrite fork), the app 1536M with `JAVA_TOOL_OPTIONS: -XX:MaxRAMPercentage=70 -XX:+ExitOnOutOfMemoryError` (≈1.05G heap; without it the JVM takes 25% of the limit).

Valkey's size is set by how many writes it must remember, measured on `valkey:8.1`: a stored HTTP idempotency response costs its size plus ~200 B for 10 minutes, an event's processed marker ~147 B per consumer group for 1 hour (`CacheEventIdempotencyStorage.PROCESSED_TTL`): ~130 MB of responses at a 100 writes/s peak — what the 2 vCPU worker can serve — plus ~50 MB of markers at that rate (it was ~250 MB/day while markers lived 24 hours). A full Valkey under `noeviction` fails every idempotent request and every event delivery, so raise `--maxmemory` (and the limit with it) before it fills. The limits add up to slightly more than 8G only during a deploy, when the app runs `start-first` and two copies briefly overlap; actual use stays well under them.

MariaDB and Valkey keep their data on node-local volumes, so both are pinned to the node labelled `database=true` (set from the inventory's `swarm_labels`, like Kafka's `kafka=true`); only the app container may float between workers.

## Monitoring

Prometheus requires basic auth (user `admin`) on every endpoint, its own `/metrics` included: the external swarm secrets `prometheus_web_config` (its `--web.config.file`, a bcrypt hash) and `prometheus_password` (the plain password, used by the self-scrape's `password_file` and Grafana's datasource via `$__file{/run/secrets/prometheus_password}`) are generated as a pair by `import-secrets.py`, which derives a missing hash from the stored password so they never diverge; a new scrape job against Prometheus itself, or a new Grafana datasource for it, must send the same credentials.

A scrape job for a swarm service uses `dns_sd_configs` on `tasks.<service>` (`tasks.<stack>_<service>` from another stack, e.g. `tasks.monolith_monolith`), never the service name or an alias, which is a virtual IP that sends each scrape to a random task; node-level alerts label nodes by `nodename` (node-exporter runs with `hostname: "{{.Node.Hostname}}"`, the recording rules join `node_uname_info`) because `instance` is a task IP.

Prometheus, Grafana and Loki keep their data on node-local volumes and are pinned to the node labelled `monitoring=true` (`manager-1`'s `swarm_labels`). Logs reach Grafana through Alloy (global, Docker socket) → Loki, labelled `stack`/`service`/`node`; dashboards filter levels on `detected_level`, which the monolith's logback level feeds as structured metadata (`alloy/config.alloy`). The provisioned dashboards (`grafana/dashboards/*.json`) refer to the data sources by their fixed uids `prometheus` and `loki`. cAdvisor keeps reporting a stopped container's last values for a couple of minutes, so a query that counts or sums containers must keep only live ones (`and on (id) (container_last_seen > time() - 30)`), or every deploy double-counts the service. A Loki instant metric query reaches a bar gauge as one unnamed frame: use a range query and a `reduce` transformation (`seriesToRows`, `sum`), which also puts every bar on one scale. Group node panels by `nodename`, not `instance`: a restarted node-exporter task gets a new IP, and an `instance`-grouped panel then shows the node twice.

MariaDB and Valkey are scraped through `database-exporter` and `redis-exporter` in the monolith stack; the MariaDB `exporter` user (`PROCESS` only) and NocoDB's `nocodb_reader` (`SELECT` on an allowlist of tables, `nocodb_readable_tables` in the template: nothing in `authorization`, no event payloads, signing keys, invitations or tombstones; a table that doesn't exist when the database starts is skipped and readable only after its next restart, because a failed `GRANT` silently ends the init file; see Monitoring in `ansible/README.md`) and `nocodb_writer` (`SELECT, INSERT` on `nocodb_insertable_tables`, today only `user.legal_document_version`, never `UPDATE`/`DELETE`) are created by `--init-file` from the swarm secret `monolith-mariadb-users-init-v<n>` (`roles/monolith/templates/users-init.sql.j2`), rendered by the monolith role from the vault, because `init-schemas.sh` runs only on an empty volume and root logs in only from inside the container: adding or renaming that secret restarts the database. cAdvisor must be v0.54.0 or newer (`ghcr.io/google/cadvisor`; `gcr.io/cadvisor` stops publishing at v0.55.1): the nodes' Docker 29 uses the containerd image store (`docker info` → `io.containerd.snapshotter.v1`), and older cAdvisor looks for the layer `mount-id` under `/var/lib/docker/image/overlayfs/layerdb`, fails for every container (`failed to identify the read-write layer ID`), and exports only label-less cgroup series, which emptied every panel and alert keyed on `container_label_com_docker_swarm_service_name` while node panels kept working. Newer cAdvisor also needs containerd's socket, which it gets through the `/var/run` mount (`/var/run` is `/run` on Ubuntu). cAdvisor has no `container_restarts_total` (the old `ContainerRestarting` alert could never fire); a crash is a container of a service that started in the last 15 minutes and is no longer seen (`service:containers_stopped_after_start:15m`). Loki deletes only by age; its stored size is `loki_ingester_chunk_size_bytes_sum` (compressed chunk bytes written, equal to the chunk files on disk), which `LogStorageGrowing` projects over the 14-day retention.

## Backups

The `backup` stack (`deployment/prod/backup`, runbook under Backups in `ansible/README.md`) gives 30 days of point-in-time recovery: its `binlog` service streams the binary log into a tmpfs and stores each file encrypted after a `FLUSH BINARY LOGS` every 5 minutes, and its `dump` service takes one nightly `mariadb-dump --single-transaction --master-data=2` of all five schemas. Both run one `backup.sh` from the pinned `mariadb:11.8.3-ubi9` image, on the manager (label `backup=true`), never on the database's node. Every file is zstd then GnuPG to the public key `prod/backup/backup-public-key.asc`. The private key stays out of the vault: the vault is committed to a public repository and CI holds its password (`ANSIBLE_VAULT_PASSWORD`), and keeping the key off servers and CI is what makes a stolen backup unreadable.

- `log_bin = binlog` is named on purpose: without a name MariaDB derives the binlog name from the hostname, which under Swarm is the container id, so every new database task would start a new series and the stored chain would break.
- `FLUSH BINARY LOGS` needs `RELOAD`; `BINLOG ADMIN` is refused (verified on 11.8.3). `mariadb-dump --master-data=2 --single-transaction` needs nothing beyond `SELECT` (no `FLUSH TABLES WITH READ LOCK` on MariaDB), and streaming needs `REPLICATION SLAVE` plus `BINLOG MONITOR` for `SHOW BINARY LOGS`/`SHOW MASTER STATUS`. The client tools verify the server's self-signed certificate through zero-configuration TLS like the app does, so the `backup` user must keep a password.
- A stored file is never overwritten (`publish`): a database restored onto a new volume numbers its binlogs from `binlog.000001` again, so the restore runbook moves the old backup directory aside before backing up again.
- `set -e` is ignored inside an `if`/`&&`/`||` condition, subshells included, so `dump` runs each dump as a separate process (`bash "$0" dump-once`) and checks its exit status. A pipeline's last stage succeeds even when `mariadb-dump` fails, so the output is written as `.partial` and renamed only after the pipeline and the `Dump completed` and position checks pass.
- The dump service's metrics are derived from the files on disk (the dump files' modification times, `du` per directory), not remembered by the process, so a restarted service reports the same values. It refreshes them every `BINLOG_ROTATE_SECONDS`, since nothing on disk changes faster, and right after a dump. The loop itself wakes every minute only to check whether the nightly dump is due. A change to `backup.sh` needs a new `backup-script-v<n>` name, like any swarm config.
- `ansible/scripts/backup-restore.sh` runs on the operator's Mac, so it stays compatible with macOS's bash 3.2 (no `mapfile`, no associative arrays). It decrypts with the operator's local `gpg` and decompresses and replays inside throwaway containers with tmpfs, so decrypted data never lands on a disk.
- Testing locally: Docker Desktop reports a bind-mounted file as executable even at `0444`, so the MariaDB entrypoint runs `init-schemas.sh` instead of sourcing it and fails with `Permission denied`. A local prod-like database therefore creates the schemas with an equivalent `.sql` file. Flyway 11.10's bundled MariaDB driver ignores `sslMode`, so against `require_secure_transport` use `useSsl=true&trustServerCertificate=true`. `gpg` in a container can't create its agent socket in a GNUPGHOME bind-mounted from macOS, so copy the keyring into the container first. The whole chain was verified that way: a restore to the latest point and one with `--until` both matched the source's `CHECKSUM TABLE` on all 52 tables, across a binlog service killed mid-stream.

## Compose files and stacks

The swarm compose schema rejects unquoted booleans in `environment` (`GF_SMTP_ENABLED: "true"`), so validate a changed stack with `docker stack config -c <file>` before deploying. YAML `<<:` merges one level deep, so a service that merges the `*replicated` template and declares its own `deploy:` loses the whole template `deploy:` block: merge `<<: *replicated-deploy` inside it (Prometheus had run without the restart and rollback policy that way).

The compose files under `deployment/prod` and `deployment/adminpanel` remain the source of truth: the `stack` role copies a stack's directory to `/opt/bookk/stacks/<stack>/` on the manager and runs `docker stack deploy` there (removing files gone from the repo first, and the vault-rendered secret files again right after the deploy, since Docker only reads them then; the `docker_stack` task runs under `no_log`, its result holds every service's env), with variables from the encrypted `inventory/group_vars/all/vault.yml` (`make vault-import` builds it and generates every key and password; `make vault-update` adds what a newer structure needs without replacing set values). A new infra stack needs an entry in `infra_stacks` and a tagged task in `playbooks/site.yml`.

The role refuses to create a stack that doesn't exist yet unless `-e allow_new_stacks=true` (`make bootstrap`, `make deploy v=… first=1`).

## VPN and nginx

The wg-easy panel (pinned to v14 by digest, configured by env vars; v15 is a different, setup-wizard config) is reachable only through nginx's `vpn.` host from the VPN subnet, its port 51821 unpublished, so the first client configs come from the `vpn_clients` role (tag `vpn`): it calls the panel's own API inside the container with `vault_vpn_password` (the plain password behind `VPN_PASSWORD_HASH`) via `docker exec … node --eval`, creates the missing `vpn_clients` and saves their configs to the gitignored `deployment/ansible/vpn-clients/`. wg-easy v14's image points `iptables` at the legacy backend, whose `nat` table an nf_tables host (Ubuntu 26.04) never loads and the container can't load, so its default hooks fail and the container crash-loops: `vpn-compose.yml` sets `WG_POST_UP`/`WG_POST_DOWN` to the same rules via the image's `iptables-nft` instead (verified in a throwaway container on the manager). dnsmasq publishes 53/udp in `mode: host`, and `docker_host` disables systemd-resolved's stub listener on managers: with the stub holding `127.0.0.53:53`, Docker silently publishes nothing for port 53 (no `docker-proxy`, no NAT rule), and every VPN client loses DNS and with it the internet. WireGuard's endpoint is the manager's public IP (`WG_HOST` = `VPN_ENDPOINT` from `vault_hosts`), never a hostname: Cloudflare proxies `vpn.<domain>` and carries no UDP, and a DNS-only record would publish the IP.

Every swarm node joins the VPN on `wg0` (`vpn_host` role) as its inventory `vpn_client`, pinned to its `vpn_address` through the API (manager `admin-1` on `vpn_host_address`, worker `worker-1` on `.4`; workers read their configs from the manager's `vpn_clients` run): dnsmasq resolves the domain to that address and wg-easy hands it out as DNS, so VPN traffic reaches nginx via the manager's `wg0` with its VPN source address intact, which is what makes nginx's subnet filter work. nginx therefore keeps 443 in `mode: host` (ingress mode would allow `start-first`, but the routing mesh rewrites the source address and every VPN-only host would deny the VPN), and avoids restarts instead: its templates, `snippets/` and `static/` are read-only directory bind mounts from the stack directory, not swarm configs (a single-file bind mount keeps the old inode after Ansible renames a new file over it), and `roles/nginx` re-renders the templates, runs `nginx -t` and reloads inside the running container when the files changed but the service spec didn't, restoring the previous `conf.d` if the test fails.

Cloudflare's `set_real_ip_from` ranges (`snippets/cloudflare-real-ip.conf`, regenerated by `scripts/cloudflare-real-ip.sh`, checked against Cloudflare's live lists on every `tags=nginx` run) are included only in the public `${DOMAIN_NAME}` server block, never at http level, so a VPN-only block's `allow` always checks the real TCP peer, never a header.

The subnet (`172.16.91.0/24`, outside Docker's bridge and overlay pools) is set only as `vpn_network_prefix` in `inventory/group_vars/all/main.yml` and reaches wg-easy, dnsmasq and nginx as `VPN_SUBNET`/`VPN_ADDRESS_TEMPLATE`/`VPN_HOST_ADDRESS` (`vpn_stack_env`), never hard-coded. wg-easy keeps the server address from its first start in `wg0.json` and ignores `WG_DEFAULT_ADDRESS` afterwards, so `ensure-clients.js` renumbers an install whose stored prefix differs (backup → rewrite every address, keeping host numbers and keys → restore → `wg-quick down/up` in the container).

## Images

`bitnami/*` images can no longer be pulled from Docker Hub: the cache everywhere (dev, prod, `RedisCacheClientTest`) is Valkey (`valkey/valkey:8.1.11-alpine`, configured on the command line: `--requirepass`, `--appendonly yes`, `FLUSHDB`/`FLUSHALL`/`CONFIG` renamed away) and prod uses the official `mariadb` image.

`deployment/prod/kafka/kafka-compose.yml` (not deployed today) mirrors dev's Kafka (`apache/kafka-native:4.2.1`, the same `KAFKA_*` settings and fixed ports 9092/9093) as a single broker like dev, reachable as `kafka:9092` on the `operational` network and pinned to the node labelled `kafka=true` (the `swarm` role applies a host's inventory `swarm_labels` with `docker_node`; values must be quoted strings, an unquoted `true` reaches Docker as `True` and never matches), because its data lives on a node-local volume. Its volumes are mounted at `/home/appuser` with `KAFKA_LOG_DIRS=/home/appuser/kafka-data` instead of dev's `/var/lib/kafka/data`: that path doesn't exist in the image, so a fresh volume there is root-owned and the broker (uid 1000) can't write to it. Dev fixes that with a `chown` init container, which Swarm can't order (it ignores `depends_on`); a volume mounted on the image's own `appuser`-owned home directory inherits that ownership instead.

## Dev environment

Dev deployment artifacts mirror the per-service ones: `deployment/dev/service/monolith.env` (one env file, all internal `*_SERVICE_HOSTNAME` vars pointed at `monolith.service` itself since every route lives in one process, no Kafka vars since it's embedded), `deployment/dev/monolith-compose.yml` (one `monolith` service, both the app port and the jdwp debug port published to the host), and `deployment/dev/rollout-monolith.sh` (same shape as `rollout.sh`, but builds the root project's image directly instead of looping per service).

Dev nginx routes differently per mode: `environment-compose.yml` mounts `${NGINX_CONF:-nginx.conf}`, `rollout.sh` sets `nginx.conf` (one upstream per `<svc>.service`) and `rollout-monolith.sh` sets `nginx-monolith.conf` (all of `/api/` and the JWKS to `monolith.service`, which has no per-service aliases in dev). Bringing the environment up by hand for the monolith needs `NGINX_CONF=nginx-monolith.conf`, or nginx keeps proxying to stale or unresolvable microservice hosts. Kafka (`kafka`, `kafka-ui`, `kafka-volume-init`) sits behind the compose profile `kafka`, which only `rollout.sh` enables (`--profile kafka`), since the monolith's events never leave the process: `rollout-monolith.sh` starts the environment without it and removes any Kafka containers left from a microservices rollout (the `kafka_volume` stays), so bringing the microservices up by hand needs `--profile kafka`.

Jib builds `linux/amd64` unless told otherwise, so on an Apple Silicon machine a plain `publishImageToLocalRegistry` gives an image that runs under emulation. Both rollout scripts first switch to the `default` Docker context, then build with `-Djib.from.platforms=linux/<arch>`, where `<arch>` is the local daemon's `docker version --format '{{.Server.Arch}}'`. The context switch comes first because `jibDockerBuild`, `docker compose` and the arch lookup all use the current context: left on `swarm-manager`, they would build for the prod manager and load the image there. The CI publish workflows pass no flag and keep building amd64 for prod.
