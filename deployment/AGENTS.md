# bookk-server — Deployment Playbook

Dev and prod deployment, CI image publishing aside (that is in `docs/agents/build-and-ci.md`). Claude Code loads this file through `deployment/CLAUDE.md` whenever it reads a file under `deployment/`; every rule in the root `AGENTS.md` still applies.

## Prod topology

**Prod deployment is scripted with Ansible in `deployment/ansible/`** (see its README). Prod runs the monolith, not the five microservices, and has no Kafka: one `monolith` stack (`deployment/prod/monolith/monolith-compose.yml`) with the app, one MariaDB holding all five schemas and one Redis. The app carries the network aliases `authorization.service`, `user.service`, `business.service`, `appointments.service`, `notifications.service`, so nginx's per-service `/api/<svc>` routes reach it unchanged, and every `*_SERVICE_HOSTNAME` in its env (`monolith_env` in `inventory/group_vars/all/main.yml`) is `monolith.service`, because `TokenIssuerImpl` issues both auth tokens and quotes with the single `APPLICATION_SERVICE_HOSTNAME` and the validators expect it as the auth/business issuer. The database is bootstrapped by `db/init-schemas.sh`, mounted as a swarm config with mode `0444` so the MariaDB entrypoint *sources* it (an executable `.sh` is run instead, and `docker_process_sql` is then undefined); it creates the five schemas and grants the app user only those, root is limited to `localhost`. The app user's `ALL PRIVILEGES` on the four short-retention schemas (`<svc>_short_retention`: only the per-person keys, created by the services' own migrations, `docs/agents/personal-data.md`) come from the users-init file instead (`short_retention_schemas`), so they also reach a database whose volume already exists; the database must have restarted with them before a version whose migrations create those schemas starts.

## Database and cache networking

MariaDB and Valkey sit only on the encrypted `storage` overlay (the app, both exporters and NocoDB join it next to `operational`; nginx, the VPN and monitoring can't reach them), and MariaDB runs with `require_secure_transport = ON` (`db/my.cnf`; dev's `deployment/dev/db/my.cnf` sets it too, so a local SQL client on `127.0.0.1:3307` must enable SSL, while the throwaway migration database on 3308 stays plaintext). Every client other than the app (whose `createDatabase` connects with `sslMode=verify-full`, see `docs/agents/infrastructure.md`) must enable TLS itself: `database-exporter` runs with `--tls.insecure-skip-verify` (its Go driver can't do that verification), and each NocoDB source has SSL on.

MariaDB's sizing lives in its own `db/tuning.cnf` (swarm config `monolith-mariadb-tuning-v<n>`, mounted next to the encryption `my.cnf` in `/etc/mysql/conf.d/`, which the ubi9 image reads through `/etc/my.cnf.d/docker.cnf`), sized for the 2 vCPU / 8 GB / NVMe worker: a 2G buffer pool, 512M redo log, `innodb_io_capacity = 1000`, `innodb_flush_neighbors = 0`; and `wait_timeout = 600` (down from 8 hours, so a client connection that vanished without closing is dropped within 10 minutes instead of filling `max_connections`); everything else stays at the 11.8 defaults, and a change needs a new config name.

The `database` service runs with `endpoint_mode: dnsrr`: behind a swarm virtual IP, IPVS silently forgets a TCP connection after 900 s without traffic, so HikariCP's idle pool connections broke on the client side while MariaDB kept every one open, until `1040 Too many connections` took all five pools to zero (seen in prod on 0.15.8, with `Failed to validate connection … closed connection` warnings). With `dnsrr`, `monolith.database` doesn't resolve at all while the database has no running task, so a database restart (any change to its configs or secrets) used to crash an app that was starting at that moment.

## Restart policy

Swarm counts restarts in a sliding `window`, and once a task reaches `max_attempts` there it is never restarted again, even after the window has passed. A dead task container can't be revived by hand either: `docker restart` fails with `unable to get secret from secret store`, because the worker drops a task's secrets when it ends. `docker service update --force <stack>_<service>` starts a new task, but from the service's *current* spec. After a failed update, that is the rolled-back one (`failure_action: rollback`), and it can predate an infrastructure change made by the same deploy. On 0.16.0 the app failed its update, Swarm rolled it back to the 0.15.11 spec, which joins only `operational`, while the database had already moved to `storage`. That spec can never resolve `monolith.database`, so neither a forced update nor any restart policy brings it back. Check `docker service inspect <svc> --format '{{.UpdateStatus.State}}'` (`rollback_*`) and the spec's networks, then redeploy the intended version instead.

The `monolith` service therefore has its own `restart_policy` (10 s delay, 5 within 10 m) on top of `createDatabase`'s ~3-minute connect retry. During a database outage of any length that allows at most 3 restarts in 10 minutes, so Swarm never gives up. Only a crash right after startup (configuration, migration) stops after 5. If any of these change, keep `window` ÷ (retry budget + `delay` + JVM start, ≈ 3.3 min today) below `max_attempts`.

A command that targets one service's container finds it with `docker ps -qf label=com.docker.swarm.service.name=<stack>_<service>`, never `name=<stack>_<service>`: the name filter matches substrings, so `name=monolith_database` also returns `monolith_database-exporter` (and `monolith_redis` returns `redis-exporter`), and `docker exec $(…)` then runs the second id as the command (`exec: "<id>": executable file not found`).

## Memory sizing and placement

The worker's memory limits are sized together with it: MariaDB 3G (a full 2G pool measured 2.17G), Valkey 768M with `--maxmemory 512mb --maxmemory-policy noeviction` (a full cache rejects writes with an error instead of OOM-killing the container or evicting idempotency and claim keys, and the headroom covers the AOF rewrite fork), the app 1536M with `JAVA_TOOL_OPTIONS: -XX:MaxRAMPercentage=70 -XX:+ExitOnOutOfMemoryError` (≈1.05G heap; without it the JVM takes 25% of the limit).

Valkey's size is set by how many writes it must remember, measured on `valkey:8.1`: a stored HTTP idempotency response costs its size plus ~200 B for 10 minutes, an event's processed marker ~147 B per consumer group for 1 hour (`CacheEventIdempotencyStorage.PROCESSED_TTL`): ~130 MB of responses at a 100 writes/s peak — what the 2 vCPU worker can serve — plus ~50 MB of markers at that rate (it was ~250 MB/day while markers lived 24 hours). A full Valkey under `noeviction` fails every idempotent request and every event delivery, so raise `--maxmemory` (and the limit with it) before it fills. The limits add up to slightly more than 8G only during a deploy, when the app runs `start-first` and two copies briefly overlap; actual use stays well under them.

MariaDB and Valkey keep their data on node-local volumes, so both are pinned to the node labelled `database=true` (set from the inventory's `swarm_labels`, like Kafka's `kafka=true`); only the app container may float between workers. NocoDB keeps its setup in a SQLite file on the node-local `admin_panel` volume, so it is pinned to `admin=true` (`manager-1`, where it ran when pinned) and updates `stop-first`, so two copies never write that file at once.

NocoDB's switches are obfuscated in its bundle, so a new one is found by loading a `process.env` proxy that logs every name read (`NODE_OPTIONS=--require=<file>`, copied in with `docker cp` before `docker start`; the proxy needs a `set` trap that assigns on the target, or Node rejects the write) and confirmed in `/api/v2/meta/nocodb/info` (`teleEnabled`, `errorReportingEnabled`, `disableOnboardingFlow`, …). Recheck the names when bumping its image.

## Monitoring

Prometheus requires basic auth (user `admin`) on every endpoint, its own `/metrics` included: the external swarm secrets `prometheus_web_config` (its `--web.config.file`, a bcrypt hash) and `prometheus_password` (the plain password, used by the self-scrape's `password_file` and Grafana's datasource via `$__file{/run/secrets/prometheus_password}`) are generated as a pair by `import-secrets.py`, which derives a missing hash from the stored password so they never diverge; a new scrape job against Prometheus itself, or a new Grafana datasource for it, must send the same credentials.

A scrape job for a swarm service uses `dns_sd_configs` on `tasks.<service>` (`tasks.<stack>_<service>` from another stack, e.g. `tasks.monolith_monolith`), never the service name or an alias, which is a virtual IP that sends each scrape to a random task; node-level alerts label nodes by `nodename` (node-exporter runs with `hostname: "{{.Node.Hostname}}"`, the recording rules join `node_uname_info`) because `instance` is a task IP.

Prometheus, Grafana and Loki keep their data on node-local volumes and are pinned to the node labelled `monitoring=true` (`manager-1`'s `swarm_labels`). Logs reach Grafana through Alloy (global, Docker socket) → Loki, labelled `stack`/`service`/`node`; dashboards filter levels on `detected_level`, which the monolith's logback level feeds as structured metadata (`alloy/config.alloy`). The provisioned dashboards (`grafana/dashboards/*.json`) refer to the data sources by their fixed uids `prometheus` and `loki`. cAdvisor keeps reporting a stopped container's last values for a couple of minutes, so a query that counts or sums containers must keep only live ones (`and on (id) (container_last_seen > time() - 30)`), or every deploy double-counts the service. A Loki instant metric query reaches a bar gauge as one unnamed frame: use a range query and a `reduce` transformation (`seriesToRows`, `sum`), which also puts every bar on one scale. Group node panels by `nodename`, not `instance`: a restarted node-exporter task gets a new IP, and an `instance`-grouped panel then shows the node twice.

MariaDB and Valkey are scraped through `database-exporter` and `redis-exporter` in the monolith stack; the MariaDB `exporter` user (`PROCESS` only) and NocoDB's `nocodb_reader` (`SELECT` on an allowlist of tables, `nocodb_readable_tables` in the template: nothing in `authorization`, no event payloads, signing keys, invitations, tombstones or erasure records; a table that doesn't exist when the database starts is skipped and readable only after its next restart, because a failed `GRANT` silently ends the init file; see Monitoring in `ansible/README.md`) and `nocodb_writer` (`SELECT, INSERT` on `nocodb_insertable_tables`, today only `user.legal_document_version`, never `UPDATE`/`DELETE`) are created by `--init-file` from the swarm secret `monolith-mariadb-users-init-v<n>` (`roles/monolith/templates/users-init.sql.j2`), rendered by the monolith role from the vault, because `init-schemas.sh` runs only on an empty volume and root logs in only from inside the container: adding or renaming that secret restarts the database. cAdvisor must be v0.54.0 or newer (`ghcr.io/google/cadvisor`; `gcr.io/cadvisor` stops publishing at v0.55.1): the nodes' Docker 29 uses the containerd image store (`docker info` → `io.containerd.snapshotter.v1`), and older cAdvisor looks for the layer `mount-id` under `/var/lib/docker/image/overlayfs/layerdb`, fails for every container (`failed to identify the read-write layer ID`), and exports only label-less cgroup series, which emptied every panel and alert keyed on `container_label_com_docker_swarm_service_name` while node panels kept working. Newer cAdvisor also needs containerd's socket, which it gets through the `/var/run` mount (`/var/run` is `/run` on Ubuntu). cAdvisor has no `container_restarts_total` (the old `ContainerRestarting` alert could never fire); a crash is a container of a service that started in the last 15 minutes and is no longer seen (`service:containers_stopped_after_start:15m`). Security alerts (`prometheus/security_alerts.yml`, `loki/security_rules.yml`, thresholds and reasons in `ansible/README.md` under Monitoring, Security alerts) are verified with `promtool test rules` (`prometheus/tests/`); assert on `ALERTS{alertname=…}` in `promql_expr_test`, since `alert_rule_test` also compares every annotation, and space the input samples closer than the shortest range in the rule: Prometheus 3 ranges exclude their start, so hourly samples leave `increase(x[1h])` empty and a firing test passes as quiet. `mysql_global_status_access_denied_errors` also counts statements refused for missing privileges (verified with mysqld-exporter v0.20.0 on 11.8.3), so failed logins are `aborted_connects`; Valkey's are `redis_errors_total{err="WRONGPASS"|"NOAUTH"}` (redis_exporter v1.93.0, stable across scrapes). Loki's ruler (tenant `fake`, rules in `/etc/loki/rules/fake/`) sends log alerts to the same Alertmanager. nginx logs only the VPN hosts' logins and refusals (`log_format admin_auth`, `if=$admin_auth`, classified by `map`s on host, method, path, status and whether an `Authorization` header was sent, so Prometheus's basic-auth challenge on every first visit and an expired panel session's 401s are not failed logins (verified in `nginx:1.29.4`); NocoDB answers a wrong password with 400, the others with 401, verified against the pinned images), never every request. Alloy reads `ssh.service` from the host journal (`/var/log/journal` and `/etc/machine-id` mounted; Ubuntu 26.04 logs `Accepted publickey for <user> from <ip>` from `sshd-session` under that unit), so a node must keep its journal on disk (`docker_host` role) or the bind mount stops Alloy from starting. The whole chain, nginx through Alertmanager and an SSH login on an Ubuntu 26.04 systemd container, was verified locally with the pinned images. Loki deletes only by age; its stored size is `loki_ingester_chunk_size_bytes_sum` (compressed chunk bytes written, equal to the chunk files on disk), which `LogStorageGrowing` projects over the 14-day retention.

The website's metrics come from nginx's log, not from the site, which exports none: the site's server block logs `site_access` JSON lines (`"log":"site"`, no query string, no user agent, the referrer's host only, an empty referrer for the site's own pages and `www.`), and a `stage.match` in `alloy/config.alloy` turns them into `site_requests_total`, `site_response_bytes_total` and `site_request_duration_seconds`, which Prometheus scrapes from `tasks.alloy:12345` (job `alloy`, `metric_relabel_configs` keep only `site_.+`). Only the manager's Alloy has them, since nginx runs there. Alloy's HTTP server listens on `127.0.0.1:12345` unless `--server.http.listen-addr` says otherwise. `stage.metrics` labels a metric with the entry's labels, so `stage.labels` sets `status_class`/`kind`/`client` before it and `stage.label_drop` removes them after it, keeping Loki's nginx stream labels unchanged. Its `max_idle_duration` (default 5m) deletes a series that saw no line for that long, and the next line starts it again at 1, which `increase` never counts, so the site's metrics keep 720h. A `stage.match` selector takes no backtick string (`syntax error: unexpected IDENTIFIER, expecting STRING` on v1.20.1), so its line filter is a double-quoted LogQL string with escaped quotes. Page, referrer, country and 404 rankings query the lines in Loki instead (unbounded labels), and the metrics carry no personal data, as the privacy texts state. A server block without its own `access_log` inherits the image's `main` format (client address, user agent, full request line): the public API block logs every request that way. Verified locally with the pinned nginx, Alloy, Loki, Prometheus and Grafana: the dashboard's Prometheus and Loki queries returned the test traffic, and a stopped site showed as `5xx`. cAdvisor on Docker Desktop exports no Docker labels, so the container panels could only be checked in prod.

## Backups

The `backup` stack (`deployment/prod/backup`, runbook under Backups in `ansible/README.md`) gives 30 days of point-in-time recovery: its `binlog` service streams the binary log into a tmpfs and stores each file encrypted after a `FLUSH BINARY LOGS` every 5 minutes, and its `dump` service takes one nightly `mariadb-dump --single-transaction --master-data=2` of all five schemas. Both run one `backup.sh` from the pinned `mariadb:11.8.3-ubi9` image, on the manager (label `backup=true`), never on the database's node. Every file is zstd then GnuPG to the public key `prod/backup/backup-public-key.asc`. The private key stays out of the vault: older encrypted copies of the vault stay in the public repository's history, and keeping the key off servers and CI is what makes a stolen backup unreadable.

- `log_bin = binlog` is named on purpose: without a name MariaDB derives the binlog name from the hostname, which under Swarm is the container id, so every new database task would start a new series and the stored chain would break.
- `FLUSH BINARY LOGS` needs `RELOAD`; `BINLOG ADMIN` is refused (verified on 11.8.3). `mariadb-dump --master-data=2 --single-transaction` needs nothing beyond `SELECT` (no `FLUSH TABLES WITH READ LOCK` on MariaDB), and streaming needs `REPLICATION SLAVE` plus `BINLOG MONITOR` for `SHOW BINARY LOGS`/`SHOW MASTER STATUS`. The client tools verify the server's self-signed certificate through zero-configuration TLS like the app does, so the `backup` user must keep a password.
- A stored file is never overwritten (`publish`): a database restored onto a new volume numbers its binlogs from `binlog.000001` again, so the restore runbook moves the old backup directory aside before backing up again.
- `set -e` is ignored inside an `if`/`&&`/`||` condition, subshells included, so `dump` runs each dump as a separate process (`bash "$0" dump-once`) and checks its exit status. A pipeline's last stage succeeds even when `mariadb-dump` fails, so the output is written as `.partial` and renamed only after the pipeline and the `Dump completed` and position checks pass.
- The dump service's metrics are derived from the files on disk (the dump files' modification times, `du` per directory), not remembered by the process, so a restarted service reports the same values. It refreshes them every `BINLOG_ROTATE_SECONDS`, since nothing on disk changes faster, and right after a dump. The loop itself wakes every minute only to check whether the nightly dump is due. A change to `backup.sh` needs a new `backup-script-v<n>` name, like any swarm config.
- `ansible/scripts/backup-restore.sh` runs on the operator's Mac, so it stays compatible with macOS's bash 3.2 (no `mapfile`, no associative arrays). It decrypts with the operator's local `gpg` and decompresses and replays inside throwaway containers with tmpfs, so decrypted data never lands on a disk. That includes the restored database itself: the `mariadb` image declares `VOLUME /var/lib/mysql`, so without a mount there every drill and rehearsal wrote prod's data to an anonymous volume on Docker's VM disk, which only the exit trap's `docker rm -v` removed, and a killed script left behind. Both containers mount a tmpfs there instead (a declared volume path that has another mount gets no anonymous volume). The ubi9 image runs as `mysql` (uid 999), so the database's tmpfs needs `uid=999,gid=999`: a root-owned one fails at start with `Can't create/write to file './ddl_recovery.log' (Errcode: 13)`. InnoDB keeps its default `O_DIRECT` on it. Verified with a dump plus a binlog replay: no volume appeared during the run, and after a `kill -9` only the two containers remained, with no volume.
- `backup-restore.sh rehearse` (`make migration-rehearsal`) restores into the drill's throwaway container and runs the Flyway CLI image `flyway/flyway:13.1.0-alpine` against it with `--network container:<target>`, so it reaches `127.0.0.1:3306` without a published port. Keep that image's version equal to `flyway` in `gradle/libs.versions.toml`, and its arguments equal to `createDatabase`'s (`defaultSchema`, `createSchemas`, `baselineOnMigrate`), or the rehearsal tests a different migration than prod runs. It finds the migrations from its own location (`../../..` is the repository root, `service/<schema>/data/src/main/resources/db/migration/<schema>`). macOS's awk rejects a newline in a `-v` value ("newline in string"), so the before/after counts reach awk through stdin, tagged per line. Verified on a dump with the 0.16.1 schema and seeded rows: the 0.17.0 migrations applied and listed the four new tables, an added `DELETE` showed its table's count drop, and a failing script exited 1 naming its schema.
- A restore with `--until` re-applies the deletions it undoes (runbook under Restoring prod in `ansible/README.md`). `sql`/`drill --until` first run the script again as `"$BASH" "$0" erasures` (its own containers and trap), which restores the latest point and prints, per record table that exists there, a `CREATE TABLE IF NOT EXISTS` built from its `SHOW CREATE TABLE` (so a restore to a point before the table existed still takes the inserts, and the app's own `CREATE TABLE IF NOT EXISTS` migration finds it later) and one `INSERT IGNORE … reapply_requested = TRUE` per record. All records, not just those after T: each is written in its deletion's transaction, so the ones the restored database already holds are skipped by the primary key, which is exact where an `erased_at > T` cut would have to guess how binlog event times straddle T. The output starts with `SET autocommit = 1`: the dump's `set autocommit=0;` stays in effect after it, so without that the appended statements ran in an open transaction, a `CREATE TABLE` committed the inserts before it, and the last insert was rolled back when the client disconnected. Verified end to end on a dump plus binlogs (an account deleted before T, an account and a client after it): `drill --until` reported 1 and 1, the `sql` output restored into a fresh database marked exactly those two, and the monolith image started on it deleted both again at start (`appointments.deleted_user`/`deleted_client` filled through the events, nothing parked). `FLUSHALL` is renamed away in prod's Valkey, so the runbook empties it with `valkey-cli --scan | xargs -r -n 500 valkey-cli del` (verified on `valkey:8.1.11-alpine`, password through `REDISCLI_AUTH`).
- The per-person keys (`<svc>_short_retention.subject_key`) never reach the binlog or the nightly dump: `db/tuning.cnf` lists the four key schemas in `binlog_ignore_db`, and the `dump` service dumps them every 5 minutes into `keys/` (`keys-once`), kept 7 days with the newest always kept, because the privacy texts promise an erased person's data is unreadable in every backup 7 days after erasure. Verified on 11.8.3 with `binlog_format = ROW`: every row change to a key table is left out, its annotated SQL text included, whatever the session's default schema, and `CREATE DATABASE <key schema>` too; but DDL is filtered by the default schema, so Flyway's `CREATE TABLE <svc>_short_retention.subject_key` (default schema `<svc>`) is logged, and a binlog replay fails with an unknown database unless the key schemas exist first. `backup-restore.sh` therefore always starts with `CREATE DATABASE IF NOT EXISTS` for them, then the key dump, then the data dump and binlogs. Shredding also writes the id into the binlogged `<svc>.shredded_subject` (`library/encryption`), and every `sql`/`drill` ends with one `INSERT … SELECT … ON DUPLICATE KEY UPDATE` per service that turns every ledgered key into a tombstone (wrapped in `BEGIN NOT ATOMIC` with a 1146 handler, under `DELIMITER ;;`, since a restore to before 0.18.0 has no ledger); with `--until` the `erasures` pass also copies the latest point's ledger rows. Key dumps never land on the operator's disk: `fetch-backups` excludes `/keys/` with `--delete-excluded`, and the restore streams the newest one with `ssh <host> cat` into the helper container (`--keys-from`, resolved from the inventory by `scripts/backup-keys-source.sh` through the JSON stdout callback; `BACKUP_RESTORE_SSH` replaces `ssh` in tests). The keys exist only on the backup node: losing its disk loses every key. A key dump must not stall behind a failed nightly dump, so the loop schedules the dump's retry instead of sleeping. Verified end to end: `backup.sh` dumps and binlogs from a prod-like 11.8.3, a key shredded after the key dump came back shredded and a key created after it was missing, both for the latest point and with `--until` before the shred.
- Testing locally: Docker Desktop reports a bind-mounted file as executable even at `0444`, so the MariaDB entrypoint runs `init-schemas.sh` instead of sourcing it and fails with `Permission denied`. A local prod-like database therefore creates the schemas with an equivalent `.sql` file. Flyway 11.10's bundled MariaDB driver ignores `sslMode`, so against `require_secure_transport` use `useSsl=true&trustServerCertificate=true`. `gpg` in a container can't create its agent socket in a GNUPGHOME bind-mounted from macOS, so copy the keyring into the container first. The whole chain was verified that way: a restore to the latest point and one with `--until` both matched the source's `CHECKSUM TABLE` on all 52 tables, across a binlog service killed mid-stream.

## Compose files and stacks

The swarm compose schema rejects unquoted booleans in `environment` (`GF_SMTP_ENABLED: "true"`), so validate a changed stack with `docker stack config -c <file>` before deploying. YAML `<<:` merges one level deep, so a service that merges the `*replicated` template and declares its own `deploy:` loses the whole template `deploy:` block: merge `<<: *replicated-deploy` inside it (Prometheus had run without the restart and rollback policy that way).

The compose files under `deployment/prod` and `deployment/adminpanel` remain the source of truth: the `stack` role copies a stack's directory to `/opt/bookk/stacks/<stack>/` on the manager and runs `docker stack deploy` there (removing files gone from the repo first, and the vault-rendered secret files again right after the deploy, since Docker only reads them then; the `docker_stack` task runs under `no_log`, its result holds every service's env), with variables from the encrypted `inventory/group_vars/all/vault.yml` (`make vault-import` builds it and generates every key and password; `make vault-update` adds what a newer structure needs without replacing set values). Every vault value the roles or inventory read, optional ones included, is added by `make vault-update`: a required one in `REQUIRED_KEYS` (`CHANGE_ME`), a generated one in `generated_secrets()`, an optional one in `OPTIONAL_KEYS` (`scripts/import-secrets.py`) with the empty value that turns its feature off, never `CHANGE_ME`, which a feature would read as set. Never tell the operator to add a key by hand, and put optional settings in the vault, not in `inventory/group_vars/all/main.yml` (`vault_telegram_bot_id`). A new infra stack needs an entry in `infra_stacks` and a tagged task in `playbooks/site.yml`.

The role refuses to create a stack that doesn't exist yet unless `-e allow_new_stacks=true` (`make bootstrap`, `make deploy v=… first=1`).

The app deploys `start-first` (two copies overlap briefly). A release whose old copy must not run next to the new one (0.18.0: a 0.17.0 relay would publish encrypted payloads to consumers that can't open them) deploys with `make deploy v=… stop_first=1`, which the monolith role passes as `MONOLITH_UPDATE_ORDER=stop-first` into the `monolith` service's `update_config.order`; the next plain deploy goes back to `start-first`.

## Deploys and the website

CI only publishes images; every deploy is run by hand from the operator's machine (`make deploy v=…` for the monolith, `make deploy-site v=…` for the website, `make deploy-webapp v=…` for the web app), and the swarm pulls the image from `ghcr.io` with the vault's registry token (`--with-registry-auth`). The vault is gitignored, so nothing in the repository or CI can decrypt it; never reintroduce a workflow that connects to the servers or needs the vault password.

The public website (`ghcr.io/nocturneproperties/bookkme-site:<version>`, a Kobweb server built and published by the `bookkme-client` repository's `site-v<version>` tag workflow) is the `site` stack (`deployment/prod/site/site-compose.yml`, `site` in `inventory/group_vars/all/main.yml`, `roles/site`, `playbooks/deploy-site.yml`): one replica on a worker, `start-first`, alias `site.service` on `operational`, port 8080. It lives on its own domain, the mail domain (`site.domain_name` is `vault_stack_env.EMAIL_DOMAIN_NAME`, `bookkme.com`; the API stays on `DOMAIN_NAME`, `bookkme.app`, which keeps the app-link `/.well-known/` files), and reaches nginx as `SITE_DOMAIN_NAME` (`nginx_stack_env`); `roles/nginx` refuses it empty or equal to `DOMAIN_NAME`. nginx has a second public server block for `${SITE_DOMAIN_NAME}` and `www.`, which sends `location /` to `upstream site.service` (`resolve`, keepalive 30 s like the API upstreams), so nginx starts while the stack is missing (those pages answer 502); the API block has no `location /`. The `acme-sh` service runs `certificates/acme_certificates.sh` (swarm config `acme-certificates-v<n>`, reading `DOMAIN_NAME`, `SITE_DOMAIN_NAME` and `ACME_ACCOUNT_EMAIL` from its environment), which issues two certificates, `${DOMAIN_NAME}` + `*.${DOMAIN_NAME}` and `${SITE_DOMAIN_NAME}` + `*.${SITE_DOMAIN_NAME}` (covering `www.` and the web app's `app.`; same Cloudflare DNS challenge; `dns_cf` finds each name's zone itself), the site's into the `nginx-cert-${SITE_DOMAIN_NAME}` volume, then `exec`s `crond`. Each `--deploy` gets its `DEPLOY_DOCKER_CONTAINER_*_FILE` paths as a prefix on that command, never in the service's `environment`: acme.sh 3.1.2's `_getdeployconf` prefers the environment over a certificate's saved deploy settings, so container-wide paths would make the nightly `acme.sh --cron` deploy the site's renewed certificate over the API's files. With the prefix, the docker hook saves each certificate's paths in its own conf (`SAVED_DEPLOY_DOCKER_CONTAINER_*`, with `Le_DeployHook`), and the cron renewal (each certificate in its own subshell in `renewAll`) deploys each to its own files. What both certificates share stays in the environment: `DEPLOY_DOCKER_CONTAINER_LABEL` is not a certificate's domain but the filter the hook uses to find the container to copy into, `sh.acme.autoload.target=nginx`, matching the label on the nginx service, and `DEPLOY_DOCKER_CONTAINER_RELOAD_CMD`. The site's issue and deploy run inside an `if !`, so a failure there only logs and `crond` still starts and renews the API's certificate; the API's steps stay fatal under `set -e` as before. `wait_for_cert.sh` (config `nginx-cert-wait-v<n>`) waits only for the API certificate and writes a 30-day self-signed placeholder for a missing site certificate, so a token without the site's zone can never keep nginx, and with it the API, from starting; the next successful deploy overwrites it and reloads nginx. Certificate alerts read acme-sh's log in Loki (`loki/certificate_rules.yml`): the image's crontab sends `acme.sh --cron` (23:48 UTC) to `/proc/1/fd/1` and `/proc/1/fd/2`, and since the script `exec`s `crond` as PID 1 that is the service log. acme.sh 3.1.2 ends a failed renewal, a failed `--deploy` after a renewed certificate included, with `Error renewing <name>_ecc.` on stderr, uncoloured outside a terminal, and every nightly run with `===End cron===`, so `CertificateRenewalFailed` matches the first and `CertificateRenewalNotRunning` alerts when the second is missing for 26 hours; `SiteCertificateMissing` matches the script's own placeholder line. A failed API certificate at startup stops the script under `set -e`, which `ContainerRestarting` reports. Verified with the real Loki config and rules, Alloy and an acme.sh 3.1.2 container running `--cron` against an unreachable ACME server: each alert fired on its line, and the missing-run alert cleared once `===End cron===` arrived. The Kobweb server runs on Ktor's Netty engine, which kept an idle keep-alive connection open for over 2 minutes, so nginx's 30 s upstream keepalive never reuses a closed one. It idles at ~90 MiB; the 384M limit with `MaxRAMPercentage=50` keeps a full heap under `ContainerHighMemoryUsage`'s 80%. Verified with the real template in `nginx:1.29.4` against the site image: `/` and other paths reached the site, the well-known files and `/api` routes were unchanged, and 40 requests used 7 upstream connections; after the split into two domains, the site domain and `www.` reached the site with the placeholder certificate, the API domain kept its well-known files and answered 404 on `/`, and the site served its placeholder certificate. `acme_certificates.sh` in the acme.sh image with the real docker deploy hook against a local nginx container carrying the label (only `--issue` and `--register-account` faked) put each certificate into its own directory, replaced each with its own new version on a later deploy with no paths in the environment (the nightly renewal's case), and on a failed site issuance still deployed the API's and started `crond`.

The client web app (`ghcr.io/nocturneproperties/bookkme-webapp:<version>`, from the `bookkme-client` repository) is the `webapp` stack, a copy of the site's setup: `deployment/prod/webapp/webapp-compose.yml`, `webapp` in `inventory/group_vars/all/main.yml`, `roles/webapp`, `playbooks/deploy-webapp.yml`, `make deploy-webapp v=…`; one replica on a worker, `start-first`, alias `webapp.service` on `operational`, port 8081 (the site uses 8080), 384M. nginx serves it on `app.${SITE_DOMAIN_NAME}` (no new variable: like `www.`, it is derived from the site's domain, and so are its CORS origin, its `/.well-known/webauthn` entry and its passkey origin in `passkeyOrigins`) with the site's certificate, which is why that certificate is `*.${SITE_DOMAIN_NAME}` (config `acme-certificates-v2`; acme.sh 3.1.2 reissues when a certificate's domain list changes instead of skipping it until renewal). Its block has `upstream webapp.service` with `resolve`, so nginx starts while the stack is missing (502), and the default access log, not `site_access`, so its traffic stays out of the `site_*` metrics. `WebAppDown` (`prometheus/site_alerts.yml`) mirrors `SiteDown` on `webapp_webapp`. Verified with the real template in `nginx:1.29.4` against a stand-in `webapp.service`: `app.` reached it, a preflight from `https://app.bookkme.com` got the CORS headers, a foreign origin none, and `/.well-known/webauthn` listed the three origins; the alert rules with promtool.

## VPN and nginx

The wg-easy panel (pinned to v14 by digest, configured by env vars; v15 is a different, setup-wizard config) is reachable only through nginx's `vpn.` host from the VPN subnet, its port 51821 unpublished, so the first client configs come from the `vpn_clients` role (tag `vpn`): it calls the panel's own API inside the container with `vault_vpn_password` (the plain password behind `VPN_PASSWORD_HASH`) via `docker exec … node --eval`, creates the missing `vpn_clients` and saves their configs to the gitignored `deployment/ansible/vpn-clients/`. wg-easy v14's image points `iptables` at the legacy backend, whose `nat` table an nf_tables host (Ubuntu 26.04) never loads and the container can't load, so its default hooks fail and the container crash-loops: `vpn-compose.yml` sets `WG_POST_UP`/`WG_POST_DOWN` to the same rules via the image's `iptables-nft` instead (verified in a throwaway container on the manager). dnsmasq publishes 53/udp in `mode: host`, and `docker_host` disables systemd-resolved's stub listener on managers: with the stub holding `127.0.0.53:53`, Docker silently publishes nothing for port 53 (no `docker-proxy`, no NAT rule), and every VPN client loses DNS and with it the internet. WireGuard's endpoint is the manager's public IP (`WG_HOST` = `VPN_ENDPOINT` from `vault_hosts`), never a hostname: Cloudflare proxies `vpn.<domain>` and carries no UDP, and a DNS-only record would publish the IP.

Every swarm node joins the VPN on `wg0` (`vpn_host` role) as its inventory `vpn_client`, pinned to its `vpn_address` through the API (manager `admin-1` on `vpn_host_address`, worker `worker-1` on `.4`; workers read their configs from the manager's `vpn_clients` run): dnsmasq resolves the domain to that address and wg-easy hands it out as DNS, so VPN traffic reaches nginx via the manager's `wg0` with its VPN source address intact, which is what makes nginx's subnet filter work. nginx therefore keeps 443 in `mode: host` (ingress mode would allow `start-first`, but the routing mesh rewrites the source address and every VPN-only host would deny the VPN), and avoids restarts instead: its templates, `snippets/` and `static/` are read-only directory bind mounts from the stack directory, not swarm configs (a single-file bind mount keeps the old inode after Ansible renames a new file over it), and `roles/nginx` re-renders the templates, runs `nginx -t` and reloads inside the running container when the files changed but the service spec didn't, restoring the previous `conf.d` if the test fails.

SSH and WireGuard refuse Ukrainian addresses (`roles/geoblock`, tag `geoblock`, runbook in `ansible/README.md`), because the privacy policy and DPA promise that no one reaches production data from Ukraine. The rules live in their own nftables table `inet bookk_geoblock`, a `filter` chain on the `prerouting` hook at priority `raw`, which runs before Docker's NAT (`dstnat`) and so should drop a packet before the swarm ingress mesh rewrites its source (not yet checked on the swarm itself: after the first run, the `udp dport 51820` counter must rise for a test from a Ukrainian address); Docker never touches the table; never enable Ubuntu's `nftables.service`, whose `flush ruleset` would also wipe Docker's rules. Verified in an Ubuntu 26.04 container: SSH and UDP from a Ukrainian source in a network namespace were dropped and other sources passed, and the role ran idempotently, with `--check`, and refused a caller inside the ranges with exit code 3. The lockout check reads the established SSH peers from `/proc/net/tcp`/`tcp6` instead of `SSH_CONNECTION`: `worker-1`'s gathered `env` facts had no `SSH_CONNECTION`, which failed the first prod run. Never block 443: Ukrainian businesses and clients use the app.

Cloudflare's `set_real_ip_from` ranges (`snippets/cloudflare-real-ip.conf`, regenerated by `scripts/cloudflare-real-ip.sh`, checked against Cloudflare's live lists on every `tags=nginx` run) are included only in the public `${DOMAIN_NAME}` and `${SITE_DOMAIN_NAME}` server blocks, never at http level, so a VPN-only block's `allow` always checks the real TCP peer, never a header.

The public block's `/api/<svc>` routes proxy to `upstream` blocks named after the service aliases (`authorization.service`, …, so the `Host` header stays the alias), each `server <alias>:80 resolve` with a `zone`, `keepalive 16` and `keepalive_timeout 30s`, plus `proxy_http_version 1.1` and an empty `Connection` header at server level. A `set $upstream …; proxy_pass http://$upstream` opens a new TCP connection to the app for every request (20 of 20 in a local test, against 1 with the upstream block); `resolve` (nginx 1.27.3+) still lets nginx start while a name doesn't resolve and follows a changed address after the resolver's `valid=30s`. The keepalive timeout must stay below Ktor CIO's `connectionIdleTimeoutSeconds` (45 s default), or nginx reuses a connection the app just closed and a POST fails with 502. A variable `proxy_pass` in another block also matches these upstream names, so never point one at an alias without its port. The email-code routes get exact-match locations with per-IP `limit_req` (`$binary_remote_addr`, which the real-ip snippet makes the Cloudflare client address; a spoofed `CF-Connecting-IP` from a non-Cloudflare peer is ignored): `email_code_send` (2/min, burst 5) on `passkey/sign_up/challenge` and `POST /api/auth/email`, `email_code_redeem` (10/min, burst 10) on `sign_up` and `email/confirm`, answering 429 and logging at `warn`. The app's own per-address limits (`library/email`) stay the real protection; these only stop one IP spraying addresses or Hostinger Mail API sends. `sign_in_challenge` (10/min, burst 20) covers `passkey/sign_in/challenge`, which needs no login and stores a challenge in Valkey for 10 minutes on every call, so under `noeviction` one IP could otherwise fill the cache; it serves sign-in and action confirmation, one challenge each, and the burst leaves room for several users behind one address. `business_link_resolve` (30/min, burst 30) covers the prefix `/api/business/link/`, the public link lookup behind bookkme.com/{name}, so one IP can't enumerate link names; the prefix never matches the signed-in `/api/business/{id}/link`. The whole public API block allows the website's browser code through CORS, set at server level so every location inherits it: the `$site_cors_origin` map echoes an `Origin` of `https://${SITE_DOMAIN_NAME}`, `https://www.${SITE_DOMAIN_NAME}` or the web app's `https://app.${SITE_DOMAIN_NAME}` into `Access-Control-Allow-Origin`, and the `$site_cors_methods`/`_headers`/`_expose`/`_max_age` maps fill the other headers only for that origin (methods `GET, POST, PUT, PATCH, DELETE, OPTIONS`; request headers `Authorization, Content-Type, Accept, Accept-Language, Idempotency-Key`; `Content-Disposition` exposed for export downloads; preflight cached 24 h), with `Vary: Origin` always. Any other origin, or none, gets no CORS header, since `add_header` skips an empty value. A server-level `if ($request_method = OPTIONS) { return 204; }` answers every preflight before location matching and `limit_req`; the app has no OPTIONS routes. A location that adds its own `add_header` stops inheriting these, so give it the same lines or none. Allowing credentials isn't needed: the API authenticates with a bearer token, not cookies. Add a new request header the app reads to `$site_cors_headers`, and a response header the site must read to `$site_cors_expose`. The API block also serves `/.well-known/webauthn` (`{"origins":["https://${SITE_DOMAIN_NAME}","https://www.${SITE_DOMAIN_NAME}","https://app.${SITE_DOMAIN_NAME}"]}`, `application/json`), the WebAuthn related-origins list that lets the website use passkeys for the API domain's relying party; the app accepts the same origins from `APPLICATION_SITE_DOMAIN_NAME` (`monolith_env`, from `site.domain_name`), see `docs/agents/security.md`. Dev's configs allow any `http://localhost:<port>` origin instead. Verified on dev's nginx (preflight, 401, 429 and a foreign origin) and with the rendered template's maps and server block in `nginx:1.29.4`. Verified with the real template, snippets and a self-signed certificate in `nginx:1.29.4`.

The subnet (`172.16.91.0/24`, outside Docker's bridge and overlay pools) is set only as `vpn_network_prefix` in `inventory/group_vars/all/main.yml` and reaches wg-easy, dnsmasq and nginx as `VPN_SUBNET`/`VPN_ADDRESS_TEMPLATE`/`VPN_HOST_ADDRESS` (`vpn_stack_env`), never hard-coded. wg-easy keeps the server address from its first start in `wg0.json` and ignores `WG_DEFAULT_ADDRESS` afterwards, so `ensure-clients.js` renumbers an install whose stored prefix differs (backup → rewrite every address, keeping host numbers and keys → restore → `wg-quick down/up` in the container).

## Images

`bitnami/*` images can no longer be pulled from Docker Hub: the cache everywhere (dev, prod, `RedisCacheClientTest`) is Valkey (`valkey/valkey:8.1.11-alpine`, configured on the command line: `--requirepass`, `--appendonly yes`, `FLUSHDB`/`FLUSHALL`/`CONFIG` renamed away) and prod uses the official `mariadb` image.

`deployment/prod/kafka/kafka-compose.yml` (not deployed today) mirrors dev's Kafka (`apache/kafka-native:4.2.1`, the same `KAFKA_*` settings and fixed ports 9092/9093) as a single broker like dev, reachable as `kafka:9092` on the `operational` network and pinned to the node labelled `kafka=true` (the `swarm` role applies a host's inventory `swarm_labels` with `docker_node`; values must be quoted strings, an unquoted `true` reaches Docker as `True` and never matches), because its data lives on a node-local volume. Its volumes are mounted at `/home/appuser` with `KAFKA_LOG_DIRS=/home/appuser/kafka-data` instead of dev's `/var/lib/kafka/data`: that path doesn't exist in the image, so a fresh volume there is root-owned and the broker (uid 1000) can't write to it. Dev fixes that with a `chown` init container, which Swarm can't order (it ignores `depends_on`); a volume mounted on the image's own `appuser`-owned home directory inherits that ownership instead.

## Dev environment

Dev deployment artifacts mirror the per-service ones: `deployment/dev/service/monolith.env` (one env file, all internal `*_SERVICE_HOSTNAME` vars pointed at `monolith.service` itself since every route lives in one process, no Kafka vars since it's embedded), `deployment/dev/monolith-compose.yml` (one `monolith` service, both the app port and the jdwp debug port published to the host), and `deployment/dev/rollout-monolith.sh` (same shape as `rollout.sh`, but builds the root project's image directly instead of looping per service).

Dev nginx routes differently per mode: `environment-compose.yml` mounts `${NGINX_CONF:-nginx.conf}`, `rollout.sh` sets `nginx.conf` (one upstream per `<svc>.service`) and `rollout-monolith.sh` sets `nginx-monolith.conf` (all of `/api/` and the JWKS to `monolith.service`, which has no per-service aliases in dev). Bringing the environment up by hand for the monolith needs `NGINX_CONF=nginx-monolith.conf`, or nginx keeps proxying to stale or unresolvable microservice hosts. Kafka (`kafka`, `kafka-ui`, `kafka-volume-init`) sits behind the compose profile `kafka`, which only `rollout.sh` enables (`--profile kafka`), since the monolith's events never leave the process: `rollout-monolith.sh` starts the environment without it and removes any Kafka containers left from a microservices rollout (the `kafka_volume` stays), so bringing the microservices up by hand needs `--profile kafka`. Both dev configs mirror prod's `upstream` blocks (`resolve`, keepalive 30 s) and `limit_req` zones (VPN and nginx above), so the app sees the same 429s; repeated sign-up testing from one address hits them, and restarting the nginx container empties the zones.

Jib builds `linux/amd64` unless told otherwise, so on an Apple Silicon machine a plain `publishImageToLocalRegistry` gives an image that runs under emulation. Both rollout scripts first switch to the `default` Docker context, then build with `-Djib.from.platforms=linux/<arch>`, where `<arch>` is the local daemon's `docker version --format '{{.Server.Arch}}'`. The context switch comes first because `jibDockerBuild`, `docker compose` and the arch lookup all use the current context: left on `swarm-manager`, they would build for the prod manager and load the image there. The CI publish workflows pass no flag and keep building amd64 for prod.
