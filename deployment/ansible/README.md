# Ansible deployment

Runs from your machine (or CI) over SSH against the prod swarm. Nothing is installed on the servers besides Docker and the Python libraries the Docker modules need.

Prod runs the **monolith** (`MonolithServer`, events in-process, no Kafka) as one stack: the app, one MariaDB holding all five schemas, and one Redis. The app answers on the network aliases `authorization.service`, `user.service`, `business.service`, `appointments.service` and `notifications.service`, so nginx routes `/api/<svc>` to it unchanged.

MariaDB and Valkey are reachable only on the `storage` network, which the app, the two exporters and NocoDB join next to `operational`; nginx, the VPN stack and monitoring can't reach them. Every network in `swarm_networks` is an encrypted overlay (IPsec between nodes), created by the `swarm` role (`make infra tags=swarm`), and must exist before a stack that uses it is deployed. MariaDB also refuses unencrypted connections (`require_secure_transport` in `db/my.cnf`), and the app connects with `sslMode=verify-full`. MariaDB ≥ 11.4 generates a self-signed certificate when none is configured, and MariaDB Connector/J ≥ 3.4 verifies it against the login password (MariaDB's zero-configuration TLS, for `mysql_native_password` or `ed25519` users with a password), so there is no CA or certificate to rotate. Any other database client must turn TLS on itself: `database-exporter` runs with `--tls.insecure-skip-verify`, because its Go driver can't verify the certificate that way, so its connection is encrypted but the certificate isn't checked.

The compose files in `deployment/prod` and `deployment/adminpanel` stay the source of truth: a stack deploy copies the stack's directory to `/opt/bookk/stacks/<stack>/` on the manager, writes its secret files from the vault next to it, and runs `docker stack deploy` there with the stack's variables in the environment. Docker reads the secret files (configs, secrets, `env_file`) only during that deploy and keeps them in the swarm, so they are deleted again right after it, also when it fails, and nothing from the vault stays on the manager's disk; files that are no longer in the repo are removed from the copy before each deploy. The monolith deploy logs out of the image registry afterwards, since `--with-registry-auth` already stored the credentials in the service. The roles install with apt, so a host that is not Debian-based fails the run instead of being skipped. Kafka (`deployment/prod/kafka`) and the per-service stacks (`deployment/prod/microservice`) are not deployed by Ansible.

## One-time setup

```sh
brew install ansible ansible-lint
security add-generic-password -a "$USER" -s bookk-ansible-vault -w "$(openssl rand -base64 32)"
security find-generic-password -s bookk-ansible-vault -w     # save this in your password manager
cd deployment/ansible
make vault-import    # builds the encrypted inventory/group_vars/all/vault.yml and generates every key and password
make vault-edit      # fill in what the import reported as CHANGE_ME
```

`make vault-import` reads `deployment/prod/keys/global/.env`, the dozzle users and alertmanager config, and generates the MariaDB encryption key, the signing-key encryption key, the database/Redis passwords, the Prometheus password, the Dozzle session secret, the NocoDB admin password, the email code secret (`vault_email_code_secret`) and the personal data encryption keys (`vault_subject_master_key`, `vault_blind_index_key`; the deploy refuses to run without them). The subject master key wraps every person's key: the app can't read any encrypted field or export without it, so never replace or lose it (the vault is its only copy). `vault_postmark_server_token` (the Postmark server token the app sends sign-up and email-change codes with) stays `CHANGE_ME` until you fill it in, and `make deploy` refuses to run until then. The codes come from `notifications@<EMAIL_DOMAIN_NAME>`, a `vault_stack_env` entry that `make vault-update` adds empty, separate from `DOMAIN_NAME` because mail goes out from another domain than the app's; the deploy refuses it empty too; `development_token`, which makes the app log emails instead of sending them, is refused too. Postmark sends only from a verified domain: add `EMAIL_DOMAIN_NAME` in Postmark and its DKIM and Return-Path records in Cloudflare (DNS isn't managed here) before the first deploy that needs email. `make vault-update` brings an existing vault to the current structure: it generates whatever is missing and never replaces a value that is set.

The vault password is read by `scripts/vault-pass.sh`: `$ANSIBLE_VAULT_PASSWORD` first (CI), then the `bookk-ansible-vault` keychain item, then `~/.bookk-vault-pass`. `vault.example.yml` shows the expected structure. Add every worker to `inventory/prod.yml` and its address to `vault_hosts`; the monolith, its database and Redis are placed on workers. A stack that keeps data on a local volume is pinned to one node by a swarm label, which `make infra tags=swarm` applies from the host's `swarm_labels` (values must be quoted strings):

```yaml
    workers:
      hosts:
        worker-1:
          ansible_host: "{{ vault_hosts['worker-1'] }}"
          swarm_labels:
            database: "true"
            kafka: "true"
```

The monolith's MariaDB and Valkey run only on the node labelled `database: "true"`, Kafka (when deployed) only on the one labelled `kafka: "true"`, Prometheus and Grafana only on the one labelled `monitoring: "true"` (`manager-1`); the app itself runs on any worker. Without the label the task stays pending instead of starting on an empty volume elsewhere, so label exactly one node for each before the first deploy (`make bootstrap` applies the labels before `make deploy`).

Edit the vault with an editor that keeps no history of the decrypted temp file: `EDITOR=nano make vault-edit`, or VS Code with `"workbench.localHistory.exclude": { "**/.ansible/tmp/**": true }`.

**Back up the vault password and `vault_swarm_secrets.mariadb_encryption_key`.** Every table is encrypted with that key; without it the database files and their backups are unreadable.

## First deployment

Publish the image first: bump `version` in the root `build.gradle.kts`, then push a matching tag (`git tag monolith/0.15.2 && git push origin monolith/0.15.2`). `.github/workflows/monolith-publish.yml` pushes `ghcr.io/nocturneproperties/bookkme-server:<version>` and refuses a tag that differs from the project version.

```sh
make check                     # what would change, connects but changes nothing
make bootstrap                 # hosts, swarm, networks, secrets, infra stacks (creates stacks that don't exist yet)
make deploy v=0.15.2 first=1   # the monolith, creating its stack
```

| What | Command |
|---|---|
| Preview everything (no changes) | `make check` |
| Preview one stack | `make check tags=nginx` |
| Hosts, swarm, networks, secrets and all infra stacks | `make infra` |
| Only some stacks | `make infra tags=nginx,monitoring` |
| Deploy / roll back the monolith | `make deploy v=0.15.2` |
| Edit secrets | `make vault-edit` |
| Copy the encrypted backups to `backups/` | `make fetch-backups` |
| Test-restore them into a throwaway container | `make restore-drill` (or `until='2026-11-02 14:30:00'`, UTC) |
| Run this checkout's migrations on the latest backup before deploying | `make migration-rehearsal` |
| Syntax check / lint | `make syntax` / `make lint` |

Tags: `hosts` (Docker, SSH and the geoblock), `ssh` (only the SSH hardening), `geoblock` (only the geoblock), `swarm`, `vpn`, `nginx`, `orchestrator`, `monitoring`, `admin`, `backup`.

Every host allows SSH logins by key only: `roles/ssh_hardening` writes `/etc/ssh/sshd_config.d/10-hardening.conf` (`PasswordAuthentication no`, `KbdInteractiveAuthentication no`, `PermitRootLogin prohibit-password`), checks it with `sshd -t`, reloads `ssh` and asserts the effective `sshd -T` values. The file name sorts before Ubuntu's `50-cloud-init.conf`, which turns password logins on, and sshd keeps the first value it reads. Port 22 is open to the internet for the GitHub-hosted deploy job, so this is what keeps it safe.

No one may reach production data from Ukraine (BookkMe's privacy policy and DPA say so), so every host drops SSH (22/tcp) and WireGuard (51820/udp) from Ukrainian addresses: `roles/geoblock` installs `/usr/local/sbin/bookk-geoblock`, which builds the ranges from RIPE NCC's delegated statistics (checked against their MD5) and loads them as the nftables table `inet bookk_geoblock`. `bookk-geoblock.service` loads the saved rules at boot and `bookk-geoblock.timer` refreshes them daily; a failed refresh keeps the previous rules. The run refuses to load ranges that hold any connected SSH client's address (read from `/proc/net/tcp` and `tcp6`, so this run's own connection included) and changes nothing, so run `make infra tags=geoblock` from outside Ukraine and with no SSH session open from there. Countries and ports are `geoblock_countries`, `geoblock_tcp_ports` and `geoblock_udp_ports` in `roles/geoblock/defaults/main.yml`. The registry country is the holder's, so this stops ordinary Ukrainian connections, not one routed through another country; the rule itself is a policy every operator follows, and this is its enforcement for the two ways into the servers. Check it on a host with `nft list table inet bookk_geoblock` (the counters show dropped packets). Locked out by a wrong range: log in through the provider's browser console and run `nft delete table inet bookk_geoblock`.

## Safety rails

- **No accidental duplicate stacks.** A stack deploy fails if no stack of that name is deployed yet, so a wrong name in `inventory/group_vars/all/main.yml` cannot start a second copy of a stack next to the real one. `make bootstrap` and `make deploy … first=1` pass `-e allow_new_stacks=true`.
- **Secrets are only created, never replaced.** The swarm role creates a missing secret from `vault_swarm_secrets` and refuses one still set to `CHANGE_ME`; rotating an existing secret stays a manual `docker secret` operation, because swarm secrets in use cannot be updated in place.
- **`--check` skips stack deploys** (`community.docker.docker_stack` has no check mode); it still shows file changes, network and secret differences.
- **Secret files are never diffed or logged** (`diff: false`, `no_log`). Neither is a stack deploy: `docker_stack`'s result carries every service's spec, vault-built env included, so it runs under `no_log` and a separate assert reports Docker's error message on failure. The deploy workflow writes the SSH key itself (`ANSIBLE_PRIVATE_KEY_FILE`), so no third-party action ever sees it or the vault password.

## VPN clients

wg-easy v14's image points `iptables` at the **legacy** backend, and an nf_tables host (Ubuntu 26.04, kernel 7.0) never loads the legacy `iptable_nat` module, which the container cannot load itself: its default `wg-quick` hooks then fail with ``can't initialize iptables table `nat'``, the container exits and swarm keeps replacing it (the `vpn_clients` role reports `No such container`, since the id it waited for is already gone). `vpn-compose.yml` therefore sets `WG_POST_UP`/`WG_POST_DOWN` to the same rules through the image's `iptables-nft`, which uses the nf_tables modules Docker already loads; keep both hooks in step with each other.

VPN clients resolve through dnsmasq on the manager's `wg0` address, so dnsmasq publishes 53/udp in `mode: host` (only on the manager, not through the ingress routing mesh on every node). Ubuntu's systemd-resolved holds port 53 on `127.0.0.53`/`127.0.0.54`, and Docker then cannot bind `0.0.0.0:53`: an ingress-published 53 got neither its `docker-proxy` socket nor its NAT rules, without an error, so every VPN client's DNS was refused (no domain, and no internet, since all of a client's DNS goes to `.2`). `docker_host` therefore turns off the stub listener on managers (`/etc/systemd/resolved.conf.d/no-stub-listener.conf`) and points `/etc/resolv.conf` at the upstream `/run/systemd/resolve/resolv.conf`.

The wildcard certificate (`DOMAIN_NAME` and `*.DOMAIN_NAME`) comes from Let's Encrypt through acme.sh in the nginx stack, with a DNS challenge on Cloudflare (`dns_cf`, token `CLOUDFLARE_DNS_API_TOKEN` in `vault_stack_env`, needing Zone Read and DNS Edit on the zone). acme.sh keeps its account, certificates and renewal settings in `/acme.sh` (the image's `LE_CONFIG_HOME`), which is the `acmesh-data` volume; it used to be mounted at `/acmesh/<domain>_ecc`, a path acme.sh never uses, so every new container issued a new certificate. With the state kept, a restart's `--issue` exits `2` (not due for renewal), which the command treats as success so `--deploy` and `crond` still run; the image's daily cron renews from the saved state. To force a new certificate: `docker exec $(docker ps -q -f name=nginx_acme-sh) acme.sh --issue --force --server letsencrypt --dns dns_cf -d <domain> -d '*.<domain>'` (Let's Encrypt allows 5 identical certificates per week).

nginx changes its configuration by reloading, not restarting. A restart drops HTTPS for a few seconds: 443 is published in `mode: host`, so the new task can't start until the old one has stopped. Ingress mode would allow `start-first`, but the routing mesh rewrites every source address, which breaks the VPN-only hosts' `allow ${VPN_SUBNET}` and `local.`'s `proxy_pass http://$remote_addr`. So the files nginx reads are bind-mounted read-only from the stack's directory on the manager, not swarm configs: `templates/` (rendered by the image's entrypoint into `/etc/nginx/conf.d`), `snippets/` and `static/` (the well-known files). They are directory mounts because Ansible replaces a file by renaming a new one over it, and a single-file bind mount keeps showing the old one. `tags=nginx` reads the service spec before and after the deploy (`roles/nginx`): when the spec is unchanged but the copied files changed, it re-renders the templates inside the running container, runs `nginx -t` and `nginx -s reload`, which replaces the workers without dropping connections. If `nginx -t` fails, the run fails, the previous `conf.d` is put back and the old configuration keeps serving; fix the file and rerun, since the next restart would render the broken one. When the spec changed (image, env, ports, networks), Swarm restarts the task with the new files and nothing is reloaded. A removed template's rendered file stays in `conf.d` until the next restart (`docker service update --force nginx_nginx`).

Public traffic reaches nginx from Cloudflare's edge, so the TCP peer is a Cloudflare address. `snippets/cloudflare-real-ip.conf` trusts Cloudflare's published ranges (`set_real_ip_from`) to set the client address from `CF-Connecting-IP` for the access logs. Only the public server block (`${DOMAIN_NAME}`) includes it, never the http level: the VPN-only blocks must check `allow ${VPN_SUBNET}` against the real peer, whatever headers a request carries. The header can be trusted because the provider firewall admits 443 only from those ranges (`scripts/cloudflare-firewall.sh`). Every `tags=nginx` run compares the snippet with `https://www.cloudflare.com/ips-v4` and `ips-v6` and fails when they differ; then run `scripts/cloudflare-real-ip.sh`, which rewrites the snippet, and `scripts/cloudflare-firewall.sh`, so the firewall admits the same ranges.

Every client config's WireGuard endpoint is the manager's public IP (`WG_HOST` = `VPN_ENDPOINT`, `vault_hosts` of the first manager, in `vpn_stack_env`), not a hostname: Cloudflare's proxy carries no UDP, so a hostname endpoint would need a DNS-only record, which publishes the IP the proxied records hide. The public `vpn.` record isn't needed, since dnsmasq maps it to the manager's VPN address inside the tunnel. If the manager's IP changes, update `vault_hosts`, rerun `tags=vpn` (the nodes' `wg0` follows) and re-import every device's config. The wg-easy panel is only reachable from inside the VPN (`https://vpn.<domain>`, nginx allows only the VPN subnet; its port 51821 is not published), so the first client configs come from Ansible: every `make infra tags=vpn` (and `make bootstrap`) creates each client in `vpn_clients` (`inventory/group_vars/all/main.yml`, `admin-2` by default) and each swarm node's client that doesn't exist yet and saves all of their configs to `deployment/ansible/vpn-clients/<name>.conf` (gitignored, mode `0600`). It logs in to the panel's API inside the wg-easy container with `vault_vpn_password`, the plain password `VPN_PASSWORD_HASH` was generated from, so the two must match. Existing clients are never changed or removed: delete a client in the panel, and drop it from `vpn_clients` too, or the next run creates it again. Add a name to `vpn_clients` to get a config for another device. A config file holds that client's private key; import it into WireGuard and delete it, rerunning fetches it again.

Every swarm node is a VPN client: each host in `inventory/prod.yml` names its client and address (`vpn_client`, `vpn_address`; the manager is `admin-1` on `vpn_host_address`, `.2` of the subnet, the worker `worker-1` on `.4`), pinned through the API and brought up on the host as `wg0` by the `vpn_host` role (`wireguard-tools`, `wg-quick@wg0` enabled at boot, without the config's `DNS` line so the host keeps its own resolver), and the run waits for each handshake. The workers get their configs from the manager's run of `vpn_clients`, so `tags=vpn` must not `--limit` the manager out. A worker on the VPN is reachable from VPN clients at its own address, with no public port, which is what lets SSH go through the VPN later. That address is what the VPN's dnsmasq resolves `DOMAIN_NAME` and every subdomain to, and the DNS server wg-easy hands out, so VPN clients reach nginx and dnsmasq through the manager's `wg0`, keeping their VPN source address (wg-easy only masquerades traffic leaving to the internet), which is what nginx's `allow ${VPN_SUBNET}` checks. The node configs are therefore not saved locally: importing one on another device would take that node's address and key. If another client already holds that address, the run stops and names it; move that client to another address in the panel.

The VPN subnet is `172.16.91.0/24`, set once as `vpn_network_prefix` in `inventory/group_vars/all/main.yml` (a `/24`, the only size wg-easy v14 supports): it lies outside Docker's default bridge pools (`172.17–31.x`, `192.168.x`) and swarm's overlay pool (`10.x`), so no Docker network on a node can take it. From it come `vpn_subnet`, `vpn_address_template` (wg-easy's `x` form) and `vpn_host_address`, which reach the stacks as `VPN_SUBNET`, `VPN_ADDRESS_TEMPLATE` and `VPN_HOST_ADDRESS` (`vpn_stack_env`, merged into every stack's environment): wg-easy's `WG_DEFAULT_ADDRESS`/`WG_ALLOWED_IPS`/`WG_DEFAULT_DNS`, dnsmasq's `host-record` and nginx's `allow` lines. wg-easy stores its server address in its volume on first start and ignores `WG_DEFAULT_ADDRESS` afterwards, so when the stored subnet differs from `vpn_network_prefix` the run renumbers the install in place: backup through the panel API, the server and every client moved to the new prefix keeping their host number (`10.8.0.5` becomes `172.16.91.5`) and their keys, restore, and `wg-quick` restarted inside the container. The manager's `wg0` and the saved configs follow on the same run; every other device must re-download its config from the panel, since a client's address is part of its config. Changing the prefix again later works the same way, and needs `make infra tags=vpn,nginx`.

## Monitoring

Prometheus finds its targets through swarm DNS, one target per task: `tasks.node-exporter` and `tasks.cadvisor` (global services, one task per node, reached on the `monitoring` network only) and `tasks.monolith_monolith` (the monolith stack's service, across stacks on `operational`, port 80, `/metrics`), plus `tasks.monolith_database-exporter` (job `mariadb`), `tasks.monolith_redis-exporter` (job `valkey`) and `tasks.loki`. A service's alias (`exporter:9100` before) is its virtual IP, which balances every scrape to a random task: with several nodes the series of all of them mixed under one target, and during a monolith deploy two processes' counters alternated. node-exporter takes its node's hostname (`hostname: "{{.Node.Hostname}}"`), and the node recording rules join `node_uname_info` on `instance` for a `nodename` label, which the alerts print, since `instance` is now a task IP that changes when the task restarts.

Prometheus keeps 30 days or 5GB, whichever is reached first (~7k series measured on one node of the test stack, about 2–3GB for 30 days at these scrape intervals). Memory limits, from idle usage measured on a test swarm with several times that as headroom: Prometheus 768M (57M idle; it sets `GOMEMLIMIT` to 90% of the limit by itself), Grafana 512M (188M), Loki 512M (70M), Alloy 256M (46M), cAdvisor 256M (23M), Alertmanager 128M (12M), node-exporter 64M (9M). `ContainerHighMemoryUsage` warns at 80% of a limit.

MariaDB and Valkey are watched by two exporters in the monolith stack. `redis-exporter` logs in with the Valkey password (Valkey has a single user) and skips config metrics (`REDIS_EXPORTER_CONFIG_COMMAND=-`, since `CONFIG` is renamed away). `database-exporter` logs in as its own MariaDB user `exporter`, which holds only `PROCESS` (server status, no table data) and at most 3 connections, with `vault_monolith_db_exporter_password`. `init-schemas.sh` only runs on an empty volume and root can only log in from inside the database container, so the user comes from MariaDB's `--init-file`: the monolith deploy renders `db/users-init.sql` from `roles/monolith/templates/users-init.sql.j2` into the swarm secret `monolith-mariadb-users-init-v<n>`, and MariaDB runs it (`CREATE USER IF NOT EXISTS`, `ALTER USER`, `GRANT`) on every start. The same file creates `nocodb_reader` for NocoDB: `SELECT` only, at most 20 connections, with `vault_monolith_db_nocodb_password`, and only on the tables listed in `nocodb_readable_tables` at the top of the template. Nothing in `authorization`, no `outbox_event`/`exhausted_event` (their payloads hold personal data), no `signing_key`, no `employee_invitation` (live invite codes), no tombstones or erasure records (`deleted_user`/`deleted_client`/`erased_client` list erased people), no `flyway_schema_history`. It is an allowlist on purpose: a new table stays hidden from NocoDB until someone adds it there. Every start revokes all of the user's privileges and grants the list again, so removing a table from it takes effect on the next restart too. A table-level `GRANT` on a table that doesn't exist yet fails with 1146, and MariaDB then silently skips the rest of the init file while still starting (verified on 11.8.3), which would leave the `backup` user unset. So the grants run as one compound statement on one line (the init file ends a statement at every line ending in `;`), with a handler that skips missing tables and schemas. A table created after the database started (a migration the app runs on deploy, or every table on a fresh volume) is therefore readable by NocoDB only after the database's next restart (`docker --context swarm-manager service update --force monolith_database`, a few seconds without database). A second user, `nocodb_writer` (`vault_monolith_db_nocodb_writer_password`, at most 5 connections), gets `SELECT, INSERT` on the tables in `nocodb_insertable_tables`, today only `user.legal_document_version`, the same way. It never gets `UPDATE` or `DELETE`: a NocoDB write skips the application's events, locks and validation, so only a table whose rows are written by hand anyway belongs there, and a published legal document version must never change. Adding or renaming that secret restarts the database once, on the first deploy that carries it (a few seconds without database); changing a password or a grant needs the secret name bumped and restarts it again.

Alerts (`prometheus/node_alerts.yml`): node CPU, memory and disk; container memory and CPU throttling; `ContainerRestarting` when a container of a service started in the last 15 minutes and stopped again (a crash, an OOM kill, a failed deploy; two deploys within 15 minutes also count the replaced container); `TargetDown` for any scrape target silent for 2 minutes; `MariaDBDown`, `MariaDBConnectionsHigh` (80% of `max_connections`), `ValkeyDown`, `ValkeyMemoryHigh` (80% of `--maxmemory`, which under `noeviction` is where writes start failing); `LogStorageGrowing`; `EventsExhausted`; `BackupDumpMissing` and `BinlogShippingStalled` (see Backups).

Logs: Alloy (a global service, so one per node) reads every swarm container's output through the node's Docker socket and pushes it to Loki (`monitoring` network only, not routed by nginx, no auth) with the labels `stack`, `service` (the compose service name, `monolith` rather than `monolith_monolith`) and `node`. For the monolith it joins a stack trace to the line it belongs to (a new entry starts with the logback timestamp), drops the per-scrape `[200 OK], GET /metrics` lines, and stores the logback level as `level` structured metadata; for every other service Loki detects the level itself. Either way queries filter on `detected_level`. Loki keeps 14 days (the compactor deletes older chunks). It cannot delete by size, so `LogStorageGrowing` fires when the last day's stored chunks (`loki_ingester_chunk_size_bytes_sum`, the compressed bytes written, which matched the chunk files on disk byte for byte) would add up to more than 5GB over 14 days; the Logs dashboard shows the same projection. Shorten `retention_period` or find the noisy service then. Alloy keeps its read positions in the node-local `alloy_data` volume, so a restart resumes where it stopped. Grafana logs at `warn`: at `info` it logged every data-source query, so each dashboard refresh filled the logs with its own requests. Dozzle stays for live tailing. Dozzle runs global (one task per node) behind the `dozzle` alias, a virtual IP that sends each request to a random task, so every task must sign logins with the same key: `vault_dozzle_session_secret` is mounted as `/data/session_secret`. Without it each task generates its own key (Dozzle ≥ v11 persists a random one there instead of deriving it from `users.yml`), a session cookie from one task is rejected by the next, and the login page redirects in a loop. The image is pinned (`amir20/dozzle:v11.3.1`), not `latest`, so a redeploy can't pull in a behavior change like that one.

NocoDB (the `admin` stack, `admin.<domain>`, VPN only) creates its super admin on start from `NOCODB_ADMIN_EMAIL` and `NOCODB_ADMIN_PASSWORD` in `vault_stack_env` (`NC_ADMIN_EMAIL`/`NC_ADMIN_PASSWORD`; change both together, NocoDB starts only with a password of 8+ characters with an uppercase letter, a digit and a special character, which `make vault-update` generates). Telemetry is off (`NC_DISABLE_TELE`). The database is added by hand in the UI as an external MariaDB source at `monolith.database:3306` (on the `storage` network) with SSL turned on, since MariaDB refuses plaintext connections, one source per schema except `authorization`, which it can't read, logging in as the read-only `nocodb_reader`, plus one more `user` source logging in as `nocodb_writer` for publishing legal document versions, (password `vault_monolith_db_nocodb_password`, `make vault-view`), never the app's `monolith` user, whose edits would skip the application's rules and the outbox, which needs `NC_ALLOW_LOCAL_EXTERNAL_DBS=true`: NocoDB refuses sources on private addresses otherwise, and the overlay network is one.

Grafana provisions three dashboards (`deployment/prod/monitoring/grafana/dashboards/`, linked to each other at the top right; Application is the home page): **Application** (requests per second, 4xx/5xx share, p95 response time, a per-route table with average, p95 and slowest, the container's and JVM's memory, CPU, GC and threads, MariaDB and Valkey, and the monolith's warnings and errors with stack traces), **Infrastructure** (CPU, memory, disk and network per node; per swarm service its containers, memory against its limit, CPU and the containers started in the last hour, which grows during a crash loop; the backups, see Backups) and **Logs** (every service's logs, filtered by stack, service, level and a regex). The data sources have fixed uids (`prometheus`, `loki`) the dashboards refer to; `datasources.yml` deletes and recreates the Prometheus one on every start because Grafana refuses to change the uid of an existing data source ("data source not found"), which the old uid-less one was. Each dashboard file is its own swarm config (`grafana_dashboard_<name>-v<n>`), so a changed dashboard needs its name bumped; edits made in the UI are lost when Grafana restarts, so export the JSON into the file instead.

## Backups

The `backup` stack (`deployment/prod/backup`) keeps 30 days of point-in-time recovery for the five schemas in `/srv/backups/bookk` on the node labelled `backup: "true"` (`manager-1`), a different machine from the database. Its two services run `backup.sh` from the pinned `mariadb:11.8.3-ubi9` image (which ships `mariadb-binlog`, `mariadb-dump`, `zstd` and GnuPG, so there is no image of our own) on the `storage` network, logging in over TLS as the database user `backup` (`vault_monolith_db_backup_password`, created by `users-init.sql.j2` next to `exporter`). It holds `SELECT, SHOW VIEW, TRIGGER` on the five schemas and the four key schemas (`<svc>_short_retention`) and `REPLICATION SLAVE, BINLOG MONITOR, RELOAD` globally, `RELOAD` only because `FLUSH BINARY LOGS` requires it (`BINLOG ADMIN` doesn't cover it).

- **`binlog`** streams the database's binary log as it is written (`mariadb-binlog --read-from-remote-server --raw --stop-never`) into a 256M tmpfs, closes the file every 5 minutes when something was written (`FLUSH BINARY LOGS`), and stores each closed file as `binlog/binlog.NNNNNN.zst.gpg`. A restore therefore loses at most the last 5 minutes. The open file stays in memory, so nothing unencrypted reaches a disk. After a restart the service continues with the file after the last one stored, which the database still has: it keeps its binlogs for 2 days (`binlog_expire_logs_seconds` in `db/tuning.cnf`, next to `log_bin = binlog`, which keeps the file names stable across containers).
- **`dump`** writes `dump/dump-<UTC time>.sql.zst.gpg`, one `mariadb-dump --single-transaction --master-data=2` of all five schemas consistent with a single binlog position, saved next to it as `.position`. It dumps when the stack starts without a dump, then every night at 03:00 UTC, retrying every 10 minutes after a failure. Afterwards it deletes the dumps older than 30 days and the binlogs older than the oldest remaining dump's position.
- **Keys:** the same service dumps the four key schemas every 5 minutes into `keys/keys-<UTC time>.sql.zst.gpg` and deletes key dumps older than 7 days, always keeping the newest. The per-person keys are the only thing in those schemas, and the database leaves them out of its binlog (`binlog_ignore_db` in `db/tuning.cnf`) as the nightly dump does: the privacy texts promise that an erased person's data can't be read from any backup 7 days after the erasure, which holds because their key is gone from every key dump by then, while the encrypted data stays in the 30-day backups. A restore therefore takes the newest key dump and loses the keys created after it (at most 5 minutes). Each erasure also writes the person's id into its service's `shredded_subject` table, which is binlogged, and a restore destroys every key listed there again, so a key dump taken before an erasure never brings that person's key back. `make fetch-backups` leaves `keys/` on the server: a copy on a laptop would outlive the 7 days. The restore streams the newest key dump over SSH instead.

Every file is compressed with zstd and encrypted with GnuPG to the public key `deployment/prod/backup/backup-public-key.asc` before it is written. The private key is never on a server, in the vault or in CI (the vault is committed to the public repository, and CI holds its password), so a compromised server can delete backups but not read them. A file is written as `.partial` and renamed when complete, and an existing file is never overwritten. A database with 10,000 clients and a year of appointments dumps to about 45MB.

The services write `backup_dump.prom` and `backup_binlog.prom` into `/var/lib/node_exporter/textfile` on that node, which node-exporter reads through its `/rootfs` mount (`--collector.textfile.directory`). The dump service derives its metrics from the files on disk every 5 minutes and right after a dump, so they survive restarts: the newest and oldest dump's time, the number of dumps, and the bytes stored per kind (`bookk_backup_stored_bytes{kind="dump"|"binlog"}`). The Infrastructure dashboard's Backups row shows them: days backed up (the oldest dump's age, which grows to 30), bytes on disk, time since the last dump and since the binlog service was last in sync, and storage over time. `BackupDumpMissing` fires when no dump has succeeded for 27 hours, `BinlogShippingStalled` when the service hasn't been in sync with the database for 20 minutes, and `KeyBackupMissing` when no key dump has succeeded for 30 minutes (`bookk_backup_keys_last_success_timestamp_seconds`). `PersonalDataKeyMissing` fires when the app meets encrypted data whose key row doesn't exist at all, which only a restore that lost keys or a bug causes. Within the database's 2 days of binlogs, a fix loses nothing. After that, the service logs that the next binlog is gone, and restores can't replay across that gap until the next dump.

### The key

```sh
brew install gnupg pinentry-mac
echo "pinentry-program $(brew --prefix)/bin/pinentry-mac" >> ~/.gnupg/gpg-agent.conf && gpgconf --kill gpg-agent
gpg --quick-generate-key 'bookk backups' future-default default never           # asks for a passphrase
gpg --armor --export 'bookk backups' > ../prod/backup/backup-public-key.asc
gpg --armor --export-secret-keys 'bookk backups'                                 # save the output and the passphrase in your password manager
```

Commit the public key. Keep a second copy of the private key offline (printed, or on a USB stick): without it every backup is unreadable. `make infra tags=backup` refuses to deploy without the public key file, or with a private key in its place. To replace the key, export the new public key over the file, bump `backup-public-key-v<n>` in `backup-compose.yml`, and keep the old private key until the last file encrypted with it is 30 days old.

### Setting it up

1. Create the key pair and commit the public key.
2. `make vault-update` adds `vault_monolith_db_backup_password`.
3. `make infra tags=swarm` labels `manager-1` with `backup: "true"`.
4. `make deploy v=<the running version>` turns on binary logging and creates the `backup` user (`monolith-mariadb-tuning-v3`, `monolith-mariadb-users-init-v2`). The database restarts once (`stop-first`), so the app has no database for about a minute.
5. `make bootstrap tags=backup` creates the directories and the stack. The first dump runs right away.
6. `make infra tags=monitoring` turns on the textfile collector and the two alerts (`prometheus_alerts_cfg-v8`).
7. `make fetch-backups && make restore-drill` checks that the backups decrypt and restore.

### Restore drill

`make fetch-backups` mirrors `/srv/backups/bookk` into the gitignored `deployment/ansible/backups/` with rsync over SSH, without `keys/` (and deleting any local copy of it). It deletes what the server pruned, so the copy never keeps data past the 30 days. `make restore-drill` (`scripts/backup-restore.sh drill`, optionally `until='YYYY-MM-DD HH:MM:SS'` in UTC) picks the newest dump at or before that time. It refuses to continue if a binlog after the dump is missing. When none is stored yet, it restores the dump alone and says so. That's normal right after the stack starts, or while the database is idle after the nightly dump, because the binlog the dump continues in is still open. Otherwise it decrypts the dump and binlogs on your machine, replays them into a throwaway MariaDB container, and prints every table's row count. It first streams the newest key dump from the backup node over SSH (`scripts/backup-keys-source.sh` finds it in the inventory) straight into the container, and prints the live and shredded keys per key schema, with the key dump's time: keys created after it are lost in a restore. The decrypted data lives only in the containers' memory and is removed with them: the database's data directory is a tmpfs, not the Docker volume the `mariadb` image would otherwise create on the disk of Docker's VM. If the script is killed before it cleans up (`kill -9`, a crash), the containers `bookk-restore-drill-<pid>` and `bookk-restore-helper-<pid>` keep running with the data in memory, still without a volume. Remove them with `docker rm -f $(docker ps -aq --filter name=bookk-restore)`. Run the drill monthly: it is the only check that the private key still opens the backups. The restore was verified locally by restoring both to the latest point and to a moment between two batches of writes, with every table's `CHECKSUM TABLE` matching the source each time, including after the binlog service was killed mid-stream.

### Migration rehearsal

Run it before deploying a version with new migrations: `make fetch-backups && make migration-rehearsal` from the checkout of that version (`scripts/backup-restore.sh rehearse`, optionally `until=…`). It restores the backup like the drill, then runs Flyway (`flyway/flyway:13.1.0-alpine`, the same version and settings as `createDatabase`) with this checkout's migrations on each of the five schemas, and prints every table whose row count changed: `new` for a created table, `dropped` for a removed one, both counts otherwise. A failing migration stops it with the schema's name and exit status 1. Every count it prints must have changed on purpose: a migration that deletes rows it shouldn't shows up here, one that only rewrites values doesn't. The rehearsal and its Flyway error output stay in the throwaway containers and your terminal.

### A migration failed in prod

The new version doesn't start, and the deploy rolls back to the old one, which keeps serving: it starts with only a warning about the failed future migration. The failed script's earlier statements stay applied (MariaDB can't roll back DDL), and the schema history holds the version with `success = 0`, which every later start of the new version refuses.

1. Fix the script so it can run again on the half-migrated schema (the idempotent statements in the root `AGENTS.md`), and check it with `make migration-rehearsal`.
2. Remove the failed row. On the worker: `docker exec -it $(docker ps -qf label=com.docker.swarm.service.name=monolith_database) sh -c 'mariadb -uroot -p"$MARIADB_ROOT_PASSWORD"'`, then `DELETE FROM <schema>.flyway_schema_history WHERE success = 0;`. That is what `flyway repair` does for a failed migration.
3. Deploy the fixed version. Its start runs the script from the first statement again.

Restore a backup only when the failed script destroyed data. A migration that fails without losing anything needs only these three steps.

### Checking and fixing the schema history

To see where each schema stands, run in the database client from step 2 above: `SELECT version, success, installed_on FROM <schema>.flyway_schema_history ORDER BY installed_rank;`. A failed migration shows `success = 0`, and the steps above fix it.

A start that fails with `Migration checksum mismatch` means a released script was edited, which the root `AGENTS.md` forbids. Put the released text back (`git checkout monolith/<version> -- <script>`) and release again. Don't run `flyway repair` to accept the edit: the database keeps what the old text did, and the running version, whose files still hold the old text, could no longer start.

### Restoring prod

Prefer restoring to the latest point (no `--until`): it replays every account and client deletion. Every restore loads the newest key dump first and ends by destroying again every key listed in the restored `shredded_subject` tables (with `--until`, the latest point's), so nobody erased after the key dump gets their key back. Data restored to a point before a client merge loses the merged duplicate's details, because the duplicate's key was destroyed by the merge. Restoring to an earlier point undoes the deletions made after it, and the restore puts them back on the app's to-do list by itself. Every account and client deletion writes a record in the same transaction (`authorization.erased_account`, `business.erased_client`, kept 60 days). With `--until`, the tool first restores the latest point in a throwaway container, reads all those records, and appends them to the restore as `INSERT IGNORE … reapply_requested = TRUE`. A record the restored database already holds is skipped, because it exists exactly when its deletion was restored too. At its next start the app's `auth-reapplyErasures` and `business-reapplyErasures` jobs delete those accounts and clients again and send the usual `UserDeleted`/`ClientDeleted` events, which every other service erases as the first time. The employees of the businesses involved get the cancellation notices a second time.

Finding the records needs the binlogs up to the latest point. When they can't be replayed, the tool stops. `--without-erasures` restores without them. The deletions made after T are then known only from the database's own binlogs, if its volume survived (see below): find them in a drill of those binlogs and insert their records with `reapply_requested = TRUE` by hand before step 7.

1. `make fetch-backups`, then `make restore-drill until='YYYY-MM-DD HH:MM:SS'` to see what the restore will give. It ends with how many deleted accounts and clients the restore brings back, which the app deletes again.
2. Stop everything that writes: `docker --context swarm-manager service scale monolith_monolith=0 backup_binlog=0 backup_dump=0`.
3. If the database volume still exists, drop the five schemas in it, but keep the four `<svc>_short_retention` key schemas: they hold every key up to now, newer than any key dump, so restore with `--without-keys` in step 4. Drop them too only when they are damaged. On the worker, open a client with `docker exec -it $(docker ps -qf label=com.docker.swarm.service.name=monolith_database) sh -c 'mariadb -uroot -p"$MARIADB_ROOT_PASSWORD"'`, then run `DROP DATABASE` for each schema. A new, empty volume already has the schemas from `init-schemas.sh`.
4. Stream the restore into the database. The decrypted SQL goes through the SSH connection only and never touches a disk:
   ```sh
   scripts/backup-restore.sh sql backups --keys-from "$(scripts/backup-keys-source.sh)" [--until 'YYYY-MM-DD HH:MM:SS'] | ssh root@<worker> "docker exec -i \$(docker ps -qf label=com.docker.swarm.service.name=monolith_database) sh -c 'mariadb --binary-mode -uroot -p\"\$MARIADB_ROOT_PASSWORD\"'"
   ```
   Replace `--keys-from …` with `--without-keys` when step 3 kept the key schemas. With `--until` it logs how many deletion records and shredded keys it appended. Without a key dump and without surviving key schemas every encrypted field reads as empty, and only the people themselves can enter their data again.
5. Empty Valkey. Everything in it expires within an hour, so nothing is lost, but its markers would make the app skip events the restore undid (an outbox event still waiting at T but handled afterwards counts as already handled for an hour), and a retried request could get a stored answer for work the restore undid. `FLUSHALL` is renamed away, so delete every key on the worker, with `vault_monolith_redis_password` from `make vault-view`:
   ```sh
   read -rs REDISCLI_AUTH && export REDISCLI_AUTH
   docker exec -e REDISCLI_AUTH $(docker ps -qf label=com.docker.swarm.service.name=monolith_redis) sh -c 'valkey-cli --scan | xargs -r -n 500 valkey-cli del; valkey-cli DBSIZE'
   unset REDISCLI_AUTH
   ```
   It prints `0` at the end.
6. On the manager, move the old backups aside before backing up again: `mv /srv/backups/bookk /srv/backups/bookk-before-<date>`. The old binlog chain doesn't continue from the restored database, and a database on a new volume numbers its binlogs from `binlog.000001` again. `backup.sh` would refuse to overwrite those names and stop. Delete its `keys/` 7 days later and the rest 30 days later. Then `make infra tags=backup` recreates the directory and redeploys the stack, which brings both backup services back. The dump service finds no dump and takes one right away, the start of the new chain.
7. Start the app: `docker --context swarm-manager service scale monolith_monolith=1`. Right at start, `auth-reapplyErasures` and `business-reapplyErasures` delete again what the restore brought back. Check that nothing is left: `SELECT COUNT(*) FROM authorization.erased_account WHERE reapply_requested` and the same for `business.erased_client`, both `0`.

If the database's volume survived but the backup was behind, the database's own binlogs (`/var/lib/mysql/binlog.*`, kept 2 days) still hold the last minutes. Copy them out before dropping anything.

## Prometheus login

Prometheus asks for HTTP basic auth on every endpoint, its own `/metrics`, the API and `/-/reload` included, on top of nginx's VPN-only `prometheus.<domain>`. The user is `admin`, the password `vault_swarm_secrets.prometheus_password` (`make vault-view`). Two swarm secrets carry it, both generated by `import-secrets.py`: `prometheus_password` (the plain password, read by Prometheus's self-scrape as `password_file` and by Grafana's provisioned datasource as `$__file{/run/secrets/prometheus_password}`) and `prometheus_web_config` (the `--web.config.file`, holding its bcrypt hash). `make vault-update` generates the pair when the password is missing, and derives the hash from the stored password when only the hash is missing, so the two always match. The secrets are created by the `swarm` tag, so the first rollout is `make infra tags=swarm,monitoring`. Changing the password follows the manual secret rotation: delete both values from the vault and run `make vault-update`, then on the manager `docker stack rm monitoring` (its volumes stay) and `docker secret rm prometheus_password prometheus_web_config` (swarm refuses to remove a secret in use), and rerun `make infra tags=swarm,monitoring`.

## Swarm configs and secrets from files are immutable

Stacks that mount a config or secret from a file (nginx, vpn, monitoring, orchestrator, monolith, backup) version its name by hand (`nginx-cert-wait-v2`, `monolith-mariadb-init-schemas-v1`). nginx's configuration and well-known files are bind mounts instead, so they need no new name and are reloaded rather than restarted. Changing such a file without bumping the name fails the deploy with "only updates to Labels are allowed" — same as with `docker stack deploy` directly.

## From CI

GitHub Actions only publishes images and calls this playbook; it never runs `docker` against the swarm itself.

- `.github/workflows/monolith-publish.yml` runs on a `monolith/<version>` tag: it checks the tag equals `version` in the root `build.gradle.kts`, pushes `ghcr.io/nocturneproperties/bookkme-server:<version>`, then calls the deploy workflow.
- `.github/workflows/microservice-publish.yml` runs on an `auth/`, `user/`, `business/`, `appointment/` or `notification/<version>` tag and only publishes `ghcr.io/nocturneproperties/bookkme-<service>:<version>` (same version check); nothing deploys microservices while prod runs the monolith.
- `.github/workflows/deploy.yml` runs `ansible-playbook playbooks/deploy.yml -e version=<version>` on a GitHub-hosted runner. Run it by hand (**Actions → Deploy monolith → Run workflow**) to redeploy or roll back to any published version.

Every workflow runs on GitHub-hosted runners pinned to `ubuntu-24.04` (`ubuntu-latest` moves to a new Ubuntu on GitHub's schedule); nothing runs inside the swarm. The deploy job therefore reaches the manager over SSH from GitHub's address ranges, which change, so the manager's SSH port must accept connections from the internet (key-only root login) at the `vault_hosts['manager-1']` address. The job installs Ansible with `uv`, pinned to the same versions as a local Homebrew install: ansible-core 2.21.5, community.docker 5.4.0, community.general 13.5.0. It pulls with the registry token from the vault, not `GITHUB_TOKEN`: the deploy passes `--with-registry-auth`, which stores the credentials in the swarm service for later pulls, and `GITHUB_TOKEN` expires when the job ends.

GitHub setup the workflows need:
- Secrets `ANSIBLE_VAULT_PASSWORD` (new), `SSH_PRIVATE_KEY`, `SSH_KNOWN_HOSTS` and `GRADLE_ENCRYPTION_KEY` (already used by the old workflows).
- An environment `production` (**Settings → Environments**) with yourself as required reviewer, so every deploy waits for an approval. Without protection rules GitHub creates it on first use and deploys without asking.

`make infra` / `make bootstrap` are not wired into CI: infrastructure changes are rare and reviewed by hand, so run them from your machine.
