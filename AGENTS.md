# bookk-server — Agent Playbook

Modular monolith split into Ktor microservices. Kotlin + Ktor (CIO) + Koin DI + Exposed ORM + kotlinx ProtoBuf serialization + MockK/JUnit5 tests. Follow the recipes below verbatim; they mirror the real code (reference implementation: `service/appointments`, the newest service).

## Module map

```
core/                    shared infra: domain Result/Error types, service (Ktor server, auth, respondWith), data (Exposed, event streaming, cache)
library/                 money, idempotency, permissions, validation
service/<svc>/
  domain/api/            operation interfaces + entities + <Svc>ErrorCodes   (package com.bookk.<svc>.domain.api.{operation,entity})
  domain/impl/           <Operation>Impl + di/DI.kt + tests                  (package com.bookk.<svc>.domain.impl.{operation,di})
  data/source/           datasource INTERFACES                               (package com.bookk.<svc>.domain.datasource)
  data/                  datasource impls, orm tables/entities, migration, di
  microservice/          route/<Svc>Routing.kt (typed Resources), route/api/*Route.kt, <Svc>Microservice.kt main, route tests
  client/                cross-service events/API
```

New gradle modules must be registered in `settings.gradle.kts` (one `include` per submodule, grouped per service). Convention plugins (`libs.plugins.bookk.microservice`, `bookk.domain.impl`, `bookk.domain.api`, `bookk.data`, …) already add Ktor/Koin/MockK/kotlin-test deps and JUnit platform — do not re-add them. **Declare each dependency once per build file**: IntelliJ warns `Dependency … is declared multiple times` for the same dependency in two configurations. `testImplementation` already inherits `implementation`, and `applyTestFixturesConvention()` (`build-src/.../convention/TestFixturesConvention.kt`, called by every convention plugin) makes `testFixturesImplementation` inherit it too, so neither repeats a main dependency. A main dependency whose types the fixtures hand to other modules' tests, or that appears in the main module's public API (a supertype, a public constructor parameter, a return type), is `api`, never `implementation` plus `testFixturesApi` (`core/data/eventstreaming/impl`: `KafkaTestBroker.drain` returns Kafka `ConsumerRecord`s). Fixtures of fixtures go through `testFixturesApi(testFixtures(…))` when the module's own tests need them as well (`core/service`). A module that needs only Kotlin applies `libs.plugins.bookk.kotlin`, never bare `libs.plugins.kotlin.jvm`, so it gets the same toolchain and opt-ins.

**Formatting is the official Kotlin code style, enforced by ktlint through Spotless.** `kotlin.code.style=official` (`gradle.properties`) sets IntelliJ's formatter, and `.editorconfig` runs ktlint (version `ktlint` in `gradle/libs.versions.toml`) with `ktlint_code_style = intellij_idea`, the ktlint style that agrees with that formatter, so IntelliJ's Reformat Code and ktlint don't fight (`ktlint_official` would). Spotless is configured once in the root `build.gradle.kts` over every `*.kt` and `*.gradle.kts` in the repository, build-src included. Run `./gradlew spotlessApply` after changing code; CI runs `spotlessCheck` before building and fails on any unformatted file. ktlint adds trailing commas to every multi-line argument and parameter list. Rules turned off in `.editorconfig`, each for a reason: `kdoc`, because the openApi plugin reads route KDoc inside `authenticate { }` blocks, which ktlint forbids; `class-signature`, because it wraps a single supertype constructor call onto its own line after the colon (`class X :` / `    BusinessError(`), which the official conventions don't ask for: keep `class X : BusinessError(` on one line; `package-name` only for the existing `build_src` and `delete_account` packages (a new package has no underscore). Line length is not enforced (`intellij_idea` leaves `max_line_length` off). A file holding one class is named after it (`filename` rule). Never silence a rule with `@Suppress("ktlint:…")` in source; a rule that doesn't fit the project is disabled in `.editorconfig` with its reason here.

**Opt-ins live only in `build-src/.../convention/KotlinConvention.kt`; never write `@OptIn` in source.** Stdlib markers (`ExperimentalUuidApi`, `ExperimentalTime`) are enabled everywhere. A library's marker is listed with its `group:module` and enabled per compilation only when that module is on the compilation's resolved compile classpath (`-jvm` suffix stripped). Enabling a marker unconditionally makes every module without that library warn `Opt-in requirement marker … is unresolved`, and a module on bare `kotlin.jvm` got no opt-ins at all, so it warned `This declaration needs opt-in`. A new experimental API is a new entry in that map, not an annotation. The classpath check reads module ids from the dependency graph (`incoming.resolutionResult.rootComponent`), never from `incoming.artifacts.resolvedArtifacts`: artifact results carry the task dependencies of other modules' jars, so their provider can't be queried before those tasks run. A Gradle compile never noticed, but IntelliJ's sync runs no tasks, and the Kotlin plugin's lenient argument import swallowed the failure and imported an empty `optIn`, so the IDE flagged every opt-in, stdlib markers included, while Gradle compiled cleanly.

**Write database migrations by hand.** This is now Claude's job, not the user's. There is no generator — earlier attempts at diffing the ORM table definitions with `MigrationUtils`/Flyway produced migration scripts that silently corrupted schema changes involving composite indices (a dropped column still referenced by a named unique index never got its `DROP INDEX`, and MariaDB rejected the result), so that tooling was removed rather than trusted. When an ORM table changes (new column, new index, new table, etc.), write the SQL directly into a new `service/<svc>/data/src/main/resources/db/migration/<schema>/V<n>__migration_script.sql`, where `<n>` is one past the highest `V<n>` already in that directory. Reflect exactly what changed in the table definition: column adds/drops/type changes, index adds/drops, constraint changes — and drop a named composite index yourself before dropping any column it covers, MariaDB will not infer that. Verify the new script applies cleanly before considering the change done: bring up a MariaDB instance reachable at `127.0.0.1:3308` (`deployment/dev/environment-compose.yml` if one isn't already running), then actually run Flyway against it through all migrations for that schema up to and including the new file and confirm it succeeds — never hand-wave this step or ship a script that hasn't been executed against a real database.
**Keep the database ER diagrams current.** `docs/database/` documents every microservice's schema as a Mermaid ER diagram in its own file (`docs/database/<svc>.md`, indexed from `docs/database/README.md`), plus `docs/database/cross-service-overview.md` for logical (non-FK) references. Any change to an ORM table — new/removed table, column, or relationship — must update that service's diagram (and the cross-service overview, if a logical reference changed) in the same change.
**Keep the operation activity diagrams current.** `docs/operations/` holds one Mermaid flowchart per HTTP route that mutates state, plus one per asynchronous reaction to a cross-service Kafka event (an `EventHandler`'s `registerResultReceiver` block — file named `on-<event>.md`, e.g. `on-user-deleted.md`), indexed in `docs/operations/README.md` and cross-linked from each route's KDoc via a `See: docs/operations/<svc>/<file>.md` line (an unrecognized KDoc field — the openApi plugin ignores it, verified by compiling). Any new mutating route or event handler, or a change to an existing one's permission checks/error cases/event publication/event handling, must add or update its diagram in the same change. Diagram nodes should carry the actual datasource calls, error codes and event names so the flow is understandable without opening the code. Whenever an operation sends a cross-service event, its diagram ends with a `**Consumed by:**` line linking forward to every reaction diagram for that event, and each reaction diagram links back to its producer(s) — keep both directions in sync, and mirror any addition/removal in `docs/operations/README.md`'s "Cross-service event map" table.
**Deployment lives in `deployment/AGENTS.md`** (prod topology, database and cache networking, Swarm restart policy, memory sizing, monitoring, Ansible stacks, VPN and nginx, the dev environment and rollout scripts), loaded automatically through `deployment/CLAUDE.md` when you read a file under `deployment/`. Prod runs the monolith, not the five microservices, and has no Kafka. Read that file before a code change that prod depends on, even outside `deployment/`: database connection, TLS, retry or pool settings (`createDatabase`, `APPLICATION_DB_*`), cache TTLs (Valkey is sized from `PROCESSED_TTL` and the idempotency response TTL), metric names and labels (alerts and dashboards query them), the log format (Alloy reads the logback level), environment variables, ports, and service hostnames.

**CI and image publishing.** The monolith image (`ghcr.io/nocturneproperties/bookkme-server:<version>`) is published by pushing a `monolith/<version>` tag (`.github/workflows/monolith-publish.yml`); the workflow fails unless the tag equals `version` in the root `build.gradle.kts`, because Jib tags the image with the project version, not the git tag, and then calls `.github/workflows/deploy.yml`, which only runs `ansible-playbook playbooks/deploy.yml` (also runnable by hand with a version, for rollbacks). A successful `Publish monolith` run (published and deployed) triggers `.github/workflows/project-mark-released.yml` (adapted from the client repo's): it moves this repository's issues from `Done` to `Released` on the `bookkme-board` project (org project 1, shared with `bookkme-client`, so it filters on `content.repository`) and comments the tag on each, with the `PROJECT_TOKEN` secret for the project and `github.token` for the comments; a hand rollback through `deploy.yml` doesn't trigger it, a missed run can be dispatched with the tag. `workflow_run` fires only from the workflow file on the default branch (`main`), so it does nothing until merged there. `Build and test` (`push-build-and-test.yml`) runs only on pushes to `develop` and pull requests into `develop`, like the client repo: the `develop` → `main` release PR and its merge commit run nothing (they used to build and test the same code twice more), and the tag's publish workflow builds the image. Microservice images are still published, never deployed: an `auth/`, `user/`, `business/`, `appointment/` or `notification/<version>` tag runs `.github/workflows/microservice-publish.yml` (one workflow, the prefix picks the Gradle module, same version check). Every workflow runs on GitHub-hosted runners pinned to `ubuntu-24.04` (not `ubuntu-latest`, which moves to a new Ubuntu on GitHub's schedule; the repository is public, so they are free; there is no self-hosted runner stack any more), so the deploy job reaches the manager over SSH from the internet. Workflows never run `docker` against the swarm themselves, and never run the infra playbook (run it by hand). The deploy job installs Ansible with `uv`, pinned to the versions of a local Homebrew install, and it must pull with the registry token from the vault, not `GITHUB_TOKEN`: `--with-registry-auth` stores the credentials in the service for later pulls, and `GITHUB_TOKEN` expires with the job. Image tasks need `--no-configuration-cache`: Jib's task holds a `Project` reference the configuration cache cannot serialize.
**Every third-party image is pinned to an exact version, in dev, prod and Testcontainers alike** (`valkey/valkey:8.1.11-alpine`, not `8.1-alpine` or `latest`). A floating tag moves on its own: prod ran `nocodb/nocodb:latest`, and the next admin stack deploy would have upgraded NocoDB the day upstream published a release. An image with no version tags is pinned by digest instead (`strm/dnsmasq:latest@sha256:…`, last pushed in 2020; wg-easy is pinned the same way). To pin something already running in prod without upgrading it, read the resolved digest from `docker --context swarm-manager service inspect <stack>_<service> --format '{{.Spec.TaskTemplate.ContainerSpec.Image}}'` and look that digest up in the repository's tags on Docker Hub. Changing only the tag (same digest) still counts as a spec change for Swarm, which restarts the service on the next deploy. Our own Jib images in `deployment/dev` (`bookkme-*:latest`) are exempt, since the rollout scripts build them right before starting them.
**A change to the Android app's signing certificates must update the passkey relying party too.** `deployment/prod/nginx/static/android_well_known.json` (served as Digital Asset Links from a read-only bind mount, picked up by the next `make infra tags=nginx` without a config name to bump) lists the certificates' SHA-256 fingerprints, and WebAuthn checks the same certificates again as `android:apk-key-hash:<hash>` origins in `createRelyingParty` (`service/authorization/domain/impl/.../passkey/RelyingPartyFactory.kt`). Each hash is its fingerprint's raw bytes in unpadded base64url (`echo <fingerprint> | tr -d ':' | xxd -r -p | base64 | tr '+/' '-_' | tr -d '='`). Updating only the well-known file makes the app's passkey registration and sign-in fail the origin check (missed in `c9b2aa5c`). Keep both lists in sync in the same change, and bump the version, since the origins are code.
**Ignore all git operations.** Managing Git is the responsibility of the developer, do not automatically commit, push or merge
**Bump the version after every code change.** The single project version lives in the root `build.gradle.kts` (`version = "X.Y.Z"`, inherited by every module via `rootProject.version`). After changing code, bump it per semantic versioning according to the kind of change: **MAJOR** for a backwards-incompatible change (removed/renamed route, field or `@ProtoNumber`; changed wire type; changed meaning of an existing field or error code; a migration that breaks older service instances), **MINOR** for a backwards-compatible feature (new route, operation, event, entity field or error case, new allowed behavior or new rejection rule), **PATCH** for a backwards-compatible fix, refactor or internal change with no API/behavior addition. A higher part resets the lower ones (`0.3.5` → `0.4.0`, `1.2.3` → `2.0.0`). **While the version is `0.x`, a backwards-incompatible change bumps MINOR, not MAJOR** — removing or renaming a route, field or `@ProtoNumber` is allowed freely and counts the same as a new feature (`0.12.0` → `0.13.0`). A release does not move the version to `1.0.0`: the first public release shipped as `0.15.7` (`RELEASE_NOTES.md`), and the project moves to `1.0.0` only when the developer decides to; the MAJOR rule applies from then on. Measure against the last released version, the newest `monolith/<version>` tag (`git tag -l 'monolith/*' --sort=-v:refname | head -1`), not the last commit or the working tree: everything since that release gets exactly one bump, at the level of its most significant change. If the current version is already above the release at that level or higher, leave it, even when the bump was committed earlier on the branch; if it is above it at a lower level (e.g. a patch bump, then a feature is added), raise it to the correct level from the released version. Docs-only or test-only changes do not bump the version. **Keep `RELEASE_NOTES.md` current in the same change.** Its top entry is the unreleased version (the one in `build.gradle.kts`, above the newest `monolith/<version>` tag) and grows with every change since that release: what changed for clients and operators, new error codes, migrations and anything that can stop a deploy, and the upgrade steps. When the version bump raises its level (a patch entry, then a feature), rename the entry to the new version and rewrite its summary line; never start a second unreleased entry.
**The monolith (`src/main/kotlin/com/bookk/server/MonolithServer.kt`) uses `EmbeddedEventConsumer`/`EmbeddedEventProducer`, never Kafka.** Each service has two module builders: `xModule()` (e.g. `authModule()`, `appointmentsModule()`) includes `eventStreamingTransportModule(Scope, SERVICE_NAME)` (Kafka) and is what the standalone microservice starts with, while `xEmbeddedModule()` includes `embeddedEventStreamingTransportModule(Scope, SERVICE_NAME)` (both from `core/data/eventstreaming/impl/.../di/DI.kt`). A service that sends events also includes `outboxModule(Scope)` in both, which binds its `StandardEventProducer` and `OutboxRelay` (see the outbox rule below); notifications sends none and has neither. `MonolithServer.diModules()` lists every service's `xEmbeddedModule()`, plus one `topicQueueHolderModule()` providing a single root-level `TopicQueueHolder<String>` singleton shared by all five scopes. `TopicQueueHolder` is pub/sub, not a point-to-point queue: `subscribe(topic)` hands each caller its own `Channel`, and `publish(event)` fans the event out to every subscriber of that topic — this matters because several services' `EventHandler`s register receivers for the same topic (e.g. `AuthEvent.UserDeleted` is consumed by user, business, appointments and notifications), so a single shared `Channel` per topic would let only one of them win the event. When adding a new service to the monolith, register it the same way: give it an `xEmbeddedModule()` with `embeddedEventStreamingTransportModule(NewScope, NEW_SERVICE_NAME)` (plus `outboxModule(NewScope)` if it sends events) and add that to `diModules()`, no other wiring needed. The service name is not optional: it becomes the consumer group the idempotency storage keys on, and two services sharing one would skip each other's events.
**The monolith needs a single cross-schema DB user, unlike per-service deployments.** `createDatabase(schemaName, ...)` (`core/data/database/Migration.kt`) reads its host/port/user/password from `AppLevelConstants`, which is process-global (`System.getenv("APPLICATION_DB_*")`) — only `schemaName` varies per call. A standalone microservice gets one schema-scoped MariaDB user (`deployment/dev/db/init.sql` creates `user`/`authorization`/`business`/`appointments`/`notifications`, each granted only on its own database). The monolith runs all five services' `createDatabase` calls inside one process reading the same env vars, so it needs one MariaDB user granted on all five schemas — `init.sql` also creates a `monolith` user with `GRANT ALL PRIVILEGES` on each of the five databases. Root-cause a `FlywaySqlUnableToConnectToDbException` / `Access denied for user 'monolith'` in the monolith container before assuming a code bug: `init.sql` only runs on a MariaDB volume's *first* initialization, so a pre-existing dev `database_data` volume won't pick up a newly added user until the grants are applied by hand (`docker exec <db-container> mysql -h 127.0.0.1 -P 3307 -u root -p'<MARIADB_ROOT_PASSWORD>' -e "..."`) or the volume is recreated. Flyway in `createDatabase` connects with the schema in the JDBC URL (`jdbc:<url>:<port>/<schema>?createDatabaseIfNotExist=true`), not a bare host: with no default schema, Flyway's MySQL support "restores" the connection after migrating by running `CREATE SCHEMA`/`USE`/`DROP SCHEMA` on a random UUID name, which every schema-scoped user is denied, logging `Access denied … to database '<uuid>'` + `Unable to restore connection to having no default schema` on each startup (`MigrationMariaDbTest`). `createDatabase` connects with `sslMode=verify-full` on both its Flyway and HikariCP URLs: MariaDB ≥ 11.4 generates a self-signed certificate, which Connector/J ≥ 3.4 verifies against the login password (zero-configuration TLS, only for `mysql_native_password`/`ed25519` users with a password; `MigrationMariaDbTest` covers a `REQUIRE SSL` user and the refusal of a certificate it can't verify), so there is no CA to manage. Flyway's migrate runs inside `retryWhileDatabaseUnreachable` (`ConnectRetry.kt`): while the database can't be reached at all (an `UnknownHostException`, `SocketException` or `SocketTimeoutException` anywhere in the cause chain), it waits 1, 2, 4, 8 s, then 10 s, about 3 minutes over 20 retries, logging `Database unreachable …` each time. Every other failure is thrown at once. Don't use Flyway's own `connectRetries` instead: it retries every `SQLException`, so a rejected login or an unverifiable certificate also waited 3 minutes before failing (`MigrationMariaDbTest`'s certificate test caught it). `MigrationMariaDbTest` opens the database's port only after `createDatabase` has started, through an in-process TCP proxy (`LateProxy`). Each test schema needs its own `src/test/resources/db/migration/<schema>/V1__…sql`, or Flyway finds no migrations and the schema stays empty. After migrating, `createDatabase` connects Exposed through one HikariCP pool per schema (`poolName` = schema, `maximumPoolSize` from `APPLICATION_DB_POOL_SIZE`, default 10, `isAutoCommit = false`, REPEATABLE READ), so the monolith holds 5 × pool size connections (keep that under MariaDB's `max_connections`, 151 by default; the pool keeps them all open while idle, so ~33% is the idle baseline). `poolConfig` pings idle connections every 5 minutes (`keepaliveTime`, HikariCP's own default is off): anything between the app and the database that drops idle TCP flows (a swarm virtual IP after 15 minutes) must see traffic before it does (`PoolConfigTest`) and a transaction no longer opens its own connection. Hikari resets isolation and autocommit when a connection is returned (a READ COMMITTED `OutboxRelay` batch doesn't leak, `MigrationMariaDbTest` pins it), but not session variables: a `SET SESSION …` stays on that pooled connection for whatever borrows it next, so production code must never set one, and a test that does (`innodb_lock_wait_timeout = 1`) affects later transactions on the same `Database`. The root project itself carries the `bookk.microservice` convention plugin (`build.gradle.kts` applies it directly, not `.apply(false)`), so `./gradlew publishImageToLocalRegistry` with no module path builds and tags the monolith image as `bookkme-server:latest` (and `:<version>`) straight from the repo root, no subproject prefix needed.

## Core conventions (apply everywhere)

- **Never write comments.** No `//` comments, no KDoc, no explanatory blocks — in production code or tests. Express intent through names and structure instead: rename the function, extract the condition into a named value, split the method. If something seems to need a comment, that is a signal the code should be clearer. The only exceptions are the route KDoc the openApi plugin parses (`Summary:`, `Body:`, `Response:`, …) and comments that already exist in the file — never delete or reword someone else's comment.
- Operations return `Result<T>`; impls **throw** errors inside `transactionManager.transaction { }`, which catches and converts to `Result.failure`.
- Domain errors: nested `sealed interface Error` in the operation interface; each case is a `class` extending `BusinessError(statusCode, code, message)` (classes, NOT data objects). Assert with `is`, never equality. Exception: appointment status-transition errors are shared, not per operation — `AppointmentStatusError` (`AlreadyCancelled`, `AlreadyCompleted`, `MarkedNoShow`, `NotStarted`, `EditWindowClosed`, next to the `Appointment` entity) is thrown by the entity's own guards `Appointment.requireScheduled()` / `requireCompletable(now)` / `requireNoShowMarkable(now)`. An operation that changes an appointment's status calls the matching guard on the row it read with `getForUpdate` instead of re-declaring these cases in its own `Error`. Appointment requests follow the same pattern: `AppointmentRequest.requirePending()` throws the shared `AppointmentRequestStatusError` (`AlreadyApproved`, `AlreadyDeclined`), used by both decline and approval (a sealed interface's subclasses must live in its own package, so the entity cannot throw an operation's nested error).
- Error codes live in `domain/api/.../<Svc>ErrorCodes` as `BASE + n`. Blocks: auth=0, user=100000, business=200000, appointments=300000, notifications=400000. Next service takes the next 100000 block. Service-independent codes live in `core/domain/.../CoreErrorCodes` (block 900000, e.g. `TRANSACTION_CONFLICT`).
- Generic infrastructure errors: `com.bookk.core.domain.entity.Error` (`NotFound`, `OperationNotAllowed`, …).
- `call.respondWith(result)` (core/service) maps: success Unit→204, success T→200, `BusinessError`→its statusCode + `SimpleServerError(errorCode, message)`, `Error.NotFound`/`Error.OperationNotAllowed`→**404** (intentional: permission failures do NOT return 403), `Error.TransactionConflict`→**409** + `SimpleServerError(CoreErrorCodes.TRANSACTION_CONFLICT, …)`, anything else→500 (logged).
- Permissions: fine-grained per-resource grants (`library.permissions.ResourcePermission(view, update, delete)`, three independent booleans with no defaults — always pass all three, no ranking between them) — `businessPermissionDataSource.getPermission(userId, businessId, BusinessResource.CLIENTS).assert(PermissionAction.UPDATE)` (business) or `appointmentPermissionDataSource.getPermission(userId, businessId).assert(PermissionAction.VIEW)` (appointments, single implicit resource) — throws `Error.OperationNotAllowed`. A caller acting on their own assigned resource (e.g. an employee's own appointment) can pass an `update`/`delete` check on a `view`-only grant via `.assertOrSelf(action, actorId, assigneeId)`. An employee's suspension (`Employee.suspendedAt`) is enforced inside `BusinessPermissionDataSource.getPermission`, which throws `library.permissions.EmployeeAccessSuspended` (403, `BUSINESS_EMPLOYEE_ACCESS_SUSPENDED`) for a suspended caller (`getViewer`/`getViewers` just report `NONE` permissions and a null `employeeId`); appointments mirrors it via the `suspended` flag on `EmployeePermissionsChanged` and `appointment_permission_grants.suspended`, throwing the same `library.permissions.EmployeeAccessSuspended`, so a new permission-gated operation gets it for free — list that 403 in its route KDoc — only paths with no permission gate (client booking via `GetAppointmentBookingContext`) must check `employee.isSuspended` themselves, and anything publishing `EmployeePermissionsChanged` must set `suspended = employee.isSuspended` alongside the stored `permissions`. See `docs/object-permissions.md` for the full model, including how a `Business`/`AppointmentSettings` entity gets the requesting user's grants attached (`Business.viewedBy(businessPermissionDataSource.getViewer(...))` / `.copy(permissions = ...)`, computed per request, never persisted on the row). A list operation resolves its caller-specific fields with one batched lookup over every id (`getViewers(userId, businessIds)`), never one datasource call per row.
- Name/email/phone/currency format checks: `library.validation.{NameValidator,EmailValidator,PhoneValidator,CurrencyValidator}.isValid(value, ...)` (library/validation, plain `bookk.domain.api` module, no domain dependency — only joda-money, for `CurrencyValidator`) — pure `Boolean` predicates, each with a default `maxLength`/`minLength` you can override per call site; the caller still owns throwing its own `*ValidationError`. Reuse these instead of hand-rolling a regex/length check in a new operation.
- Wire format is ProtoBuf (`application/x-protobuf`) for all bodies/responses. **A nullable collection (`List<T>?`, `Map<K, V>?`) cannot be serialized when null** — kotlinx throws `'null' is not supported as the value of collection types in ProtoBuf`. For an optional group of fields in a partial-update DTO, wrap them in a nullable `@Serializable` holder class (a nullable message is fine) instead of making each list nullable — see `BusinessUpdateModel.schedule: Schedule?`. **A nullable property must not also have a default** — the serializer runs with `encodeDefaults = true`, and encoding a defaulted null throws `'null' is not supported for optional properties in ProtoBuf` as soon as a caller omits it. Give every nullable field on a partial-update DTO no default at all and pass them explicitly (`BusinessUpdateModel`, `UserEditModel`). **Never use a `Map` keyed by an enum as a request body field** (e.g. `Map<BusinessResource, ResourcePermission>`): the openApi plugin renders it as bare `additionalProperties` with no key list, and on the ProtoBuf wire the keys are unannotated enum ordinals, so the valid keys are documented nowhere. Give the DTO one nullable field per enum value with its own `@ProtoNumber` and convert to a map in the DTO (`EmployeePermissionsRequest.grants()`).
- Entities: `@Serializable data class` in `domain/api/.../entity` with a `companion object { fun stub(...) }` factory (defaulted params, `Uuid.random()`, `Instant.fromEpochMilliseconds(0)`) — add `stub()` to every new entity; tests rely on it.
- **Every amount inside one business is in the business currency.** Joda `Money.plus` throws `CurrencyMismatchException` on mixed currencies, and every total here is a plain `reduce { acc, price -> acc + price }` (`IssueQuoteImpl`, `Appointment.totalAmount`, `AppointmentRequest.totalAmount`), so a mixed-currency business turns quoting and booking into 500s. Hence: `CreateService`/`UpdateService` re-denominate the client's price into the business currency (`Money.inCurrencyOrNull`, `service/business/domain/impl/.../operation/service/BusinessCurrencyPricing.kt`; an amount with more decimals than the currency allows is `PricePrecisionInvalid`, not rounded), and `UpdateBusiness` rejects a currency change once `ServiceDataSource.hasServices` is true (`CurrencyLocked`; re-sending the stored code is always a no-op). Both sides go through `BusinessDataSource.lockBusiness(id, RowLock)`, which locks the business row and returns its currency: service writes take `RowLock.SHARED` (they don't block each other), a currency change takes `RowLock.EXCLUSIVE`, each as the transaction's first statement (see the lock-first rule below). A stored code `CurrencyValidator` rejects (legacy rows such as `usd`) doesn't lock, so the owner can still fix it, and service writes reject it with `BusinessCurrencyInvalid` instead of a 500. A new write that stores a price on a business entity must take the same lock and never trust the currency the client sends.
- **Never accept another service's identity/pricing data as free text from the client.** A snapshot field sourced from another service's data (an employee's name, a client's contact info, a service's price/duration, …) must be resolved server-side via a synchronous internal client call at write time (`BusinessClient`-style, see `service/business/client` + the `Api.Internal.*` routes it calls) — the wire DTO the client submits carries only the foreign id(s), never the name/price/etc. it claims. - **Every ProtoBuf wire type carries an explicit `@ProtoNumber` on every serialized field** — request/response DTOs, entities, events, and enum entries (`@ProtoNumber(n) ENTRY`, which replaces the implicit ordinal). Without one, kotlinx numbers a field by declaration order (index + 1; ordinal for enums), so inserting or reordering silently renumbers the wire. That includes an event's body property `override val topic: String = TOPIC`, which is serialized after every constructor parameter — annotate it on the line above (`@ProtoNumber(n)\n override val topic`). A new field takes the next unused number with a default; never reuse or change an existing one. JSON-only types (`Jwk`/`JwkSet`, the idempotency cache records) are exempt.

- **Use `runSuspendCatching { }` (`com.bookk.core.domain.entity`), never `runCatching { }`, around any block that suspends.** `runCatching` catches `CancellationException` too, so a cancelled coroutine turns into a `Result.failure` and keeps running. A DLT consumer then retries a cancelled handler, and `ExposedTransactionManager` turns cancellation into `Error.UnknownError`. `runSuspendCatching` rethrows cancellation and catches everything else. It is `inline`, so `return` / `return@runSuspendCatching` work as they did. Plain `runCatching` is still fine for purely blocking code (parsing, decoding, a blocking SDK call), since nothing in it can be cancelled. The same goes for `recoverCatching` around a suspending transform: use `recoverSuspendCatching { }` (the `Error.kt` helpers `onConstraintFailure`/`onPermissionsMissing`/… are built on it). A hand-written `catch (e: Exception)`/`catch (e: Throwable)` around suspending code needs a `catch (e: CancellationException) { throw e }` before it (`JobRunner`, `CleanUpWorker`, `IdempotencyPlugin`). Where the catch-all should still handle the block's *own* `withTimeout` (`DataSource.mapExceptions` maps a query timeout to `Error.UnknownError`) or should keep a consumer loop alive after a stray cancellation, use `runCatchingUnlessCancelled { }` (next to `runSuspendCatching`): it catches everything and rethrows only when the calling coroutine itself was cancelled (`currentCoroutineContext().ensureActive()`). `EmbeddedEventConsumer.dispatch` needs it: with `runSuspendCatching`, a stray cancellation ends that topic's flow inside `merge()`. The sibling topics keep running, so the dead topic goes unnoticed, and its events wait in the unlimited channel forever (`EmbeddedDltRetryTest` pins it for a DLT topic). A hand-written catch-all with `ensureActive()` first is the same thing, where a `finally` is needed too (`DataSource.mapExceptions`). To undo something when a block fails or is cancelled (release a reserved token, discard a Redis `MULTI`), use `runCleaningUpOnFailure(cleanUp = { … }) { block }` (`com.bookk.core.domain.entity`, next to `runSuspendCatching`) instead of a hand-written `try`/`catch (Throwable)` + `withContext(NonCancellable)`: it runs the clean-up under `NonCancellable`, so it can still suspend after the caller was cancelled, and always rethrows the block's own failure, attaching a failed clean-up as suppressed instead of letting it replace that failure (`RunCleaningUpOnFailureTest`). It has to wrap the block: a `Result`-style `onFailure` after `runSuspendCatching` never sees a cancellation, so a cancelled call would keep the token spent. `mockTransaction()` rethrows cancellation like `ExposedTransactionManager` does. A cancellation test must assert `is CancellationException`, not `assertSame`: coroutines' stack-trace recovery re-creates the exception when it crosses a context switch (`suspendTransaction`).

- **Single-use tokens are claimed with one atomic `CacheClient.setIfAbsent` (Redis `SET NX EX`), never a `get` check followed by a later `set`.** The two-step version lets concurrent requests with the same token both pass. Reserve before doing the work, keep the reservation on success, and release it (`delete`, best effort) on any failure, wrapping the work in `runCleaningUpOnFailure(cleanUp = { release… }) { … }`, so a rejected call doesn't burn the token (`CreateAppointmentRequestImpl` + `AppointmentRequestDataSource.reserveOfferToken`/`releaseOfferToken`). `InMemoryCacheClient` implements `setIfAbsent`, so datasource tests cover it.
- **Event consumers deduplicate per consumer group with an atomic claim, never a read-only "was it processed?" check.** `KafkaEventConsumer` and `EmbeddedEventConsumer` both run every receiver through `IdempotentDelivery` (`core/data/eventstreaming/impl`), backed by `CacheEventIdempotencyStorage` (`core/data/repository`, bound in `commonModule()`): `claim` is one `setIfAbsent` on `event:<consumerGroup>:<topic>:<idempotencyKey>` (1-min claim, `EventIdempotencyStorage.claimTtl`; a key that vanishes between the `SET NX` and the read is claimed again, not reported in progress), a successful handler then `markProcessed` (kept 1 hour, `PROCESSED_TTL`: every redelivery path — DLT retries, the `IN_PROGRESS` wait, an outbox batch republished after a crash or deploy, a Kafka rebalance — arrives within minutes; a Kafka consumer that stays down longer than that with processed-but-uncommitted offsets would handle those events again, and so does a hand replay of `exhausted_event`, which is meant to; it was 24 hours, which made the markers the bulk of Valkey's memory), and a failed or cancelled one `release`s the claim (under `NonCancellable`) before the DLT retry, so the retry can claim it again. Every `deliver` call claims and releases under its own random `deliveryId`, stored in the claim record, and `release` is a compare-and-delete on it (`CacheClient.deleteIfEquals`: a Lua `GET`-compare-`DEL` on Redis, `computeIfPresent` in `InMemoryCacheClient`): a handler that outlived its claim must not free the claim of the delivery that took over, or wipe the processed marker it left, which let a third delivery handle the event again (`IdempotentDeliveryTest` reproduces it in virtual time via `inMemoryEventIdempotencyStorage(testTimeSource)`; `InMemoryCacheClient(timeSource = …)` drives Caffeine's expiry from a `TestTimeSource`/`testTimeSource`, so TTL tests never wait; like Valkey's `SET … EX`, every `set` replaces the key's expiration (`Expiry.writing`) and a `deleteIfEquals` that doesn't match leaves it untouched (`InMemoryCacheClientTest`) — with `Expiry.creating` the processed marker silently kept the claim's 1-minute TTL, so marker-lifetime tests passed for the wrong reason). A cancellation the handler throws itself (a `withTimeout` inside it) is an ordinary failure and retried; only the consumer's own cancellation (`ensureActive()`) stops the delivery. `IN_PROGRESS` (another delivery holds the claim, or a crashed one left it) is waited out: `IdempotentDelivery` re-claims every second for up to `claimTtl`, so a crashed delivery's event is handled once its claim expires instead of being parked. A parked event is deleted 30 days after it was parked (`ExhaustedEventReplayerImpl.DEFAULT_RETENTION`, `deleteParkedBefore` on every tick), since its payload can hold personal data. Until then it is replayed by `ExhaustedEventReplayer` (`docs/exhausted-events.md`): every start marks all parked rows `replay_requested`, and a 1-minute loop locks requested rows (READ COMMITTED, like `OutboxRelay`), hands each to `Consumer.replay` — which publishes it to that consumer group's own DLT topic with attempt 0 and a new random key, so no other group sees it and a re-failure parks a new row instead of hitting the old row's unique key — then deletes the replayed rows and clears the request on rows the consumer refuses (no receiver, undecodable, embedded consumer not started), so a poison row can't loop. It also exports `events_exhausted{consumer_group, topic}` (the `MeterRegistry` from `startServer`, bound in Koin by `meterRegistryModule`), which drives the `EventsExhausted` alert. `startEventHandling` starts every scope's `EventHandler`s before any replayer: an embedded publish to a topic nobody has subscribed to yet is silently dropped. Only a claim still held after the TTL, or a failed claim, goes through the DLT; a failed `markProcessed` is only logged, since the handler already succeeded. A handler must therefore finish within `claimTtl`. `deliver` returns `DeliveryOutcome` (`HANDLED` / `SKIPPED_DUPLICATE`) so logs tell a skipped duplicate from a processed event. DLT topics are per consumer group (`DltRetry.dltTopic(topic, consumerGroup)` = `<topic>_<consumerGroup>_dlt`): with one shared `<topic>_dlt`, every group subscribed to it and re-ran every other group's failures, multiplying retries (7 attempts instead of 3 with two failing groups). Two things this replaced, both silent event loss: the old `isEventProcessed` was the HTTP `getResponseOrLock`, which *writes* an in-progress lock on a miss and was never released, so every DLT retry saw it and skipped the event; and the key was `topic:idempotencyKey` with no consumer group while every service shares one Redis (`redis_local`, no key prefix), so of the four `AuthEvent.UserDeleted` consumers only the first to check handled it. The consumer group is part of the key, not the instance: replicas of one service share it, which is what makes a rebalance redelivery a duplicate. Test consumers with `inMemoryEventIdempotencyStorage()` (`testFixtures(projects.core.data.eventstreaming.impl)`, the real storage on `InMemoryCacheClient`), never a hand-written fake: the old `RecordingIdempotencyStorage` fake had no lock side effect, which is why every DLT test passed while production lost the events.
- **`RedisCacheClient` must return every borrowed connection to the pool:** `withPooledConnection { }` is `borrowObject().use { }`. If the action fails it sends `DISCARD` (through `runCleaningUpOnFailure`) before the connection goes back to the pool. - **`transactionManager.transaction { }` may run its block up to 3 times.** `core/data/map/Mapper.kt` maps MariaDB's write conflicts to `Error.TransactionConflict`: error 1020 "Record has changed since last read" (`innodb_snapshot_isolation=ON`, the default since 11.6) and deadlocks (1213 / SQLState `40001`), found anywhere in the cause chain. `ExposedTransactionManager` re-runs the whole block in a fresh transaction, with a fresh snapshot, up to `MAX_ATTEMPTS_ON_CONFLICT` (3) times with a short jittered backoff, and only then returns the conflict, which `respondWith` turns into a 409. Only the outermost call retries. A nested `transaction { }` (e.g. `CreateAppointmentRequestImpl` → `createAppointment`) makes a single attempt and passes the conflict up: re-running an inner block inside an outer transaction that already failed would be wrong. The manager tracks this with its own coroutine-context marker, not Exposed internals. It also sets `maxAttempts = 1` on every Exposed transaction: Exposed's built-in retry would otherwise re-run a block 3 times on *any* raw `SQLException`, including a constraint violation flushed at commit, and stack on top of this retry. Consequence for every operation: a block must be safe to re-run. Database writes are, since they roll back. Anything else in the block repeats on retry: a cross-service call is made again (harmless for the reads they are today). Don't add new non-database side effects inside a transaction block. `eventProducer.send` is not one: it is a database write (see the outbox rule below), so only the attempt that commits leaves an event. Tests: `ExposedTransactionManagerTest` (H2) for retry/give-up/nesting, and `BusinessRowLockMariaDbTest` for a real 1020 (two updates of one service row) and a real deadlock (two transactions locking two business rows in opposite order), both recovering through the retry.
- **Every event goes through the transactional outbox, so `eventProducer.send` must run inside `transactionManager.transaction { }`.** In every service scope `StandardEventProducer` is `OutboxEventProducer`: it stores the encoded event in the service's own `outbox_event` table within the caller's transaction, and `OutboxRelay` publishes committed rows afterwards (`docs/transactional-outbox.md`). A rollback or conflict retry discards the row together with the write, so an event exists exactly when its write committed. A `send` outside a transaction throws `IllegalStateException` (checked with `transactionManager.isInTransaction()`) and the event is lost, so a compensating send after a failed transaction needs a transaction of its own (`FinishRegistrationImpl`'s `onFailure`). A service that starts sending events needs an `outbox_event` migration (the same SQL as `business/V15`), the table in its ER diagram, and `outboxModule(Scope)` in both module builders. - **A client's phone and email are each unique per business, across detached and integrated clients alike** (`client_business_id_phone_unique`, `client_business_id_email_unique`; the email index compares case-insensitively under `utf8mb4_uca1400_ai_ci`, so in-memory dedup lowercases). - **An appointment's `client_id` (`ClientSnapshot.id`) is the business's client row id, never a user id; the users on it are separate columns.** Integrated and detached clients alike get a random `client.id`, so matching it against a user id (`client_id = userId`) silently matches nothing: account deletion never cleared a user's details from appointments that way. Every appointment and request carries two users: `initiator_user_id` (`initiatorUserId`) is who booked, and `client_user_id` (`client.userId`, nullable) is the client's own account, resolved server-side (the booking context's client row, never the request body or the caller: on an instant appointment the caller is the employee) and cleared on erasure. Account deletion is handled inside appointments on `AuthEvent.UserDeleted` by `client_user_id` (`DeleteUserAppointmentData`): it cancels the user's upcoming scheduled appointments in both roles first, in one locking read (`client_user_id = ? OR employee_user_id = ?`, both indexed; a second locking read after the first one's plain read of the services could fail with 1020): as client with reason "User deleted their account", telling each one's employee through `AppointmentEvent.CancelledForDeletedClient` (no client name, it is sent after the erasure), as employee with "Employee deleted their account", telling a client with an account through `AppointmentEvent.Cancelled` (a stopgap until #137 reassigns them). So business announces it with one event, `BusinessEvent.ClientLinked(businessId, clientId, userId, mergedClientIds)`: the kept row, its account, and the duplicates deleted into it (booking takeover, or profile sync). Moving and linking stay in one event on purpose: as two events on separate topics they could arrive in either order and leave moved rows without the account. This event and `UserDeleted` have no relative order, so `LinkClientUser` reads `deleted_user` first under a shared lock and runs the erasure for the rows it just linked when the account is gone. The lock makes a link and a deletion wait for each other in either order (`DeletedUserLockMariaDbTest`). `markDeleted` is an `INSERT IGNORE`, never an upsert: an upsert takes an exclusive lock on an existing row, so two links for an already-deleted user, each holding the shared lock, deadlocked, and it overwrote the first deletion time. A new booking path must check both tombstones.

Account deletion deletes requests where the user is the client or the employee, and keeps the ones they only booked for someone else with `initiator_user_id` set to `Uuid.NIL`.
- **A client is kept only while they are active within the business's retention period.** The business is the controller of its clients' data and sets the period as a business setting, `business.client_data_retention_months` (12 to 120, default 36, `UpdateBusiness`). `client.last_activity_at` is set when a client row is created, edited or taken over, and moved forward (never back) to each booked visit's end by `RecordClientVisit`, fed by `AppointmentEvent.ClientVisitBooked`. A new appointments write that books or moves a slot must send that event in its transaction, or the business may delete a client with an upcoming appointment. The daily `business-deleteInactiveClients` job (`DeleteInactiveClients`, one `READ_COMMITTED` transaction per business, so it takes no gap locks that hold up new clients, `ClientRetentionMariaDbTest`) deletes the rows older than the cutoff and sends `BusinessEvent.ClientDeleted` for each, the same erasure as `DeleteClient`. Client deletion (`anonymizeClient`) and account deletion (`anonymizeClientUser`) erase the same appointment fields through one helper, `eraseClientDetails` in `AppointmentDataSourceImpl`: client name (placeholder), phone, email, `client_user_id` and the optional `note`; the cancellation reason and the price adjustment reason stay as the business's record (developer's decision). A new appointment column that holds client data goes into that helper. Every status guard (`requireScheduled` / `requireCompletable` / `requireNoShowMarkable`) also refuses an appointment that ended more than `Appointment.EDIT_WINDOW` (7 days) ago with `AppointmentStatusError.EditWindowClosed` (`APPOINTMENT_EDIT_WINDOW_CLOSED`), and a new operation that changes an appointment calls one of them.
- **Appointment/request double-booking is guarded by a lock, not a unique index.** Every write that books a slot (`CreateAppointment`, `UpdateAppointment`, `CreateAppointmentRequest`) first takes `AppointmentSettingsDataSource.getForUpdate(businessId)`, which serializes them per business, then runs `hasOverlapsWith` (active statuses only). Don't put a unique index on `(user_id, business_id, date_start)` or similar slot columns: it also counts cancelled/declined rows, so rebooking a freed slot fails with a 500 (that index existed until `V7` for exactly this reason). A new booking path must take the same settings lock before its overlap check.
- **A write addressed by a child id must be scoped to the business the permission check ran against.** The permission check passes on the `businessId` the caller supplies (path or body), so a datasource update/delete that matches only `WHERE id = ?` lets anyone with a grant in their own business reach another business's row by id. Put `business_id = ?` in the same `WHERE` (`ServiceDataSourceImpl.editService`, `deleteService`, `deleteServiceGroup`), and never write `businessId` from the request in an update's `set` block. Resolve a referenced child the same way, with a scoped read, and store and return what the server found, not the object the client sent (`getServiceGroup` in `CreateService`/`UpdateService`).
- **An Exposed FK column accessed through `val x by Table.column` on a DAO entity is typed `EntityID<Uuid>`, not `Uuid`.** Comparing it with `==` against a plain `Uuid` (e.g. `it.businessId == someUuid` after a `findById(id)`) always evaluates to `false` — the types never match structurally — silently making a scoping check useless instead of failing loudly. Unwrap with `.value` first (`it.businessId.value == someUuid`), or push the comparison into the Exposed DSL instead (`Table.businessId eq someUuid` inside `find { }`), which handles the conversion correctly.

### Writes live on the entity, not in the datasource

Rules that fall out of this:
- **Never call `flush()` or `refresh()`.** Exposed flushes its entity cache before executing any statement, so a staged insert/update is always written before the next query or DSL statement observes it. Every such call added during this codebase's history turned out to be dead — `refresh()` is worse than dead, it re-reads the row and discards pending writes, which then needs a `flush()` before it to compensate.
- Business-rule guards (status transitions, "has the appointment started", …) belong in the **operation**, not the datasource: the operation's **first** read of the row is a locking one (`getForUpdate`, `SELECT … FOR UPDATE`), it checks and throws its own domain errors, then calls an unconditional datasource write (`markCompletedByUser`, `markNoShow`). The lock is held for the rest of `transactionManager.transaction { }`, so no concurrent write slips in between. The locking read must come first: Exposed's `EntityClass.wrap` returns the entity already in the transaction's cache and ignores the freshly selected row, so a plain `get(id)` followed by `getForUpdate(id)`/`findByIdAndUpdate(id)` in the same transaction takes the lock but still sees the values read **before** it (verified against exposed-dao 1.3.1 sources).
- **Take a row lock as the transaction's first statement, before any plain read — including the permission lookup.** MariaDB runs at REPEATABLE READ (nothing in `core` overrides it), and InnoDB fixes a transaction's snapshot at its *first* plain read. Lock first and the snapshot is taken after the lock is granted, so every later plain read sees what the previous holder committed. Read first (e.g. `getPermission`) and then lock, and two things go wrong. A later plain read still sees the old snapshot and misses rows committed while you waited, so two concurrent invitation creations could both take the last slot. Making that read a locking read doesn't rescue it either: MariaDB ≥ 11.6 ships `innodb_snapshot_isolation=ON`, so a locking read that meets a row changed after the snapshot fails with error 1020 "Record has changed since last read" (a 500). Whether that happens depends on the query plan: `hasServices` escaped only because its `LIMIT 1` was answered from the `business_id` index. So: lock first, then plain reads (`CreateEmployeeInvitationImpl`, `UpdateBusinessImpl` when `currencyCode` is sent, `CreateServiceImpl`/`UpdateServiceImpl`, `DeleteServiceGroupImpl`; in appointments, approving a request locks the request, then the settings, then reads the permission, since an overlap check from a snapshot taken before the settings lock misses the booking it waited for), and pin the order with a `coVerifyOrder { lockBusiness(...); getPermission(...); … }` impl test. When an operation must call another service and must not hold a lock during that call, split it: check and resolve in a first short transaction and outside any transaction, then lock first in the writing transaction, compare the locked row with the one checked and answer `Error.TransactionConflict` (409) if it changed, and repeat the checks after the locks (`UpdateAppointmentImpl`). Return the mismatch out of the block and throw the conflict after it: a `TransactionConflict` thrown inside `transaction { }` makes `ExposedTransactionManager` re-run that same block three times for nothing. Keep any check that depends on the lock result (e.g. "the stored currency is unsupported") until after the permission check, so a caller without access learns nothing. `Query.forShare()` (`core/data/RowLocking.kt`) emits `LOCK IN SHARE MODE` on MariaDB and falls back to the stronger `FOR UPDATE` on H2, which has no shared row lock; use it for the lock itself, not for reads after a snapshot exists. H2 can't reproduce snapshot or lock-mode behavior, so test locking against a real MariaDB with `BusinessRowLockMariaDbTest` as the template: testcontainers `mariadb:11.8.3-ubi9`, schema from the real Flyway migrations via `createDatabase`, holder/waiter interleavings ordered with `CompletableDeferred` plus polling `information_schema.INNODB_TRX` for `trx_state = 'LOCK WAIT'` — **more slowly than every 100ms** (`SLOWER_THAN_INNODB_TRX_CACHE_REFRESH`): InnoDB serves `INNODB_TRX` from a cache it refreshes only after 100ms *without reads*, so a 10ms poll that first reads just before the waiter blocks keeps getting the stale snapshot forever (this was the 'flaky under load' timeout of `BusinessRowLockMariaDbTest` and `OutboxRelayMariaDbTest`), and `SET SESSION innodb_lock_wait_timeout = 1` to make "would block" fail fast. Two more traps in such tests. Every test in the class shares one container, so rows earlier tests left behind change which gaps a scan locks (and can change the plan): a "does it block?" test passed or failed depending on test order until `ClientRetentionMariaDbTest` (business) emptied the tables in a `@BeforeEach` (a blocking `transaction(db = database) { … }`, not `runBlocking`). Give the waiting side its own single-connection pool (a second `createDatabase(…, maxPoolSize = 1)`; Flyway does nothing the second time), so its `SET SESSION innodb_lock_wait_timeout = 1` never reaches a connection another transaction borrows: resetting it in a `finally` runs before commit, where Exposed still flushes pending inserts that would then wait the default 50 seconds. And wrap the waiter's whole `suspendTransaction` in `runSuspendCatching`, not just the call inside it: when a DAO insert times out inside the block, Exposed still flushes the pending child inserts at commit, outside an inner catch, so the test fails on a foreign key error instead of reporting the lock wait. Assert the lock wait itself (a `SQLException` with `errorCode == 1205` in the cause chain), not just `isFailure`, and pair a "doesn't block at READ COMMITTED" test with a "blocks at REPEATABLE READ" one, so the first can't pass because the scenario never locked anything.
- Return `Unit` from datasource writes unless a caller branches on the result. A `Boolean` that only tests assert on is dead API; assert the guard through the stored state instead.
- Read a row back with `findById(...)?.toDomain()`, not a hand-rolled `selectAll().where { }` + `wrapRow`. Do not re-read after a write either — `new(...)` and `findByIdAndUpdate(...)` return the entity, so `.toDomain()` on it is enough.
- Entity referrers lazy-load one query per parent, so a read returning **many** rows needs `.with(Entity::children)` to batch them. Today's reads are all effectively single-row (`BusinessTable.userId` is a `uniqueIndex`, so a user owns at most one business), so plain referrers are correct — revisit if that changes.
- Rows that belong to an entity should reach it through a real FK so they are a DAO referrer (`val grants by XEntity referrersOn Table.ownerId`, eager-loaded with `.with(...)`), not through a manual join. Exposed's `referrersOn` follows exactly one FK column's `referee` — a logical link over several columns (e.g. grants keyed by `(user_id, business_id)`) cannot be a referrer, so add the owner's id column (`business_permission_grants.employee_id`, backfilled by a join in the migration) instead. Reference: `EmployeeEntity.grants`.
- A request DTO that replaces a whole entity as a PUT body (`EmployeeUpdateModel` for `Employee`) should reuse the entity's `@ProtoNumber`s for the fields it keeps, so older clients still sending the full entity decode cleanly — the extra fields are simply ignored.
- **Race-safe get-or-create** (e.g. resolving a foreign identity's local row by an id it doesn't yet know, provisioning it on first use): back it with a DB-level unique index on the lookup key (composite `uniqueIndex(colA, colB)` in the table's `init { }` block is fine even when one column is nullable — MariaDB treats NULLs as distinct, so unrelated nullable rows don't collide), then in the datasource do find → insert, and on failure re-find before giving up. `onConstraintFailure { }` cannot be reused here since its recovery lambda returns `Nothing` (it is only for turning a race into a thrown domain error) — inside the same `dbQuery { }` block a driver exception hasn't been mapped yet either, so catch it with `runCatching` and classify it yourself via `throwable.toDomain() is Error.UniqueConstraintFailed` (`com.bookk.core.data.map.toDomain`) before re-querying. Reference: `ClientDataSourceImpl.getOrCreateIntegratedClient`.
6. Write the impl unit test (see Testing) — every `Error` case + success + event publication if any.

Fully qualified type names in brackets. ## Testing

Run: `./gradlew :service:<svc>:microservice:test` / `:service:<svc>:domain:impl:test` (append `--tests "com.bookk...ClassName"` to filter).

Keep Testcontainers at **1.21.4 or newer** (`testcontainers` in `gradle/libs.versions.toml`). Docker Engine 29, which GitHub's `ubuntu-24.04` runners ship, rejects API versions below 1.44. Older Testcontainers (1.20.4) negotiate 1.32, so every container test in CI fails in `@BeforeAll` as `initializationError` / `IllegalStateException` ("Could not find a valid Docker environment"). Hard rules (enforced by fixtures or review):
- NEVER `runBlocking`. Operation tests: `runUnitTest { }`; route tests: `routeTest { }` (both from core fixtures).
- `given()` / `whenn()` / `then()` markers are **required in every test** — `runUnitTest` asserts at runtime that all three were called; a test without them fails.
- Fresh SUT and fresh mocks per test — no sharing across tests, no class-level mocks.
- DO NOT EDIT `core/src/testFixtures/kotlin/com/bookk/core/test/Test.kt`.
- Test names: backticked sentences, e.g. `` fun `should return failure when request overlaps with existing appointment`() ``.
- Use entity `stub()` factories instead of hand-built instances; pass only the fields the test depends on. Provide real entity instances to mocks (ProtoBuf serialization NPEs otherwise). **Never write a local test-file helper function (`private fun createTestX()`, `makeX()`, …) that re-lists an entity's fields to construct it** — that duplicates the field list the entity's own `stub()` exists to own. The one exception is a partial-update DTO (`BusinessUpdateModel`, `ClientUpdateModel`, …) — those are request shapes, not domain entities, so they don't get a `stub()`; a local private helper (conventionally named `updateModel(...)`, defaulting every field to `null`) is the established pattern for building them in tests, e.g. `UpdateBusinessImplTest.updateModel()`.
- JUnit assertions (`org.junit.jupiter.api.Assertions`). Assert error types with `is`: `assertTrue(result.exceptionOrNull() is DoThing.Error.ThingExists)`.

### Development Workflow: Test-Driven Development

Always implement features using strict TDD. For every requested feature or change:

1. **Red** — Write a failing test first that captures the expected behavior. Do not write any implementation code before the test exists.
2. **Green** — Write the minimum implementation needed to make the test pass.
3. **Refactor** — Clean up the implementation and tests while keeping all tests green.

Rules:
- Never write production code without a failing test that requires it.
- Run the test suite after each step and confirm the expected pass/fail state before proceeding.
- Keep tests small and focused; one behavior per test.
- If a requirement is ambiguous, write the test that encodes your assumption and state it explicitly.

Assert the whole name → interval map, and per job both the invocation (with arguments) and that a `Result.failure` propagates — that is what catches a dropped `getOrThrow()`. A module's `testFixtures` source set can read that module's `internal` members (`runJob` reads `SchedulerConfiguration.jobs`), so a fixture never needs a production API widened just for tests. `MonolithJobsTest` (root project, `src/test`) covers the monolith's single shared scheduler: it asserts `registerMonolithJobs` registers exactly the union of each service's own `register<Svc>Jobs` (a cross-service name clash throws at registration, a service missing from the monolith shows up as a map mismatch), and that same-typed operations in different scopes (auth vs business `RotateSigningKeys`) resolve from their own scope — use the `startScopedApplication(AuthScope to { … }, BusinessScope to { … })` overload for several scopes at once. Every job name is `"$<SVC>_SERVICE_NAME-<jobName>"` (`auth-rotateSigningKeys`, `business-rotateSigningKeys`), so names can't clash in the monolith and a log line names its service. `MonolithJobsTest` fails on a job without its service's prefix, and a service that gets its first job must be added to that check.

## Datasource (H2 integration) test conventions

`createTestDatabase(vararg tables: Table)` in `core/data/src/testFixtures` creates a per-test H2 database in `MODE=MySQL`. Call datasource methods inside `suspendTransaction { fixture.sut.method() }` within `runUnitTest { }`. Use `dbQuery`-based methods inside `suspendTransaction {}`. Cache-based methods (those using `mapExceptions` without `dbQuery`) are called directly without wrapping.

### CacheClient in datasource tests

Use `InMemoryCacheClient` from `testFixtures(projects.core.data.cache.impl)` — do NOT use `mockk<CacheClient<String>>`. The relaxed mock returns a non-null mock for `get()` which fails the reified cast. Example fixture:
```kotlin
private class SutFixture {
    val db = createTestDatabase(...)
    val cacheClient = InMemoryCacheClient()
    val sut = MyDataSourceImpl(cacheClient)
}
```
See `PassKeyDataSourceImplTest` and `AppointmentRequestDataSourceImplTest` as reference.

### H2 dialect limitations — untestable operations

These throw `UnsupportedByDialectException` in H2 even with `MODE=MySQL`. Omit their tests and leave a comment in the test file:

| Operation | Used by | Workaround for reads |
|---|---|---|
| `updateReturning` | — | rewrite as `update {}` + a follow-up `selectAll()` read, which H2 supports and makes the method testable (`BusinessDataSourceImpl.updateBusiness` was converted this way) |
| `deleteReturning` | `BusinessDataSourceImpl.deleteUserBusinesses`, `DeviceDataSourceImpl.deleteInactiveDevices` | — |
| `upsertReturning` | `NotificationSettingsDataSourceImpl.upsert(settings)` | insert via DAO entity directly |
| `upsert(where = …)` | — | split into `insert`/`update` datasource methods and let the operation choose (`NotificationTargetDataSourceImpl` + `UpdateTargetInformation`) |

For read methods whose writes use an unsupported upsert, insert test data directly via the DAO entity (e.g. `NotificationSettingsEntity.new(id) { ... }`).

Plain `upsert {}` (no `where` parameter) **is** supported by H2 and resolves conflicts via `uniqueIndex` columns — use it freely in datasource tests. Passing `where` to it throws `UnsupportedByDialectException`. Split a conditional upsert into separate `insert`/`update` datasource methods — the guard lives in the `update {}` where clause and returns whether a row matched — and let the operation decide, inside its `transactionManager.transaction { }`, whether to insert.

### Asserting unique-constraint violations

`runUnitTest` cannot be nested inside `assertThrows` (its body is `suspend`, and the outer `TestHolder` context would be lost). Assert constraint failures with `runCatching` instead:
```kotlin
whenn()
val result = runCatching { suspendTransaction { fixture.sut.createX(duplicate) } }

then()
assertTrue(result.exceptionOrNull() is Error.UniqueConstraintFailed)
```
`dbQuery { }` maps the driver exception to `com.bookk.core.domain.entity.Error.UniqueConstraintFailed`, which operations turn into a domain error via `.onConstraintFailure { }`.

A DAO entity **update** (`findByIdAndUpdate`, setting a property on a found entity) is only flushed at the next statement or at commit, after `dbQuery { }` has returned, so its constraint violation is the raw driver exception, not `Error.UniqueConstraintFailed`. In production `ExposedTransactionManager` maps it with `toDomain()`, so `.onConstraintFailure { }` on the operation still works; in an H2 datasource test assert `result.exceptionOrNull()?.toDomain() is Error.UniqueConstraintFailed` (`UserDataSourceImplTest`).

A DAO insert (`XEntity.new { }`) is flushed as a JDBC **batch**, so the driver reports a duplicate as `java.sql.BatchUpdateException`, not `SQLIntegrityConstraintViolationException` — verified on `mariadb-java-client` 3.4.1 (SQLState `23000`, and its cause is another `BatchUpdateException`) and on H2 (`23505`). `core/data/map/Mapper.kt`'s `toDomain()` therefore classifies by SQLState class `23` as well as by exception type; narrowing it back to an `instanceof` check turns every duplicate DAO insert into `Error.DatabaseError` (500) and silently disables `.onConstraintFailure { }` (`DataSourceConstraintMappingTest` covers both the single-row and batch paths). A "does it already exist?" check followed by an insert is never enough on its own: back it with a unique index and map the race with `.onConstraintFailure { }` to the same domain error the check throws (`JoinBusinessImpl` + `employee_business_id_user_id_unique`).

### Batch-update / batch-cancel patterns

`markCompleted(before: Instant)` and `cancelOutdated(before: Instant)` update rows where `dateEnd < before`. Test the happy path by creating entities at `Instant.fromEpochMilliseconds(0)` (epoch → well in the past) and calling with `Clock.System.now()`. Test the boundary by creating entities at `Clock.System.now() + 24.hours` and verifying they are NOT affected.

### Cleanup methods (deleteDayOffsInThePast)

Insert `DayOffRange(LocalDate(2020,1,1), LocalDate(2020,1,2))` for a past day-off and `DayOffRange(LocalDate(2099,12,30), LocalDate(2099,12,31))` for a future one. After calling `deleteDayOffsInThePast()` re-read via `sut.get(businessId)` and assert counts.

### Never use `advanceUntilIdle()` to drive work running on `backgroundScope` — use `advanceTimeBy` + `runCurrent`

This bit twice before the real cause was found, so: **`TestScope.advanceUntilIdle()` deliberately does not fully drain `backgroundScope`.** Straight from the `kotlinx-coroutines-test` KDoc on `TestScope.backgroundScope` — "The coroutines in this scope are run as usual when using `advanceTimeBy` and `runCurrent`. `advanceUntilIdle`, on the other hand, will stop advancing the virtual time once only the coroutines in this scope are left unprocessed." This is intentional (it's what lets a `backgroundScope` job that loops forever not hang `advanceUntilIdle()`), not a bug — but every `EmbeddedEventConsumer` test here runs the consumer via `consumer.start(backgroundScope)`, so `advanceUntilIdle()` is the wrong tool for **any** of them, not just multi-round DLT retry chains: it previously looked like it worked (a plain single-hop `send()` → `advanceUntilIdle()` → assert delivered) purely by timing coincidence, and stopped working the moment something upstream changed (see `EmbeddedEventStreamingTest`, which predates this whole feature and still hit it).

The fix, per that same KDoc: drive time with `runCurrent()` (runs whatever is due at the current virtual instant — nothing more) and `advanceTimeBy(duration)` (moves the clock forward, running scheduled tasks in the meantime) instead. Two things to know about these:
- `advanceTimeBy(duration)` does **not** run tasks scheduled for exactly `currentTime + duration` — always follow it with a `runCurrent()` to catch anything sitting exactly on that boundary.
- `runCurrent()` alone will not run a task scheduled via `delay()` for a future virtual time — only `advanceTimeBy`/`advanceUntilIdle` actually move the clock, so a chain with real backoff needs the clock advanced past each `delay()`, not just `runCurrent()` in a loop.

Pattern used across `EmbeddedDltRetryTest`/`EmbeddedEventStreamingTest`: for a delay-free single hop, `runCurrent()` alone is enough. For a chain with backoff (DLT retries), advance a single generous virtual duration (see `advanceThroughRetries()`: `runCurrent(); advanceTimeBy(1.hours); runCurrent()`) — virtual time is free, so there's no cost to advancing far more than the scenario actually needs, and it reliably sweeps through however many delay-then-reschedule rounds occur without having to compute exact cumulative backoff by hand.

### `runUnitTest`'s timeout is real time, not virtual

`runUnitTest` passes its 30-second budget as `runTest(context, timeout = 30.seconds) { ... }` (`core/src/testFixtures/.../Test.kt`), not a manual `withTimeout()` nested inside the test body. `runTest`'s own `timeout` parameter is a real-wall-clock watchdog against a hung test (it runs on the outer `runBlocking` dispatcher, outside the `TestCoroutineScheduler`) — it does not count virtual time advanced via `advanceTimeBy()`/`advanceUntilIdle()`. So a DLT retry test can freely use the production `DltRetry.DEFAULT_MAX_ATTEMPTS` and uncapped `backoffMillis` even though cumulative simulated backoff reaches many seconds or more — advancing that much virtual time costs no measurable real time.

Because the budget is real time, it also has to cover a test JVM's cold start, which the first test in each module pays: loading MockK and ByteBuddy, creating the first H2 database and starting Exposed, Ktor's test engine, Koin, the ProtoBuf serializers. Locally that is 0.75s to 4.2s (`CommunicationDataSourceImplTest`). On a GitHub runner shared by parallel Gradle test JVMs and the Testcontainers suites it went past the old 5-second budget, and CI failed a different module's first test each run with `UncompletedCoroutinesError` ("the test body did not run to completion") while every test passed locally. A Linux container capped at `--cpus=0.25` reproduces it. That is why the budget is 30 seconds, and `routeTest` runs on `runUnitTest` like everything else. Don't lower it to catch slow tests: the first test's time measures the JVM, not the test. For the same reason, keep real cryptography out of unit tests. RSA-2048 key generation is a random prime search with a long tail. `GetActiveSigningKeyImpl` and `RotateSigningKeysImpl` take a `SigningKeyPairGenerator` (bound in `signingModule` to `RsaSigningKeyFactory::generate`, scoped because every service scope loads the module), and their tests stub it. A test that only passes keys through uses `SigningKey.stub()`.
