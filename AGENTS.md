# bookk-server — Agent Playbook

Modular monolith split into Ktor microservices. Kotlin + Ktor (CIO) + Koin DI + Exposed ORM + kotlinx ProtoBuf serialization + MockK/JUnit5 tests. Follow the recipes below verbatim; they mirror the real code (reference implementation: `service/appointments`, the newest service).

## Module map

```
core/                    shared infra: domain Result/Error types, service (Ktor server, auth, respondWith), data (Exposed, event streaming, cache)
library/                 money, idempotency, permissions, validation
service/<svc>/
  domain/api/            operation interfaces + entities + <Svc>ErrorCodes   (package com.bookk.<svc>.domain.api.{operation,entity})
  domain/impl/           <Operation>Impl + di/DI.kt + tests                  (package com.bookk.<svc>.domain.impl.{operation,di})
  data/source/           datasource INTERFACES                               (package com.bookk.<svc>.domain.datasource)
  data/                  datasource impls, orm tables/entities, migration, di
  microservice/          route/<Svc>Routing.kt (typed Resources), route/api/*Route.kt, <Svc>Microservice.kt main, route tests
  client/                cross-service events/API
```

New gradle modules must be registered in `settings.gradle.kts` (one `include` per submodule, grouped per service). Convention plugins (`libs.plugins.bookk.microservice`, `bookk.domain.impl`, `bookk.domain.api`, `bookk.data`, …) already add Ktor/Koin/MockK/kotlin-test deps and JUnit platform — do not re-add them.

**Write database migrations by hand.** This is now Claude's job, not the user's. There is no generator — earlier attempts at diffing the ORM table definitions with `MigrationUtils`/Flyway produced migration scripts that silently corrupted schema changes involving composite indices (a dropped column still referenced by a named unique index never got its `DROP INDEX`, and MariaDB rejected the result), so that tooling was removed rather than trusted. When an ORM table changes (new column, new index, new table, etc.), write the SQL directly into a new `service/<svc>/data/src/main/resources/db/migration/<schema>/V<n>__migration_script.sql`, where `<n>` is one past the highest `V<n>` already in that directory. Reflect exactly what changed in the table definition: column adds/drops/type changes, index adds/drops, constraint changes — and drop a named composite index yourself before dropping any column it covers, MariaDB will not infer that. Verify the new script applies cleanly before considering the change done: bring up a MariaDB instance reachable at `127.0.0.1:3308` (`deployment/dev/environment-compose.yml` if one isn't already running), then actually run Flyway against it through all migrations for that schema up to and including the new file and confirm it succeeds — never hand-wave this step or ship a script that hasn't been executed against a real database.
**Keep the database ER diagrams current.** `docs/database/` documents every microservice's schema as a Mermaid ER diagram in its own file (`docs/database/<svc>.md`, indexed from `docs/database/README.md`), plus `docs/database/cross-service-overview.md` for logical (non-FK) references. Any change to an ORM table — new/removed table, column, or relationship — must update that service's diagram (and the cross-service overview, if a logical reference changed) in the same change.
**Keep the operation activity diagrams current.** `docs/operations/` holds one Mermaid flowchart per HTTP route that mutates state, plus one per asynchronous reaction to a cross-service Kafka event (an `EventHandler`'s `registerResultReceiver` block — file named `on-<event>.md`, e.g. `on-user-deleted.md`), indexed in `docs/operations/README.md` and cross-linked from each route's KDoc via a `See: docs/operations/<svc>/<file>.md` line (an unrecognized KDoc field — the openApi plugin ignores it, verified by compiling). Any new mutating route or event handler, or a change to an existing one's permission checks/error cases/event publication/event handling, must add or update its diagram in the same change. Diagram nodes should carry the actual datasource calls, error codes and event names so the flow is understandable without opening the code. Whenever an operation sends a cross-service event, its diagram ends with a `**Consumed by:**` line linking forward to every reaction diagram for that event, and each reaction diagram links back to its producer(s) — keep both directions in sync, and mirror any addition/removal in `docs/operations/README.md`'s "Cross-service event map" table.
**Prod deployment is scripted with Ansible in `deployment/ansible/`** (see its README). Prod runs the monolith, not the five microservices, and has no Kafka: one `monolith` stack (`deployment/prod/monolith/monolith-compose.yml`) with the app, one MariaDB holding all five schemas and one Redis. The app carries the network aliases `authorization.service`, `user.service`, `business.service`, `appointments.service`, `notifications.service`, so nginx's per-service `/api/<svc>` routes reach it unchanged, and every `*_SERVICE_HOSTNAME` in its env (`monolith_env` in `inventory/group_vars/all/main.yml`) is `monolith.service`, because `TokenIssuerImpl` issues both auth tokens and quotes with the single `APPLICATION_SERVICE_HOSTNAME` and the validators expect it as the auth/business issuer. The database is bootstrapped by `db/init-schemas.sh`, mounted as a swarm config with mode `0444` so the MariaDB entrypoint *sources* it (an executable `.sh` is run instead, and `docker_process_sql` is then undefined); it creates the five schemas and grants the app user only those, root is limited to `localhost`. MariaDB's sizing lives in its own `db/tuning.cnf` (swarm config `monolith-mariadb-tuning-v<n>`, mounted next to the encryption `my.cnf` in `/etc/mysql/conf.d/`, which the ubi9 image reads through `/etc/my.cnf.d/docker.cnf`), sized for the 2 vCPU / 8 GB / NVMe worker: a 2G buffer pool, 512M redo log, `innodb_io_capacity = 1000`, `innodb_flush_neighbors = 0`; everything else stays at the 11.8 defaults, and a change needs a new config name. The worker's memory limits are sized together with it: MariaDB 3G (a full 2G pool measured 2.17G), Valkey 768M with `--maxmemory 512mb --maxmemory-policy noeviction` (a full cache rejects writes with an error instead of OOM-killing the container or evicting idempotency and claim keys, and the headroom covers the AOF rewrite fork), the app 1536M with `JAVA_TOOL_OPTIONS: -XX:MaxRAMPercentage=70 -XX:+ExitOnOutOfMemoryError` (≈1.05G heap; without it the JVM takes 25% of the limit). Valkey's size is set by how many writes it must remember, measured on `valkey:8.1`: a stored HTTP idempotency response costs its size plus ~200 B for 10 minutes, an event's processed marker ~147 B per consumer group for 1 hour (`CacheEventIdempotencyStorage.PROCESSED_TTL`): ~130 MB of responses at a 100 writes/s peak — what the 2 vCPU worker can serve — plus ~50 MB of markers at that rate (it was ~250 MB/day while markers lived 24 hours). A full Valkey under `noeviction` fails every idempotent request and every event delivery, so raise `--maxmemory` (and the limit with it) before it fills. The limits add up to slightly more than 8G only during a deploy, when the app runs `start-first` and two copies briefly overlap; actual use stays well under them. MariaDB and Valkey keep their data on node-local volumes, so both are pinned to the node labelled `database=true` (set from the inventory's `swarm_labels`, like Kafka's `kafka=true`); only the app container may float between workers. Prometheus requires basic auth (user `admin`) on every endpoint, its own `/metrics` included: the external swarm secrets `prometheus_web_config` (its `--web.config.file`, a bcrypt hash) and `prometheus_password` (the plain password, used by the self-scrape's `password_file` and Grafana's datasource via `$__file{/run/secrets/prometheus_password}`) are generated as a pair by `import-secrets.py`, which derives a missing hash from the stored password so they never diverge; a new scrape job against Prometheus itself, or a new Grafana datasource for it, must send the same credentials. The swarm compose schema rejects unquoted booleans in `environment` (`GF_SMTP_ENABLED: "true"`), so validate a changed stack with `docker stack config -c <file>` before deploying. A scrape job for a swarm service uses `dns_sd_configs` on `tasks.<service>` (`tasks.<stack>_<service>` from another stack, e.g. `tasks.monolith_monolith`), never the service name or an alias, which is a virtual IP that sends each scrape to a random task; node-level alerts label nodes by `nodename` (node-exporter runs with `hostname: "{{.Node.Hostname}}"`, the recording rules join `node_uname_info`) because `instance` is a task IP. Prometheus, Grafana and Loki keep their data on node-local volumes and are pinned to the node labelled `monitoring=true` (`manager-1`'s `swarm_labels`). Logs reach Grafana through Alloy (global, Docker socket) → Loki, labelled `stack`/`service`/`node`; dashboards filter levels on `detected_level`, which the monolith's logback level feeds as structured metadata (`alloy/config.alloy`). The provisioned dashboards (`grafana/dashboards/*.json`) refer to the data sources by their fixed uids `prometheus` and `loki`. cAdvisor keeps reporting a stopped container's last values for a couple of minutes, so a query that counts or sums containers must keep only live ones (`and on (id) (container_last_seen > time() - 30)`), or every deploy double-counts the service. A Loki instant metric query reaches a bar gauge as one unnamed frame: use a range query and a `reduce` transformation (`seriesToRows`, `sum`), which also puts every bar on one scale. Group node panels by `nodename`, not `instance`: a restarted node-exporter task gets a new IP, and an `instance`-grouped panel then shows the node twice. MariaDB and Valkey are scraped through `database-exporter` and `redis-exporter` in the monolith stack; the MariaDB `exporter` user (`PROCESS` only) is created by `--init-file` from the swarm secret `monolith-mariadb-exporter-init-v<n>`, rendered by the monolith role from the vault, because `init-schemas.sh` runs only on an empty volume and root logs in only from inside the container: adding or renaming that secret restarts the database. cAdvisor has no `container_restarts_total` (the old `ContainerRestarting` alert could never fire); a crash is a container of a service that started in the last 15 minutes and is no longer seen (`service:containers_stopped_after_start:15m`). Loki deletes only by age; its stored size is `loki_ingester_chunk_size_bytes_sum` (compressed chunk bytes written, equal to the chunk files on disk), which `LogStorageGrowing` projects over the 14-day retention. YAML `<<:` merges one level deep, so a service that merges the `*replicated` template and declares its own `deploy:` loses the whole template `deploy:` block: merge `<<: *replicated-deploy` inside it (Prometheus had run without the restart and rollback policy that way). The monolith image (`ghcr.io/nocturneproperties/bookkme-server:<version>`) is published by pushing a `monolith/<version>` tag (`.github/workflows/monolith-publish.yml`); the workflow fails unless the tag equals `version` in the root `build.gradle.kts`, because Jib tags the image with the project version, not the git tag, and then calls `.github/workflows/deploy.yml`, which only runs `ansible-playbook playbooks/deploy.yml` (also runnable by hand with a version, for rollbacks). Microservice images are still published, never deployed: an `auth/`, `user/`, `business/`, `appointment/` or `notification/<version>` tag runs `.github/workflows/microservice-publish.yml` (one workflow, the prefix picks the Gradle module, same version check). Every workflow runs on GitHub-hosted runners pinned to `ubuntu-24.04` (not `ubuntu-latest`, which moves to a new Ubuntu on GitHub's schedule; the repository is public, so they are free; there is no self-hosted runner stack any more), so the deploy job reaches the manager over SSH from the internet. Workflows never run `docker` against the swarm themselves, and never run the infra playbook (run it by hand). The deploy job installs Ansible with `uv`, pinned to the versions of a local Homebrew install, and it must pull with the registry token from the vault, not `GITHUB_TOKEN`: `--with-registry-auth` stores the credentials in the service for later pulls, and `GITHUB_TOKEN` expires with the job. Image tasks need `--no-configuration-cache`: Jib's task holds a `Project` reference the configuration cache cannot serialize. The compose files under `deployment/prod` and `deployment/adminpanel` remain the source of truth: the `stack` role copies a stack's directory to `/opt/bookk/stacks/<stack>/` on the manager and runs `docker stack deploy` there (removing files gone from the repo first, and the vault-rendered secret files again right after the deploy, since Docker only reads them then; the `docker_stack` task runs under `no_log`, its result holds every service's env), with variables from the encrypted `inventory/group_vars/all/vault.yml` (`make vault-import` builds it and generates every key and password; `make vault-update` adds what a newer structure needs without replacing set values). A new infra stack needs an entry in `infra_stacks` and a tagged task in `playbooks/site.yml`. The wg-easy panel (pinned to v14 by digest, configured by env vars; v15 is a different, setup-wizard config) is reachable only through nginx's `vpn.` host from the VPN subnet, its port 51821 unpublished, so the first client configs come from the `vpn_clients` role (tag `vpn`): it calls the panel's own API inside the container with `vault_vpn_password` (the plain password behind `VPN_PASSWORD_HASH`) via `docker exec … node --eval`, creates the missing `vpn_clients` and saves their configs to the gitignored `deployment/ansible/vpn-clients/`. wg-easy v14's image points `iptables` at the legacy backend, whose `nat` table an nf_tables host (Ubuntu 26.04) never loads and the container can't load, so its default hooks fail and the container crash-loops: `vpn-compose.yml` sets `WG_POST_UP`/`WG_POST_DOWN` to the same rules via the image's `iptables-nft` instead (verified in a throwaway container on the manager). dnsmasq publishes 53/udp in `mode: host`, and `docker_host` disables systemd-resolved's stub listener on managers: with the stub holding `127.0.0.53:53`, Docker silently publishes nothing for port 53 (no `docker-proxy`, no NAT rule), and every VPN client loses DNS and with it the internet. The manager host joins the VPN as `vpn_host_client` (`admin-1`, pinned to `vpn_host_address` through the API) on `wg0` (`vpn_host` role): dnsmasq resolves the domain to that address and wg-easy hands it out as DNS, so VPN traffic reaches nginx via the manager's `wg0` with its VPN source address intact, which is what makes nginx's subnet filter work. The subnet (`172.16.91.0/24`, outside Docker's bridge and overlay pools) is set only as `vpn_network_prefix` in `inventory/group_vars/all/main.yml` and reaches wg-easy, dnsmasq and nginx as `VPN_SUBNET`/`VPN_ADDRESS_TEMPLATE`/`VPN_HOST_ADDRESS` (`vpn_stack_env`), never hard-coded. wg-easy keeps the server address from its first start in `wg0.json` and ignores `WG_DEFAULT_ADDRESS` afterwards, so `ensure-clients.js` renumbers an install whose stored prefix differs (backup → rewrite every address, keeping host numbers and keys → restore → `wg-quick down/up` in the container). The role refuses to create a stack that doesn't exist yet unless `-e allow_new_stacks=true` (`make bootstrap`, `make deploy v=… first=1`). `bitnami/*` images can no longer be pulled from Docker Hub: the cache everywhere (dev, prod, `RedisCacheClientTest`) is Valkey (`valkey/valkey:8.1-alpine`, configured on the command line: `--requirepass`, `--appendonly yes`, `FLUSHDB`/`FLUSHALL`/`CONFIG` renamed away) and prod uses the official `mariadb` image. `deployment/prod/kafka/kafka-compose.yml` (not deployed today) mirrors dev's Kafka (`apache/kafka-native:4.2.1`, the same `KAFKA_*` settings and fixed ports 9092/9093) as a single broker like dev, reachable as `kafka:9092` on the `operational` network and pinned to the node labelled `kafka=true` (the `swarm` role applies a host's inventory `swarm_labels` with `docker_node`; values must be quoted strings, an unquoted `true` reaches Docker as `True` and never matches), because its data lives on a node-local volume. Its volumes are mounted at `/home/appuser` with `KAFKA_LOG_DIRS=/home/appuser/kafka-data` instead of dev's `/var/lib/kafka/data`: that path doesn't exist in the image, so a fresh volume there is root-owned and the broker (uid 1000) can't write to it. Dev fixes that with a `chown` init container, which Swarm can't order (it ignores `depends_on`); a volume mounted on the image's own `appuser`-owned home directory inherits that ownership instead.
**Ignore all git operations.** Managing Git is the responsibility of the developer, do not automatically commit, push or merge
**Bump the version after every code change.** The single project version lives in the root `build.gradle.kts` (`version = "X.Y.Z"`, inherited by every module via `rootProject.version`). After changing code, bump it per semantic versioning according to the kind of change: **MAJOR** for a backwards-incompatible change (removed/renamed route, field or `@ProtoNumber`; changed wire type; changed meaning of an existing field or error code; a migration that breaks older service instances), **MINOR** for a backwards-compatible feature (new route, operation, event, entity field or error case, new allowed behavior or new rejection rule), **PATCH** for a backwards-compatible fix, refactor or internal change with no API/behavior addition. A higher part resets the lower ones (`0.3.5` → `0.4.0`, `1.2.3` → `2.0.0`). **While the version is `0.x`, a backwards-incompatible change bumps MINOR, not MAJOR** — removing or renaming a route, field or `@ProtoNumber` is allowed freely and counts the same as a new feature (`0.12.0` → `0.13.0`). A release does not move the version to `1.0.0`: the first public release shipped as `0.15.7` (`RELEASE_NOTES.md`), and the project moves to `1.0.0` only when the developer decides to; the MAJOR rule applies from then on. Measure against the version in the last commit (`git show HEAD:build.gradle.kts`), not the working tree: the uncommitted change set gets exactly one bump, at the level of its most significant change — if the working tree is already bumped at that level or higher, leave it; if it is bumped at a lower level (e.g. a patch bump, then a feature is added), raise it to the correct level from the committed version. Docs-only or test-only changes do not bump the version.
**The monolith (`src/main/kotlin/com/bookk/server/MonolithServer.kt`) uses `EmbeddedEventConsumer`/`EmbeddedEventProducer`, never Kafka.** Each service has two module builders: `xModule()` (e.g. `authModule()`, `appointmentsModule()`) includes `eventStreamingTransportModule(Scope, SERVICE_NAME)` (Kafka) and is what the standalone microservice starts with, while `xEmbeddedModule()` includes `embeddedEventStreamingTransportModule(Scope, SERVICE_NAME)` (both from `core/data/eventstreaming/impl/.../di/DI.kt`). A service that sends events also includes `outboxModule(Scope)` in both, which binds its `StandardEventProducer` and `OutboxRelay` (see the outbox rule below); notifications sends none and has neither. `MonolithServer.diModules()` lists every service's `xEmbeddedModule()`, plus one `topicQueueHolderModule()` providing a single root-level `TopicQueueHolder<String>` singleton shared by all five scopes. `TopicQueueHolder` is pub/sub, not a point-to-point queue: `subscribe(topic)` hands each caller its own `Channel`, and `publish(event)` fans the event out to every subscriber of that topic — this matters because several services' `EventHandler`s register receivers for the same topic (e.g. `AuthEvent.UserDeleted` is consumed by user, business, appointments and notifications), so a single shared `Channel` per topic would let only one of them win the event. When adding a new service to the monolith, register it the same way: give it an `xEmbeddedModule()` with `embeddedEventStreamingTransportModule(NewScope, NEW_SERVICE_NAME)` (plus `outboxModule(NewScope)` if it sends events) and add that to `diModules()`, no other wiring needed. The service name is not optional: it becomes the consumer group the idempotency storage keys on, and two services sharing one would skip each other's events.
**The monolith needs a single cross-schema DB user, unlike per-service deployments.** `createDatabase(schemaName, ...)` (`core/data/database/Migration.kt`) reads its host/port/user/password from `AppLevelConstants`, which is process-global (`System.getenv("APPLICATION_DB_*")`) — only `schemaName` varies per call. A standalone microservice gets one schema-scoped MariaDB user (`deployment/dev/db/init.sql` creates `user`/`authorization`/`business`/`appointments`/`notifications`, each granted only on its own database). The monolith runs all five services' `createDatabase` calls inside one process reading the same env vars, so it needs one MariaDB user granted on all five schemas — `init.sql` also creates a `monolith` user with `GRANT ALL PRIVILEGES` on each of the five databases. Root-cause a `FlywaySqlUnableToConnectToDbException` / `Access denied for user 'monolith'` in the monolith container before assuming a code bug: `init.sql` only runs on a MariaDB volume's *first* initialization, so a pre-existing dev `database_data` volume won't pick up a newly added user until the grants are applied by hand (`docker exec <db-container> mysql -h 127.0.0.1 -P 3307 -u root -p'<MARIADB_ROOT_PASSWORD>' -e "..."`) or the volume is recreated. Flyway in `createDatabase` connects with the schema in the JDBC URL (`jdbc:<url>:<port>/<schema>?createDatabaseIfNotExist=true`), not a bare host: with no default schema, Flyway's MySQL support "restores" the connection after migrating by running `CREATE SCHEMA`/`USE`/`DROP SCHEMA` on a random UUID name, which every schema-scoped user is denied, logging `Access denied … to database '<uuid>'` + `Unable to restore connection to having no default schema` on each startup (`MigrationMariaDbTest`). After migrating, `createDatabase` connects Exposed through one HikariCP pool per schema (`poolName` = schema, `maximumPoolSize` from `APPLICATION_DB_POOL_SIZE`, default 10, `isAutoCommit = false`, REPEATABLE READ), so the monolith holds 5 × pool size connections (keep that under MariaDB's `max_connections`, 151 by default) and a transaction no longer opens its own connection. Hikari resets isolation and autocommit when a connection is returned (a READ COMMITTED `OutboxRelay` batch doesn't leak, `MigrationMariaDbTest` pins it), but not session variables: a `SET SESSION …` stays on that pooled connection for whatever borrows it next, so production code must never set one, and a test that does (`innodb_lock_wait_timeout = 1`) affects later transactions on the same `Database`. The root project itself carries the `bookk.microservice` convention plugin (`build.gradle.kts` applies it directly, not `.apply(false)`), so `./gradlew publishImageToLocalRegistry` with no module path builds and tags the monolith image as `bookkme-server:latest` (and `:<version>`) straight from the repo root, no subproject prefix needed. Dev deployment artifacts mirror the per-service ones: `deployment/dev/service/monolith.env` (one env file, all internal `*_SERVICE_HOSTNAME` vars pointed at `monolith.service` itself since every route lives in one process, no Kafka vars since it's embedded), `deployment/dev/monolith-compose.yml` (one `monolith` service, both the app port and the jdwp debug port published to the host since there's no nginx entry routing to it yet), and `deployment/dev/rollout-monolith.sh` (same shape as `rollout.sh`, but builds the root project's image directly instead of looping per service).

## Core conventions (apply everywhere)

- **Never write comments.** No `//` comments, no KDoc, no explanatory blocks — in production code or tests. Express intent through names and structure instead: rename the function, extract the condition into a named value, split the method. If something seems to need a comment, that is a signal the code should be clearer. The only exceptions are the route KDoc the openApi plugin parses (`Summary:`, `Body:`, `Response:`, …) and comments that already exist in the file — never delete or reword someone else's comment.
- Operations return `Result<T>`; impls **throw** errors inside `transactionManager.transaction { }`, which catches and converts to `Result.failure`.
- Domain errors: nested `sealed interface Error` in the operation interface; each case is a `class` extending `BusinessError(statusCode, code, message)` (classes, NOT data objects). Assert with `is`, never equality. Exception: appointment status-transition errors are shared, not per operation — `AppointmentStatusError` (`AlreadyCancelled`, `AlreadyCompleted`, `MarkedNoShow`, `NotStarted`, next to the `Appointment` entity) is thrown by the entity's own guards `Appointment.requireScheduled()` / `requireCompletable(now)` / `requireNoShowMarkable(now)`. An operation that changes an appointment's status calls the matching guard on the row it read with `getForUpdate` instead of re-declaring these cases in its own `Error`. Appointment requests follow the same pattern: `AppointmentRequest.requirePending()` throws the shared `AppointmentRequestStatusError` (`AlreadyApproved`, `AlreadyDeclined`), used by both decline and approval (a sealed interface's subclasses must live in its own package, so the entity cannot throw an operation's nested error).
- Error codes live in `domain/api/.../<Svc>ErrorCodes` as `BASE + n`. Blocks: auth=0, user=100000, business=200000, appointments=300000, notifications=400000. Next service takes the next 100000 block. Service-independent codes live in `core/domain/.../CoreErrorCodes` (block 900000, e.g. `TRANSACTION_CONFLICT`).
- Generic infrastructure errors: `com.bookk.core.domain.entity.Error` (`NotFound`, `OperationNotAllowed`, …).
- `call.respondWith(result)` (core/service) maps: success Unit→204, success T→200, `BusinessError`→its statusCode + `SimpleServerError(errorCode, message)`, `Error.NotFound`/`Error.OperationNotAllowed`→**404** (intentional: permission failures do NOT return 403), `Error.TransactionConflict`→**409** + `SimpleServerError(CoreErrorCodes.TRANSACTION_CONFLICT, …)`, anything else→500 (logged).
- Permissions: fine-grained per-resource grants (`library.permissions.ResourcePermission(view, update, delete)`, three independent booleans with no defaults — always pass all three, no ranking between them) — `businessPermissionDataSource.getPermission(userId, businessId, BusinessResource.CLIENTS).assert(PermissionAction.UPDATE)` (business) or `appointmentPermissionDataSource.getPermission(userId, businessId).assert(PermissionAction.VIEW)` (appointments, single implicit resource) — throws `Error.OperationNotAllowed`. A caller acting on their own assigned resource (e.g. an employee's own appointment) can pass an `update`/`delete` check on a `view`-only grant via `.assertOrSelf(action, actorId, assigneeId)`. An employee's suspension (`Employee.suspendedAt`) is enforced inside `BusinessPermissionDataSource.getPermission`, which throws `library.permissions.EmployeeAccessSuspended` (403, `BUSINESS_EMPLOYEE_ACCESS_SUSPENDED`) for a suspended caller (`getViewer`/`getViewers` just report `NONE` permissions and a null `employeeId`); appointments mirrors it via the `suspended` flag on `EmployeePermissionsChanged` and `appointment_permission_grants.suspended`, throwing the same `library.permissions.EmployeeAccessSuspended`, so a new permission-gated operation gets it for free — list that 403 in its route KDoc — only paths with no permission gate (client booking via `GetAppointmentBookingContext`) must check `employee.isSuspended` themselves, and anything publishing `EmployeePermissionsChanged` must set `suspended = employee.isSuspended` alongside the stored `permissions`. See `docs/object-permissions.md` for the full model, including how a `Business`/`AppointmentSettings` entity gets the requesting user's grants attached (`Business.viewedBy(businessPermissionDataSource.getViewer(...))` / `.copy(permissions = ...)`, computed per request, never persisted on the row). A list operation resolves its caller-specific fields with one batched lookup over every id (`getViewers(userId, businessIds)`), never one datasource call per row.
- Name/email/phone/currency format checks: `library.validation.{NameValidator,EmailValidator,PhoneValidator,CurrencyValidator}.isValid(value, ...)` (library/validation, plain `bookk.domain.api` module, no domain dependency — only joda-money, for `CurrencyValidator`) — pure `Boolean` predicates, each with a default `maxLength`/`minLength` you can override per call site; the caller still owns throwing its own `*ValidationError`. Reuse these instead of hand-rolling a regex/length check in a new operation.
- Wire format is ProtoBuf (`application/x-protobuf`) for all bodies/responses. **A nullable collection (`List<T>?`, `Map<K, V>?`) cannot be serialized when null** — kotlinx throws `'null' is not supported as the value of collection types in ProtoBuf`. For an optional group of fields in a partial-update DTO, wrap them in a nullable `@Serializable` holder class (a nullable message is fine) instead of making each list nullable — see `BusinessUpdateModel.schedule: Schedule?`. **A nullable property must not also have a default** — the serializer runs with `encodeDefaults = true`, and encoding a defaulted null throws `'null' is not supported for optional properties in ProtoBuf` as soon as a caller omits it. Give every nullable field on a partial-update DTO no default at all and pass them explicitly (`BusinessUpdateModel`, `UserEditModel`). **Never use a `Map` keyed by an enum as a request body field** (e.g. `Map<BusinessResource, ResourcePermission>`): the openApi plugin renders it as bare `additionalProperties` with no key list, and on the ProtoBuf wire the keys are unannotated enum ordinals, so the valid keys are documented nowhere. Give the DTO one nullable field per enum value with its own `@ProtoNumber` and convert to a map in the DTO (`EmployeePermissionsRequest.grants()`).
- Entities: `@Serializable data class` in `domain/api/.../entity` with a `companion object { fun stub(...) }` factory (defaulted params, `Uuid.random()`, `Instant.fromEpochMilliseconds(0)`) — add `stub()` to every new entity; tests rely on it.
- **Every amount inside one business is in the business currency.** Joda `Money.plus` throws `CurrencyMismatchException` on mixed currencies, and every total here is a plain `reduce { acc, price -> acc + price }` (`IssueQuoteImpl`, `Appointment.totalAmount`, `AppointmentRequest.totalAmount`), so a mixed-currency business turns quoting and booking into 500s. Hence: `CreateService`/`UpdateService` re-denominate the client's price into the business currency (`Money.inCurrencyOrNull`, `service/business/domain/impl/.../operation/service/BusinessCurrencyPricing.kt`; an amount with more decimals than the currency allows is `PricePrecisionInvalid`, not rounded), and `UpdateBusiness` rejects a currency change once `ServiceDataSource.hasServices` is true (`CurrencyLocked`; re-sending the stored code is always a no-op). Both sides go through `BusinessDataSource.lockBusiness(id, RowLock)`, which locks the business row and returns its currency: service writes take `RowLock.SHARED` (they don't block each other), a currency change takes `RowLock.EXCLUSIVE`, each as the transaction's first statement (see the lock-first rule below). A stored code `CurrencyValidator` rejects (legacy rows such as `usd`) doesn't lock, so the owner can still fix it, and service writes reject it with `BusinessCurrencyInvalid` instead of a 500. A new write that stores a price on a business entity must take the same lock and never trust the currency the client sends.
- **Never accept another service's identity/pricing data as free text from the client.** A snapshot field sourced from another service's data (an employee's name, a client's contact info, a service's price/duration, …) must be resolved server-side via a synchronous internal client call at write time (`BusinessClient`-style, see `service/business/client` + the `Api.Internal.*` routes it calls) — the wire DTO the client submits carries only the foreign id(s), never the name/price/etc. it claims. When a caller always needs the same set of related fields together (e.g. an appointment booking needs its employee, client and services in one shot), resolve them with one combined operation/HTTP round trip instead of one call per entity — fewer network failure points, and a slim consumer-shaped aggregate type (see `BusinessDTO`, `AppointmentBookingContext`) is normal here rather than reusing raw domain entities 1:1.
- **Every ProtoBuf wire type carries an explicit `@ProtoNumber` on every serialized field** — request/response DTOs, entities, events, and enum entries (`@ProtoNumber(n) ENTRY`, which replaces the implicit ordinal). Without one, kotlinx numbers a field by declaration order (index + 1; ordinal for enums), so inserting or reordering silently renumbers the wire. That includes an event's body property `override val topic: String = TOPIC`, which is serialized after every constructor parameter — annotate it on the line above (`@ProtoNumber(n)\n override val topic`). A new field takes the next unused number with a default; never reuse or change an existing one. JSON-only types (`Jwk`/`JwkSet`, the idempotency cache records) are exempt.
- **Log level and request metrics are set in `core`, not per service.** The root logger level comes from `APPLICATION_LOG_LEVEL` (default `info`; the dev env files in `deployment/dev/service` set `debug`). `logback.xml` must keep a single `<root>`: with two, logback applies the last one, which is how prod logged at DEBUG (`LogbackConfigurationTest`). Every request is logged once at INFO by `installRequestLogging()` (`[status], METHOD path`), and `installRequestMetrics()` exports request durations as Prometheus histogram buckets (5ms … 10s, `ktor_http_server_requests_seconds_bucket`, aggregated with `histogram_quantile`) instead of Micrometer's default client-side percentiles, which cannot be combined across routes or instances (`RequestObservabilityTest`). Internal service-to-service HTTP clients install `installInternalCallLogging()` (`core/client`): request and response lines and bodies, written at DEBUG to the `com.bookk.core.client.InternalCall` logger, so they show in dev and never in prod (`InternalCallLoggingTest`). Ktor's `Logger.DEFAULT` logs at INFO whatever the level is, which is how prod logged every internal call's body; the `AppLevelConstants.BUILD_TYPE` switch that chose `BODY` was a compile-time `DEBUG` and is gone.
- **Use `runSuspendCatching { }` (`com.bookk.core.domain.entity`), never `runCatching { }`, around any block that suspends.** `runCatching` catches `CancellationException` too, so a cancelled coroutine turns into a `Result.failure` and keeps running. A DLT consumer then retries a cancelled handler, and `ExposedTransactionManager` turns cancellation into `Error.UnknownError`. `runSuspendCatching` rethrows cancellation and catches everything else. It is `inline`, so `return` / `return@runSuspendCatching` work as they did. Plain `runCatching` is still fine for purely blocking code (parsing, decoding, a blocking SDK call), since nothing in it can be cancelled. The same goes for `recoverCatching` around a suspending transform: use `recoverSuspendCatching { }` (the `Error.kt` helpers `onConstraintFailure`/`onPermissionsMissing`/… are built on it). A hand-written `catch (e: Exception)`/`catch (e: Throwable)` around suspending code needs a `catch (e: CancellationException) { throw e }` before it (`JobRunner`, `CleanUpWorker`, `IdempotencyPlugin`). Where the catch-all should still handle the block's *own* `withTimeout` (`DataSource.mapExceptions` maps a query timeout to `Error.UnknownError`) or should keep a consumer loop alive after a handler throws a stray cancellation (`EmbeddedEventConsumer.start`), call `currentCoroutineContext().ensureActive()` first in the catch instead: it rethrows only when the calling coroutine itself was cancelled. `mockTransaction()` rethrows cancellation like `ExposedTransactionManager` does. A cancellation test must assert `is CancellationException`, not `assertSame`: coroutines' stack-trace recovery re-creates the exception when it crosses a context switch (`suspendTransaction`).
- **Single-use tokens are claimed with one atomic `CacheClient.setIfAbsent` (Redis `SET NX EX`), never a `get` check followed by a later `set`.** The two-step version lets concurrent requests with the same token both pass. Reserve before doing the work, keep the reservation on success, and release it (`delete`, inside `withContext(NonCancellable)`, best effort) on any failure, so a rejected call doesn't burn the token (`CreateAppointmentRequestImpl` + `AppointmentRequestDataSource.reserveOfferToken`/`releaseOfferToken`). `InMemoryCacheClient` implements `setIfAbsent`, so datasource tests cover it.
- **Event consumers deduplicate per consumer group with an atomic claim, never a read-only "was it processed?" check.** `KafkaEventConsumer` and `EmbeddedEventConsumer` both run every receiver through `IdempotentDelivery` (`core/data/eventstreaming/impl`), backed by `CacheEventIdempotencyStorage` (`core/data/repository`, bound in `commonModule()`): `claim` is one `setIfAbsent` on `event:<consumerGroup>:<topic>:<idempotencyKey>` (1-min claim, `EventIdempotencyStorage.claimTtl`; a key that vanishes between the `SET NX` and the read is claimed again, not reported in progress), a successful handler then `markProcessed` (kept 1 hour, `PROCESSED_TTL`: every redelivery path — DLT retries, the `IN_PROGRESS` wait, an outbox batch republished after a crash or deploy, a Kafka rebalance — arrives within minutes; a Kafka consumer that stays down longer than that with processed-but-uncommitted offsets would handle those events again, and so does a hand replay of `exhausted_event`, which is meant to; it was 24 hours, which made the markers the bulk of Valkey's memory), and a failed or cancelled one `release`s the claim (under `NonCancellable`) before the DLT retry, so the retry can claim it again. Every `deliver` call claims and releases under its own random `deliveryId`, stored in the claim record, and `release` is a compare-and-delete on it (`CacheClient.deleteIfEquals`: a Lua `GET`-compare-`DEL` on Redis, `computeIfPresent` in `InMemoryCacheClient`): a handler that outlived its claim must not free the claim of the delivery that took over, or wipe the processed marker it left, which let a third delivery handle the event again (`IdempotentDeliveryTest` reproduces it in virtual time via `inMemoryEventIdempotencyStorage(testTimeSource)`; `InMemoryCacheClient(timeSource = …)` drives Caffeine's expiry from a `TestTimeSource`/`testTimeSource`, so TTL tests never wait; like Valkey's `SET … EX`, every `set` replaces the key's expiration (`Expiry.writing`) and a `deleteIfEquals` that doesn't match leaves it untouched (`InMemoryCacheClientTest`) — with `Expiry.creating` the processed marker silently kept the claim's 1-minute TTL, so marker-lifetime tests passed for the wrong reason). A cancellation the handler throws itself (a `withTimeout` inside it) is an ordinary failure and retried; only the consumer's own cancellation (`ensureActive()`) stops the delivery. `IN_PROGRESS` (another delivery holds the claim, or a crashed one left it) is waited out: `IdempotentDelivery` re-claims every second for up to `claimTtl`, so a crashed delivery's event is handled once its claim expires instead of being parked. Nothing replays `exhausted_event` automatically, so parking is effectively loss until someone replays by hand. Only a claim still held after the TTL, or a failed claim, goes through the DLT; a failed `markProcessed` is only logged, since the handler already succeeded. A handler must therefore finish within `claimTtl`. `deliver` returns `DeliveryOutcome` (`HANDLED` / `SKIPPED_DUPLICATE`) so logs tell a skipped duplicate from a processed event. DLT topics are per consumer group (`DltRetry.dltTopic(topic, consumerGroup)` = `<topic>_<consumerGroup>_dlt`): with one shared `<topic>_dlt`, every group subscribed to it and re-ran every other group's failures, multiplying retries (7 attempts instead of 3 with two failing groups). Two things this replaced, both silent event loss: the old `isEventProcessed` was the HTTP `getResponseOrLock`, which *writes* an in-progress lock on a miss and was never released, so every DLT retry saw it and skipped the event; and the key was `topic:idempotencyKey` with no consumer group while every service shares one Redis (`redis_local`, no key prefix), so of the four `AuthEvent.UserDeleted` consumers only the first to check handled it. The consumer group is part of the key, not the instance: replicas of one service share it, which is what makes a rebalance redelivery a duplicate. Test consumers with `inMemoryEventIdempotencyStorage()` (`testFixtures(projects.core.data.eventstreaming.impl)`, the real storage on `InMemoryCacheClient`), never a hand-written fake: the old `RecordingIdempotencyStorage` fake had no lock side effect, which is why every DLT test passed while production lost the events.
- **`RedisCacheClient` must return every borrowed connection to the pool:** `withPooledConnection { }` is `borrowObject().use { }`. Lettuce's pool hands out wrapped connections whose `close()` returns them; a bare `with(connectionPool.borrowObject())` opens a fresh Redis connection on every call and never closes it, which is how it leaked one connection per cache call until `RedisCacheClientTest` caught it. `withTransaction` queues writes on the **async** API between `MULTI` and `EXEC`, without waiting for replies: a coroutine command inside `MULTI` waits for a reply that only arrives at `EXEC`, so Lettuce's `coroutines().multi { }` hangs forever. If the action fails it sends `DISCARD` (under `NonCancellable`) before the connection goes back to the pool. Inside a transaction only `set`/`delete` work; `get`/`setIfAbsent`/`deleteIfEquals` throw `UnsupportedOperationException`, since their result doesn't exist until `EXEC`. `RedisCacheClientTest` runs against a real Valkey (`valkey/valkey:8.1-alpine`, the Redis fork every environment uses) via testcontainers (`GenericContainer`, Docker required, like the Kafka tests) and asserts `INFO clients` to catch pool leaks.
- **`transactionManager.transaction { }` may run its block up to 3 times.** `core/data/map/Mapper.kt` maps MariaDB's write conflicts to `Error.TransactionConflict`: error 1020 "Record has changed since last read" (`innodb_snapshot_isolation=ON`, the default since 11.6) and deadlocks (1213 / SQLState `40001`), found anywhere in the cause chain. `ExposedTransactionManager` re-runs the whole block in a fresh transaction, with a fresh snapshot, up to `MAX_ATTEMPTS_ON_CONFLICT` (3) times with a short jittered backoff, and only then returns the conflict, which `respondWith` turns into a 409. Only the outermost call retries. A nested `transaction { }` (e.g. `CreateAppointmentRequestImpl` → `createAppointment`) makes a single attempt and passes the conflict up: re-running an inner block inside an outer transaction that already failed would be wrong. The manager tracks this with its own coroutine-context marker, not Exposed internals. It also sets `maxAttempts = 1` on every Exposed transaction: Exposed's built-in retry would otherwise re-run a block 3 times on *any* raw `SQLException`, including a constraint violation flushed at commit, and stack on top of this retry. Consequence for every operation: a block must be safe to re-run. Database writes are, since they roll back. Anything else in the block repeats on retry: a cross-service call is made again (harmless for the reads they are today). Don't add new non-database side effects inside a transaction block. `eventProducer.send` is not one: it is a database write (see the outbox rule below), so only the attempt that commits leaves an event. Tests: `ExposedTransactionManagerTest` (H2) for retry/give-up/nesting, and `BusinessRowLockMariaDbTest` for a real 1020 (two updates of one service row) and a real deadlock (two transactions locking two business rows in opposite order), both recovering through the retry.
- **Every event goes through the transactional outbox, so `eventProducer.send` must run inside `transactionManager.transaction { }`.** In every service scope `StandardEventProducer` is `OutboxEventProducer`: it stores the encoded event in the service's own `outbox_event` table within the caller's transaction, and `OutboxRelay` publishes committed rows afterwards (`docs/transactional-outbox.md`). A rollback or conflict retry discards the row together with the write, so an event exists exactly when its write committed. A `send` outside a transaction throws `IllegalStateException` (checked with `transactionManager.isInTransaction()`) and the event is lost, so a compensating send after a failed transaction needs a transaction of its own (`FinishRegistrationImpl`'s `onFailure`). A service that starts sending events needs an `outbox_event` migration (the same SQL as `business/V15`), the table in its ER diagram, and `outboxModule(Scope)` in both module builders. Each service's `<Svc>ModuleTest` pins that wiring through `serviceScopeWithMockedInfrastructure(Scope, module)` (`testFixtures(projects.core.data.eventstreaming.data)`), which mocks the transaction manager, transport producer, consumer and root `CacheClient`, so the real modules resolve without env vars or a broker. `mockTransaction()` reports `isInTransaction()` as true while a mocked block runs, so an operation test can assert that a send happened inside one. Consumer-side DLT sends go to `KafkaEventProducer` directly, never through the outbox.
- **A transaction that holds row locks while it waits on something outside the database must not take gap locks.** `OutboxRelay.relayBatch` locks its batch (`SELECT … ORDER BY id LIMIT n FOR UPDATE`) and keeps the locks while Kafka acknowledges; at the default REPEATABLE READ, a scan that reaches the end of the table also locks the gap after the last row, so every business write's outbox `INSERT` waited behind a slow broker until `innodb_lock_wait_timeout` (proved by `OutboxRelayMariaDbTest`). It runs at `transactionManager.transaction(TransactionIsolation.READ_COMMITTED) { }` instead (record locks only). `mockTransaction()` stubs both `transaction` overloads. Publish a batch with `RawProducer.publishAll`: Kafka sends every record, then awaits all acks (one round trip, per-partition order kept by the single idempotent producer), tested with `MockProducer(autoComplete = false)` through `KafkaEventProducer`'s internal `Producer` constructor.
- **Never throw a `BusinessError` inside `dbQuery { }`.** `DataSource.mapExceptions` passes only core `com.bookk.core.domain.entity.Error` through; anything else, `BusinessError` included, becomes `Error.UnknownError` and a 500. A datasource that must fail with a domain error returns the raw result from `dbQuery` and throws after it (`BusinessPermissionDataSourceImpl.getPermission`). `ExposedTransactionManager` does pass `BusinessError` through.
- **Appointment/request double-booking is guarded by a lock, not a unique index.** Every write that books a slot (`CreateAppointment`, `UpdateAppointment`, `CreateAppointmentRequest`) first takes `AppointmentSettingsDataSource.getForUpdate(businessId)`, which serializes them per business, then runs `hasOverlapsWith` (active statuses only). Don't put a unique index on `(user_id, business_id, date_start)` or similar slot columns: it also counts cancelled/declined rows, so rebooking a freed slot fails with a 500 (that index existed until `V7` for exactly this reason). A new booking path must take the same settings lock before its overlap check.
- **A write addressed by a child id must be scoped to the business the permission check ran against.** The permission check passes on the `businessId` the caller supplies (path or body), so a datasource update/delete that matches only `WHERE id = ?` lets anyone with a grant in their own business reach another business's row by id. Put `business_id = ?` in the same `WHERE` (`ServiceDataSourceImpl.editService`, `deleteService`, `deleteServiceGroup`), and never write `businessId` from the request in an update's `set` block. Resolve a referenced child the same way, with a scoped read, and store and return what the server found, not the object the client sent (`getServiceGroup` in `CreateService`/`UpdateService`).
- **An Exposed FK column accessed through `val x by Table.column` on a DAO entity is typed `EntityID<Uuid>`, not `Uuid`.** Comparing it with `==` against a plain `Uuid` (e.g. `it.businessId == someUuid` after a `findById(id)`) always evaluates to `false` — the types never match structurally — silently making a scoping check useless instead of failing loudly. Unwrap with `.value` first (`it.businessId.value == someUuid`), or push the comparison into the Exposed DSL instead (`Table.businessId eq someUuid` inside `find { }`), which handles the conversion correctly.

### Writes live on the entity, not in the datasource

Mapping a domain model onto rows belongs in the DAO entity's companion, so a datasource method stays a one-liner and the field list has exactly one home. Reference: `AppointmentBusinessEntity`, `BusinessEntity`, `AppointmentEntity`.

```kotlin
internal class ThingEntity(id: EntityID<Uuid>) : UuidEntity(id) {
    var name by ThingTable.name

    fun domain(): Thing = Thing(id = id.value, name = name)

    private fun replaceChildren(children: List<Child>) {
        val entityId = id.value // `id` inside a table lambda resolves to the table's column, not the entity
        ChildTable.deleteWhere { ChildTable.thingId eq entityId }
        ChildTable.batchInsert(children) { this[ChildTable.thingId] = entityId /* … */ }
    }

    companion object : DecoratorUUIDEntityClass<ThingEntity>(ThingTable) {
        fun new(model: Thing): ThingEntity = new { name = model.name }.apply { replaceChildren(model.children) }

        fun findByIdAndUpdate(model: ThingUpdate) = findByIdAndUpdate(model.id) {
            model.name?.let { name -> it.name = name }
            it.updatedAt = Clock.System.now()
        }
    }
}
```
```kotlin
override suspend fun create(model: Thing): Thing = dbQuery { ThingEntity.new(model).domain() }
override suspend fun update(model: ThingUpdate): Thing = dbQuery {
    (ThingEntity.findByIdAndUpdate(model) ?: throw Error.NotFound()).domain()
}
```

Rules that fall out of this:
- **Never call `flush()` or `refresh()`.** Exposed flushes its entity cache before executing any statement, so a staged insert/update is always written before the next query or DSL statement observes it. Every such call added during this codebase's history turned out to be dead — `refresh()` is worse than dead, it re-reads the row and discards pending writes, which then needs a `flush()` before it to compensate.
- Business-rule guards (status transitions, "has the appointment started", …) belong in the **operation**, not the datasource: the operation's **first** read of the row is a locking one (`getForUpdate`, `SELECT … FOR UPDATE`), it checks and throws its own domain errors, then calls an unconditional datasource write (`markCompletedByUser`, `markNoShow`). The lock is held for the rest of `transactionManager.transaction { }`, so no concurrent write slips in between. The locking read must come first: Exposed's `EntityClass.wrap` returns the entity already in the transaction's cache and ignores the freshly selected row, so a plain `get(id)` followed by `getForUpdate(id)`/`findByIdAndUpdate(id)` in the same transaction takes the lock but still sees the values read **before** it (verified against exposed-dao 1.3.1 sources).
- **Take a row lock as the transaction's first statement, before any plain read — including the permission lookup.** MariaDB runs at REPEATABLE READ (nothing in `core` overrides it), and InnoDB fixes a transaction's snapshot at its *first* plain read. Lock first and the snapshot is taken after the lock is granted, so every later plain read sees what the previous holder committed. Read first (e.g. `getPermission`) and then lock, and two things go wrong. A later plain read still sees the old snapshot and misses rows committed while you waited, so two concurrent invitation creations could both take the last slot. Making that read a locking read doesn't rescue it either: MariaDB ≥ 11.6 ships `innodb_snapshot_isolation=ON`, so a locking read that meets a row changed after the snapshot fails with error 1020 "Record has changed since last read" (a 500). Whether that happens depends on the query plan: `hasServices` escaped only because its `LIMIT 1` was answered from the `business_id` index. So: lock first, then plain reads (`CreateEmployeeInvitationImpl`, `UpdateBusinessImpl` when `currencyCode` is sent, `CreateServiceImpl`/`UpdateServiceImpl`, `DeleteServiceGroupImpl`), and pin the order with a `coVerifyOrder { lockBusiness(...); getPermission(...); … }` impl test. Keep any check that depends on the lock result (e.g. "the stored currency is unsupported") until after the permission check, so a caller without access learns nothing. `Query.forShare()` (`core/data/RowLocking.kt`) emits `LOCK IN SHARE MODE` on MariaDB and falls back to the stronger `FOR UPDATE` on H2, which has no shared row lock; use it for the lock itself, not for reads after a snapshot exists. H2 can't reproduce snapshot or lock-mode behavior, so test locking against a real MariaDB with `BusinessRowLockMariaDbTest` as the template: testcontainers `mariadb:11.8.3-ubi9`, schema from the real Flyway migrations via `createDatabase`, holder/waiter interleavings ordered with `CompletableDeferred` plus polling `information_schema.INNODB_TRX` for `trx_state = 'LOCK WAIT'` — **more slowly than every 100ms** (`SLOWER_THAN_INNODB_TRX_CACHE_REFRESH`): InnoDB serves `INNODB_TRX` from a cache it refreshes only after 100ms *without reads*, so a 10ms poll that first reads just before the waiter blocks keeps getting the stale snapshot forever (this was the 'flaky under load' timeout of `BusinessRowLockMariaDbTest` and `OutboxRelayMariaDbTest`), and `SET SESSION innodb_lock_wait_timeout = 1` to make "would block" fail fast.
- Return `Unit` from datasource writes unless a caller branches on the result. A `Boolean` that only tests assert on is dead API; assert the guard through the stored state instead.
- Read a row back with `findById(...)?.toDomain()`, not a hand-rolled `selectAll().where { }` + `wrapRow`. Do not re-read after a write either — `new(...)` and `findByIdAndUpdate(...)` return the entity, so `.toDomain()` on it is enough.
- Entity referrers lazy-load one query per parent, so a read returning **many** rows needs `.with(Entity::children)` to batch them. Today's reads are all effectively single-row (`BusinessTable.userId` is a `uniqueIndex`, so a user owns at most one business), so plain referrers are correct — revisit if that changes.
- Rows that belong to an entity should reach it through a real FK so they are a DAO referrer (`val grants by XEntity referrersOn Table.ownerId`, eager-loaded with `.with(...)`), not through a manual join. Exposed's `referrersOn` follows exactly one FK column's `referee` — a logical link over several columns (e.g. grants keyed by `(user_id, business_id)`) cannot be a referrer, so add the owner's id column (`business_permission_grants.employee_id`, backfilled by a join in the migration) instead. Reference: `EmployeeEntity.grants`.
- A request DTO that replaces a whole entity as a PUT body (`EmployeeUpdateModel` for `Employee`) should reuse the entity's `@ProtoNumber`s for the fields it keeps, so older clients still sending the full entity decode cleanly — the extra fields are simply ignored.
- **Race-safe get-or-create** (e.g. resolving a foreign identity's local row by an id it doesn't yet know, provisioning it on first use): back it with a DB-level unique index on the lookup key (composite `uniqueIndex(colA, colB)` in the table's `init { }` block is fine even when one column is nullable — MariaDB treats NULLs as distinct, so unrelated nullable rows don't collide), then in the datasource do find → insert, and on failure re-find before giving up. `onConstraintFailure { }` cannot be reused here since its recovery lambda returns `Nothing` (it is only for turning a race into a thrown domain error) — inside the same `dbQuery { }` block a driver exception hasn't been mapped yet either, so catch it with `runCatching` and classify it yourself via `throwable.toDomain() is Error.UniqueConstraintFailed` (`com.bookk.core.data.map.toDomain`) before re-querying. Reference: `ClientDataSourceImpl.getOrCreateIntegratedClient`.
6. Write the impl unit test (see Testing) — every `Error` case + success + event publication if any.

```kotlin
         * Response: 200 application/x-protobuf [com.bookk.svc.domain.api.entity.Thing] Created thing
         * Response: 422 application/x-protobuf [com.bookk.core.domain.entity.SimpleServerError] Create thing errors<br>THING_EXISTS (300010) Thing already exists
         */
        post<Api.Thing> {
            val principal = requireNotNull(call.principal<AppPrincipal>())
            val body = call.receive<ThingRequest>()
            val doThing by application.inject<DoThing>()

            call.respondWith(doThing(userId = principal.userId, ...))
        }
    }
}
```
3. KDoc OpenAPI rules (the ktor openApi plugin parses these): `Summary:`, optional `Description:`, `Tag:`, `Security: jwt` only when inside `authenticate {}`, **`Body:` (NEVER `RequestBody:`)**, one `Response:` line per status. Fully qualified type names in brackets. Every case of the operation's `sealed interface Error` must appear under the 422 response with `NAME (<n>) message`. 204 responses: `Response: 204 application/x-protobuf <description>` (no type). **Never use a colon (`:`) anywhere in the KDoc text after the field prefix** (e.g. `NAME (<n>) message`, not `NAME (<n>): message`) — the openApi plugin parses on `:` and an extra one breaks the field. **NEVER put a generic type in a `Response:` KDoc line** (e.g. `[kotlin.collections.List<Foo>]` silently produces no schema — the compiler plugin's `TypeReference$Link$Reference.asIrType()` passes the raw string including `<…>` to `FqName()` then `ClassId.topLevel()`, which finds no class and returns null). For any `List<T>` response, omit the `Response:` line from KDoc and chain a `.describe {}` block instead:
```kotlin
        /**
         * Summary: Get things
         * Tag: thing
         * Security: jwt
         */
        get<Api.Things> {
            // ...
        }.describe {
            responses {
                response(HttpStatusCode.OK.value) {
                    schema = jsonSchema<List<Thing>>()
                    description = "List of things"
                    ContentType.Application.ProtoBuf()
                }
            }
        }
```
Required imports: `io.ktor.http.ContentType`, `io.ktor.openapi.jsonSchema`, `io.ktor.server.routing.openapi.describe`.
4. When a path id duplicates a body id, validate: `if (it.id != body.id) call.respond(HttpStatusCode.BadRequest, "Invalid request") else ...`.
5. Register the new route fn in `route/<Svc>Route.kt` aggregator (`fun Routing.<svc>Route()`); the aggregator is already wired in `<Svc>Microservice.kt`.
6. `AppPrincipal` fields: `authId`, `userId`, `deviceId` (all `Uuid`).
   To give an existing body-less route an optional body without breaking older clients, read it with `call.receiveNullable<XRequest>()` and keep every `XRequest` field nullable with no default — an empty request decodes to `null` (verified by `CompleteAppointmentTest`, which still posts with no body).
7. **For `get`/`post`/`delete`/`put`/`patch` matching a typed `@Resource`, import from `io.ktor.server.resources.*`, never `io.ktor.server.routing.*`.** The two packages both export a same-named function taking a generic type parameter, so the wrong import still compiles: `io.ktor.server.routing.patch<R>(body: suspend RoutingContext.(R) -> Unit)` treats `R` as a **request-body type to deserialize** (`call.receive<R>()`) and registers a bare `method(HttpMethod.Patch)` node with no path — it silently ignores the `@Resource` class entirely instead of routing by it. A route written as `patch<Api.Thing.Id> { ... }` with that import compiles clean but never matches its real URL, so every request 404s with no error anywhere (found via `service/business/microservice/route/api/Client.kt`, which had `import io.ktor.server.routing.patch` where every sibling handler in the same file correctly imported from `io.ktor.server.resources.*`).

## Testing

Run: `./gradlew :service:<svc>:microservice:test` / `:service:<svc>:domain:impl:test` (append `--tests "com.bookk...ClassName"` to filter).

Keep Testcontainers at **1.21.4 or newer** (`testcontainers` in `gradle/libs.versions.toml`). Docker Engine 29, which GitHub's `ubuntu-24.04` runners ship, rejects API versions below 1.44. Older Testcontainers (1.20.4) negotiate 1.32, so every container test in CI fails in `@BeforeAll` as `initializationError` / `IllegalStateException` ("Could not find a valid Docker environment"). The same tests still pass against a local Docker Desktop 27. Gradle stops at the first failing module, so CI usually reports only one such test (`MigrationMariaDbTest`).

Hard rules (enforced by fixtures or review):
- NEVER `runBlocking`. Operation tests: `runUnitTest { }`; route tests: `routeTest { }` (both from core fixtures).
- `given()` / `whenn()` / `then()` markers are **required in every test** — `runUnitTest` asserts at runtime that all three were called; a test without them fails.
- Fresh SUT and fresh mocks per test — no sharing across tests, no class-level mocks.
- DO NOT EDIT `core/src/testFixtures/kotlin/com/bookk/core/test/Test.kt`.
- Test names: backticked sentences, e.g. `` fun `should return failure when request overlaps with existing appointment`() ``.
- Use entity `stub()` factories instead of hand-built instances; pass only the fields the test depends on. Provide real entity instances to mocks (ProtoBuf serialization NPEs otherwise). **Never write a local test-file helper function (`private fun createTestX()`, `makeX()`, …) that re-lists an entity's fields to construct it** — that duplicates the field list the entity's own `stub()` exists to own. If the entity has no `stub()` yet, add one to its companion (see the Entities rule above) and call it directly at each test call site instead. The one exception is a partial-update DTO (`BusinessUpdateModel`, `ClientUpdateModel`, …) — those are request shapes, not domain entities, so they don't get a `stub()`; a local private helper (conventionally named `updateModel(...)`, defaulting every field to `null`) is the established pattern for building them in tests, e.g. `UpdateBusinessImplTest.updateModel()`.
- JUnit assertions (`org.junit.jupiter.api.Assertions`). Assert error types with `is`: `assertTrue(result.exceptionOrNull() is DoThing.Error.ThingExists)`.
- If the operation sends events: include a test with `coVerify(exactly = 1) { eventProducer.send(any(SvcEvent.X::class), any()) }`.

### Operation (domain/impl) test template

Using testing rules from AGENTS.md cover all ViewModels, Use cases(operations) and Data sources with unit tests. Afrer covering each feature (appointments, business etc.) Do a code review of your work and fix the issues if encountered. Make sure tests are fast, repeatable. Create utility functions or testFixtures in the core module for tools that are used across each tests. Do not share the state between unit tests, use private class SutFixture {
val thingArgParameter = mockk<SomeArgClass>()

Before writing code, enumerate and track as a checklist:
1. Happy path.
2. EVERY case of the operation's `sealed interface Error` — at BOTH levels: impl test (exception type) and route test (HTTP status + `SimpleServerError.errorCode`).
3. Auth: 401 unauthenticated; permission-denied (impl: `Error.OperationNotAllowed`; route: 404).

### Development Workflow: Test-Driven Development

Always implement features using strict TDD. For every requested feature or change:

1. **Red** — Write a failing test first that captures the expected behavior. Do not write any implementation code before the test exists.
2. **Green** — Write the minimum implementation needed to make the test pass.
3. **Refactor** — Clean up the implementation and tests while keeping all tests green.

Rules:
- Never write production code without a failing test that requires it.
- Run the test suite after each step and confirm the expected pass/fail state before proceeding.
- Keep tests small and focused; one behavior per test.
- If a requirement is ambiguous, write the test that encodes your assumption and state it explicitly.

### H2 dialect limitations — untestable operations

These throw `UnsupportedByDialectException` in H2 even with `MODE=MySQL`. Omit their tests and leave a comment in the test file:

| Operation | Used by | Workaround for reads |
|---|---|---|
| `updateReturning` | — | rewrite as `update {}` + a follow-up `selectAll()` read, which H2 supports and makes the method testable (`BusinessDataSourceImpl.updateBusiness` was converted this way) |
| `deleteReturning` | `BusinessDataSourceImpl.deleteUserBusinesses`, `DeviceDataSourceImpl.deleteInactiveDevices` | — |
| `upsertReturning` | `NotificationSettingsDataSourceImpl.upsert(settings)` | insert via DAO entity directly |
| `upsert(where = …)` | — | split into `insert`/`update` datasource methods and let the operation choose (`NotificationTargetDataSourceImpl` + `UpdateTargetInformation`) |

For read methods whose writes use an unsupported upsert, insert test data directly via the DAO entity (e.g. `NotificationSettingsEntity.new(id) { ... }`).

Plain `upsert {}` (no `where` parameter) **is** supported by H2 and resolves conflicts via `uniqueIndex` columns — use it freely in datasource tests. Passing `where` to it throws `UnsupportedByDialectException`. Split a conditional upsert into separate `insert`/`update` datasource methods — the guard lives in the `update {}` where clause and returns whether a row matched — and let the operation decide, inside its `transactionManager.transaction { }`, whether to insert.

### Asserting unique-constraint violations

`runUnitTest` cannot be nested inside `assertThrows` (its body is `suspend`, and the outer `TestHolder` context would be lost). Assert constraint failures with `runCatching` instead:
```kotlin
whenn()
val result = runCatching { suspendTransaction { fixture.sut.createX(duplicate) } }

then()
assertTrue(result.exceptionOrNull() is Error.UniqueConstraintFailed)
```
`dbQuery { }` maps the driver exception to `com.bookk.core.domain.entity.Error.UniqueConstraintFailed`, which operations turn into a domain error via `.onConstraintFailure { }`.

A DAO insert (`XEntity.new { }`) is flushed as a JDBC **batch**, so the driver reports a duplicate as `java.sql.BatchUpdateException`, not `SQLIntegrityConstraintViolationException` — verified on `mariadb-java-client` 3.4.1 (SQLState `23000`, and its cause is another `BatchUpdateException`) and on H2 (`23505`). `core/data/map/Mapper.kt`'s `toDomain()` therefore classifies by SQLState class `23` as well as by exception type; narrowing it back to an `instanceof` check turns every duplicate DAO insert into `Error.DatabaseError` (500) and silently disables `.onConstraintFailure { }` (`DataSourceConstraintMappingTest` covers both the single-row and batch paths). A "does it already exist?" check followed by an insert is never enough on its own: back it with a unique index and map the race with `.onConstraintFailure { }` to the same domain error the check throws (`JoinBusinessImpl` + `employee_business_id_user_id_unique`).

### Batch-update / batch-cancel patterns

`markCompleted(before: Instant)` and `cancelOutdated(before: Instant)` update rows where `dateEnd < before`. Test the happy path by creating entities at `Instant.fromEpochMilliseconds(0)` (epoch → well in the past) and calling with `Clock.System.now()`. Test the boundary by creating entities at `Clock.System.now() + 24.hours` and verifying they are NOT affected.

### Cleanup methods (deleteDayOffsInThePast)

Insert `DayOffRange(LocalDate(2020,1,1), LocalDate(2020,1,2))` for a past day-off and `DayOffRange(LocalDate(2099,12,30), LocalDate(2099,12,31))` for a future one. After calling `deleteDayOffsInThePast()` re-read via `sut.get(businessId)` and assert counts.

### Never use `advanceUntilIdle()` to drive work running on `backgroundScope` — use `advanceTimeBy` + `runCurrent`

This bit twice before the real cause was found, so: **`TestScope.advanceUntilIdle()` deliberately does not fully drain `backgroundScope`.** Straight from the `kotlinx-coroutines-test` KDoc on `TestScope.backgroundScope` — "The coroutines in this scope are run as usual when using `advanceTimeBy` and `runCurrent`. `advanceUntilIdle`, on the other hand, will stop advancing the virtual time once only the coroutines in this scope are left unprocessed." This is intentional (it's what lets a `backgroundScope` job that loops forever not hang `advanceUntilIdle()`), not a bug — but every `EmbeddedEventConsumer` test here runs the consumer via `consumer.start(backgroundScope)`, so `advanceUntilIdle()` is the wrong tool for **any** of them, not just multi-round DLT retry chains: it previously looked like it worked (a plain single-hop `send()` → `advanceUntilIdle()` → assert delivered) purely by timing coincidence, and stopped working the moment something upstream changed (see `EmbeddedEventStreamingTest`, which predates this whole feature and still hit it).

The fix, per that same KDoc: drive time with `runCurrent()` (runs whatever is due at the current virtual instant — nothing more) and `advanceTimeBy(duration)` (moves the clock forward, running scheduled tasks in the meantime) instead. Two things to know about these:
- `advanceTimeBy(duration)` does **not** run tasks scheduled for exactly `currentTime + duration` — always follow it with a `runCurrent()` to catch anything sitting exactly on that boundary.
- `runCurrent()` alone will not run a task scheduled via `delay()` for a future virtual time — only `advanceTimeBy`/`advanceUntilIdle` actually move the clock, so a chain with real backoff needs the clock advanced past each `delay()`, not just `runCurrent()` in a loop.

Pattern used across `EmbeddedDltRetryTest`/`EmbeddedEventStreamingTest`: for a delay-free single hop, `runCurrent()` alone is enough. For a chain with backoff (DLT retries), advance a single generous virtual duration (see `advanceThroughRetries()`: `runCurrent(); advanceTimeBy(1.hours); runCurrent()`) — virtual time is free, so there's no cost to advancing far more than the scenario actually needs, and it reliably sweeps through however many delay-then-reschedule rounds occur without having to compute exact cumulative backoff by hand.

### `runUnitTest`'s timeout is real time, not virtual

`runUnitTest` passes its 30-second budget as `runTest(context, timeout = 30.seconds) { ... }` (`core/src/testFixtures/.../Test.kt`), not a manual `withTimeout()` nested inside the test body. `runTest`'s own `timeout` parameter is a real-wall-clock watchdog against a hung test (it runs on the outer `runBlocking` dispatcher, outside the `TestCoroutineScheduler`) — it does not count virtual time advanced via `advanceTimeBy()`/`advanceUntilIdle()`. So a DLT retry test can freely use the production `DltRetry.DEFAULT_MAX_ATTEMPTS` and uncapped `backoffMillis` even though cumulative simulated backoff reaches many seconds or more — advancing that much virtual time costs no measurable real time.

Because the budget is real time, it also has to cover a test JVM's cold start, which the first test in each module pays: loading MockK and ByteBuddy, creating the first H2 database and starting Exposed, Ktor's test engine, Koin, the ProtoBuf serializers. Locally that is 0.75s to 4.2s (`CommunicationDataSourceImplTest`). On a GitHub runner shared by parallel Gradle test JVMs and the Testcontainers suites it went past the old 5-second budget, and CI failed a different module's first test each run with `UncompletedCoroutinesError` ("the test body did not run to completion") while every test passed locally. A Linux container capped at `--cpus=0.25` reproduces it. That is why the budget is 30 seconds, and `routeTest` runs on `runUnitTest` like everything else. Don't lower it to catch slow tests: the first test's time measures the JVM, not the test. For the same reason, keep real cryptography out of unit tests. RSA-2048 key generation is a random prime search with a long tail. `GetActiveSigningKeyImpl` and `RotateSigningKeysImpl` take a `SigningKeyPairGenerator` (bound in `signingModule` to `RsaSigningKeyFactory::generate`, scoped because every service scope loads the module), and their tests stub it. A test that only passes keys through uses `SigningKey.stub()`.
